# Fleet format

A fleet describes the hosts that `personal-skills` syncs. Sync it with `python3 scripts/sync.py --dry-run`, then `python3 scripts/sync.py`; the per-file tools named below are the steps it runs. The public `example/` folder shows the format with made-up values. Your real fleet lives in a private fleet directory with the same layout, outside this repository.

```
example/                     public, made up
  hosts.json
  paseo-providers.json       optional
  client-config.json         optional
  global/AGENTS.md           optional
  bin/common/hello-fleet    optional helper example
<fleet directory>/           yours, private (copy example/ here and edit)
  hosts.json
  paseo-providers.json       optional
  client-config.json         optional
  global/AGENTS.md           optional
  skills/<name>/SKILL.md     optional private skills (the overlay)
  bin/common/               optional helpers for every host
  bin/macos/                optional macOS helpers
  bin/linux/                optional Linux helpers
  bin/windows/              optional Windows helpers
```

## Where the fleet lives

`python3 scripts/fleet.py resolve` prints the directory in use. The first match wins:

1. `$LOADOUT_FLEET`, a directory. If it is set but missing, resolution fails instead of falling back.
2. `${XDG_CONFIG_HOME:-~/.config}/loadout/fleet/`. On Windows, `%APPDATA%\loadout\fleet\`.

With neither, `fleet.py resolve` reports `fleet: none (current host only)`, and `sync.py` and every step stop with nothing synced until you create a fleet. To sync only this host, create one whose `hosts.json` lists just this host as `source_host`.

### Fleet push

Edit the fleet only on the source host. `python3 scripts/fleet.py push [--dry-run] [--host <name>]` copies its published files, `hosts.json`, `paseo-providers.json`, `client-config.json`, `global/AGENTS.md`, and `bin/`, to `~/.config/loadout/fleet/` (`%APPDATA%\loadout\fleet\` on Windows) on every other `ssh` host, and every sync run does this first. Every other file, such as a token file, a pairing offer, a backup, or notes, stays on the source host; a file an earlier push copied and the push no longer publishes is removed from a host whose copy is unedited. Hosts need `node`.

- Each copy carries a `.loadout-sync.json` record of the hashes last synced, and a host's copy is replaced only while it still matches that record. Before writing, a push records there the versions it is about to write, so a push cut off part way recognizes its own writes.
- A hand-edited, added, or unrecorded differing file is a conflict: nothing is written on that host until you resolve it, usually by deleting the host's copy.
- Each file and the record are written through a uniquely named, exclusively created temp file, and the record is read back. Each copied file is verified by SHA256, and the resulting copy is verified again after writing. Each write and removal checks its file and the directories from the home directory down again right before it, and a removal first moves the file aside and verifies it, so a linked `~/.config` or a file edited during the push stops the host and keeps the edit.

### Helpers in `bin/`

The optional private `bin/` holds portable plain files only. The skills step installs `common/` plus the host's `os` folder flat into `~/.local/bin` (`%USERPROFILE%\.local\bin` on Windows), with verified bytes and local-edit protection recorded in `loadout/global-sync.json`. Identical existing files are adopted (an identical destination symlink is atomically replaced by a regular file without changing its target), differing unrecorded files are conflicts, and only recorded, unedited files retire on a full run. On macOS/Linux, extensionless files and `.sh` files are `0755`, others `0644`. Duplicate common/OS names, links, nested directories and nonportable names stop the run. Real helpers stay in the private fleet, never in this public repository.

## Private skills

Put skills that must stay private (personal, account-bound, or holding credentials) in `skills/<name>/` inside the fleet directory on the source host, laid out like any installed package with a `SKILL.md`. The skills step installs them with the published ones, with the same `--skills` and `exclude_skills` selection and the same local-edit protection:

- A name that is also a published skill stops the run; rename one of them.
- Every overlay file hash a host has accepted is recorded in `skills/.loadout-overlay.json`, so a newer version replaces an older installed one while a hand edit on a host stays a conflict. A skill that moved here from the public repository also replaces its last published copy.
- A skill removed from the overlay is retired from hosts like an unpublished package (see `Local-edit protection` in `SKILL.md`), so keep the overlay complete and check `--dry-run` first. With `skills_overlay: true` in `hosts.json`, a missing `skills/`, or one that is not a directory, stops all retirement on every host, each reported as `blocked`. To retire every overlay skill, leave an empty `skills/` directory.
- Hosts install overlay files owner-only: on macOS and Linux as `0600` files in `0700` directories the sync creates (a replaced file keeps stricter permissions, and files and directories an earlier sync installed lose group and other access). On Windows they inherit the user profile's ACL.
- `__pycache__`, `.pyc`, and `.DS_Store` are skipped; symlinks are errors.
- The fleet push does not copy `skills/`; skill bytes travel only through the skills step.

## hosts.json

`python3 scripts/fleet.py validate` checks the file and prints each host's transport and sync scopes. Unknown keys and values are errors.

- `schema_version`: `2`. A file without it is version 1: `transport` is free text, every host is reached over SSH, and hosts have no `transport` or `sync` of their own.
- `source_host`: name of the host whose checkout is the sync source. It runs locally, so it must use `ssh`.
- `transport`: default for every host; `ssh`, the only value. Record host names, not IP addresses that may change.
- `notes`: optional free text.
- `skills_overlay`: optional, `true` or `false` (default). `true` says this fleet keeps private skills in `skills/` (see Private skills).
- `hosts[]`: one entry per host.
  - `name`: address used by the transport; for `ssh`, the SSH alias. Letters, digits, `.`, `_` and `-`, not starting with `-`.
  - `os`: `macos`, `windows`, or `linux`.
  - `transport`: optional, overrides the top-level value.
    - `ssh`: files and commands travel over SSH.
  - `paseo_offer`: optional path to a file holding the host's Paseo pairing offer; the providers step then reloads that daemon through the offer instead of over SSH. A relative path resolves inside the fleet directory. Keep offers private: the fleet push never copies one and refuses to run while an offer resolves to a file it publishes.
  - `paseo_home`: optional Paseo home for this host's daemon, absolute on that host or starting with `~`. The plugins and providers steps use it for that host only (plugin config reads, settings backups, installs, reloads, `plugin ls` confirmations, the provider config merge and reload). The skills step still finds a Pi runtime from the default `~/.paseo/config.json`. An inherited `PASEO_HOME`, `PASEO_HOST`, `PASEO_AGENT_ID` or `PASEO_AGENT_CWD` (from an agent session, a scratch daemon, or a shell profile) is always cleared first, so without `paseo_home` the default `~/.paseo` and its daemon are used. A host with `paseo_offer` reloads through its offer whatever this says.
  - `sync`: optional list of scopes from `skills`, `plugins`, `providers`, `client-config`. Default: `skills`, plus `plugins` when `paseo` is present. A host outside a scope is reported as skipped, not failed. `providers` (Paseo provider pickers) and `client-config` (managed Codex and Claude Code settings) are opt-in.
  - `exclude_skills`: optional skill names the skills sync leaves alone on this host, such as a package you keep a private version of.
  - `checkout`: path to a local Git checkout of this repository, or `null` (the default). A host without a checkout receives verified bytes from the source host and reverifies them.
  - `clients`: clients to sync, from `codex`, `claude`, `opencode`. Required when `sync` includes `skills`. Absent clients are skipped and reported.
  - `paseo`: optional. Paseo plugin sync for this host's daemon. Required when `sync` includes `plugins`.
    - `plugin_root`: directory where verified plugin sources are staged, one subdirectory per plugin ID. Changing it for a host with installed plugins needs the manual move in the `Paseo plugins` section of `SKILL.md`.
    - `stage`: plugin IDs whose verified source is copied to `plugin_root`, installed with `npm ci`, and checked.
    - `install`: plugin IDs, a subset of `stage`, authorized for `paseo plugin install` on this daemon. List a plugin here only after its host-local settings and arming have been decided.
- `global`: optional. Maps each client to where `global/AGENTS.md` is installed. A target is a path starting with `~`, `/`, `$VAR` or `${VAR}`, `%VAR%`, or a drive such as `C:\`, and must be absolute once the host expands it. `fleet.py validate` rejects anything else, and a host refuses a target that is not absolute or names a variable it does not set.
  - `codex`: normally `$CODEX_HOME/AGENTS.md`.
  - `claude`: normally `~/.claude/CLAUDE.md`. For a managed deployment, `managed-settings:claudeMd` installs the instructions as the `claudeMd` string field of Claude Code's `managed-settings.json`: `/Library/Application Support/ClaudeCode/` on macOS, `/etc/claude-code/` on Linux, and `%ProgramFiles%\ClaudeCode\` on Windows (`C:\ProgramData\ClaudeCode\` only when that file exists and the Program Files one does not). Only `claudeMd` changes: the file is backed up beside itself as `<file>.bak-<UTC stamp>` (see [Backup retention](#backup-retention)), then replaced atomically and checked. When the user cannot replace it, macOS and Linux use `sudo -n` and keep its owner and mode; if that needs a password, nothing is written. On Windows run the sync from an administrator shell. `--dry-run` reports whether elevation is needed. `LOADOUT_CLAUDE_MANAGED_SETTINGS` on the host overrides the file path, for tests.
  - `opencode`: normally `~/.config/opencode/AGENTS.md`.

Omit `global` or `global/AGENTS.md` to skip global instructions. Global instructions follow the same preflight: never overwrite a changed target that matches no known prior version. For `managed-settings:claudeMd` the preflight compares the field's value, a missing file or field is added, and unparseable JSON or a non-object is a conflict.

Plugin settings, plugin state, and the daemon's `pluginsEnabled` switch are host-local. The sync never writes them (see `Paseo plugins` in `SKILL.md`).

## paseo-providers.json

Optional. The providers step (`python3 scripts/paseo_providers.py`) reads it and updates hosts whose `sync` includes `providers`. It holds router URLs and host settings, so it stays in the private fleet directory.

- `providers`: pinned blocks keyed by Paseo provider, such as `claude` or `codex`. Each block's fields replace the same fields in the host's `agents.providers.<provider>`; other fields there are kept. `models[]` rows need a unique `id` and a `label` that is a name only: no digits and not the model ID.
- `env`: optional default environment per provider, merged into `agents.providers.<provider>.env` on every host. A value's `%VAR%` is expanded from the host environment and written in plain text to `config.json` and its backups, so `%VAR%` must never name a secret; names containing KEY, TOKEN, SECRET, PASSWORD, CREDENTIAL or AUTH are refused with nothing written.
- `launch`: optional launch settings for the `claude`, `codex` and `pi` providers, so routing reaches only Paseo-launched agents while a terminal `claude` or `codex` keeps the user's own login. Example: `example/routed-launch-overlay.json`.
  - The providers step wraps each provider that has settings in the `loadout/mcp-env.cjs` launcher as `node mcp-env.cjs --provider <id> -- <command>` and records the settings in `loadout/mcp-env.json`; both are non-secret. The directory is `${XDG_CONFIG_HOME:-~/.config}/loadout` on POSIX and `%APPDATA%\loadout` on Windows. A provider with no `command` set is wrapped as its bare name; a `claude` or `codex` with settings but no row in the host config gets a row holding just that wrapped command; `pi` settings need a `pi` row.
  - On Windows the launcher resolves a bare name as Paseo does: each `PATH` directory in order (surrounding quotes removed) with the `PATHEXT` extensions, then winget package executables. It runs a `.exe` such as `claude.exe` directly. For an npm `.cmd` shim such as `codex.cmd` it runs what the shim runs, without `cmd.exe` (the shim's Node script under the shim's `node.exe` or this Node, or the shim's `.exe`), so stdio and `app-server` work unchanged and no argument is expanded. Any other `.cmd` or `.bat` runs through `cmd.exe`, refused when an argument holds `%`, `!`, `^`, `&`, `|`, `<`, `>`, `(`, `)` or a control character.
  - `tokenFiles`: env name to a file on the host, absolute or starting with `~/` or `~\` (the user's home, `%USERPROFILE%` on Windows), such as `{"ANTHROPIC_AUTH_TOKEN": "~/.config/example-router/api-key"}`. The file holds the bare value on one line and is delivered separately. **Owner-only check**: on POSIX the file is owned by the harness user with mode `0600`; on Windows its ACL must have inheritance off, an owner that is the current user, SYSTEM or Administrators, allow rules only for those or OWNER RIGHTS, and an allow rule for the current user, compared by SID; no link, junction or other reparse point may sit anywhere on the path. The launcher checks the ACL on the handle it reads through, opened so the file cannot be replaced, renamed or written meanwhile, reads the value into the child environment at launch, and fails closed on a missing, linked or unsafe file. The sync never copies or reads the value; it checks only that the file is present and owner-only, reported per host, and a real sync fails the host otherwise. The value is never written to `config.json`, `mcp-env.json`, or any client file, so it cannot go in `env`. Keep the non-secret `ANTHROPIC_BASE_URL` in `env`.
  - `args`: strings the launcher puts right after the executable, as global flags before any subcommand Paseo adds, such as `["-c", "model_provider=\"example_router\""]` for `codex app-server`. The host's provider command must then be the executable alone, and the named provider section (`[model_providers.example_router]`) must exist in that host's `~/.codex/config.toml`, for example through `client-config.json`.
  - A host's `hosts.<name>.launch.<provider>` replaces the top-level entry for that provider; `{}` drops it. Dropping a provider's settings unwraps its command on the next sync unless fleet MCP env files still need the launcher. Without `launch` settings, Windows provider commands stay unwrapped.

To create a Windows token file, run `scripts/new_token_file.ps1` as the user the Paseo daemon runs as, under the secret runner so the value arrives in an environment variable and is never typed or printed (`ROUTER_KEY` stands for that variable):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\new_token_file.ps1 `
  -Path "$env:USERPROFILE\.config\example-router\api-key" -FromEnv ROUTER_KEY
```

It refuses an existing file and any link or junction on the path, creates the file with a protected ACL granting only the current user's SID, reads that ACL back from the open handle, and stops before writing the value, removing the empty file, if anything differs. To replace a value, delete the file first.

- `disabledProviders`: optional list of provider ids to turn off, such as `["example-retired"]`. Each listed id gets `enabled: false` in `agents.providers.<id>`, keeps its other fields, and loses its `models` key, so its picker shows none. Removing a block from `providers` alone leaves the host's old block as it was. An id may not also be in the host's effective `providers`, and `pi`, `claude` and `codex` are refused. The dry run and the result line name only the ids that run turns off.
- `hosts`: optional settings by host name, each for a host with the `providers` scope.
  - `disabledProviders`: replaces the top-level list for this host; `[]` disables none.
  - `launch`: per-provider launch settings layered over the default, as above.
  - `env`: per-provider values layered over the default.
  - `inherit_env`: `false` skips the default `env`, so the host keeps its own values.
  - `required_env`: per-provider variable names that must be set after the merge, or the host fails without a write.

## Pi surface on stock Paseo

`paseo-providers.json` may contain `pi` with `root`, `catalogSources` (normally `claude` and `codex`), `defaultSourceProvider`, and `runtime`; hosts can override `pi`. `example/pi-provider-overlay.json` illustrates the fields. The providers step generates Pi's `models.json` from the same provider rows on every selected host; do not maintain a separate Pi model list. Canonical labels are Opus, Sonnet, Fable, Haiku, Astra, Sol, Luna, Web Extra, Web Pro, one row per label. A row may include `api` and `apiModelId` when the backend needs a different API or catalog ID than the native CLI (copy the backend ID from its model list; a native Claude catalog can keep its context suffix while the row records the router's exact unsuffixed ID). Native routes remain available. On POSIX hosts `fleet-routing.mjs` keeps each agent's Pi session files 600 and their directories 700, since Pi creates them under the normal umask and they hold transcripts.

Optional `pi` keys:

- `pi.claudeApiKeyRoute`, `{"prefix": "api", "labelSuffix": "API"}`: adds a second Pi entry per Claude row, directly after it, labeled for example "Opus API", whose model ID is `<prefix>/<apiModelId>`, for a router that pins that prefix to a pay-per-use API key. It copies the Claude row's transport, context window, output limit and thinking options, so verify the key's real context window first. Pi only.
- `pi.contextWindows`, for example `{"Opus": 400000}`: Pi's context window per canonical label (API entries included) when the backend's cap is below the catalog default (1,000,000 for Claude rows, 272,000 otherwise). Pi's context meter and compaction trigger read it.
- `pi.maxTokens`, for example `{"Opus": 65536}`: output cap per canonical label in place of the default 32,768, validated like `pi.contextWindows`.
- `pi.labelOrder`, for example `["Fable", "Opus", "Sonnet"]`: puts those labels first in Pi only, each followed by its API entry; unlisted labels keep catalog order and direct provider rows stay last.
- `pi.options`: becomes the generated row's `agents.providers.pi.options`, for example `{"rpcTimeoutMs": 900000}` so Pi can acknowledge a prompt after a long pre-prompt compaction instead of failing at Paseo's 60-second default. Paseo accepts `sessionDir`, `rpcTimeoutMs` and `extensionTimeoutMs` and applies them to sessions started after the reload; a running agent keeps old values until `paseo agent reload <id>` or a daemon restart. `rpcTimeoutMs` bounds every Pi RPC, so a hung Pi also takes that long to fail. Removing `pi.options` leaves the host's existing value.

New picker rows need a daemon config reload. **Compaction sizing**: Pi compacts above the context window minus `compaction.reserveTokens`, and caps a summary, thinking included, at min(0.8 x `reserveTokens`, `maxTokens`); a summary that outgrows the cap fails and retries the whole request. So keep a reserve of at least 40,960 for the default 32,768 cap, and when raising `maxTokens` also raise `compaction.modelOverrides.<model>.reserveTokens` in the Pi settings, keyed by the exact `provider/modelId` (for example `fleet/<apiModelId>`, and `fleet/api/<apiModelId>` for an API entry), to at least 1.25 x the new cap (81,920 for 65,536).

### Pi runtime

`runtime` describes the router `route` (TOML path and key path) or `baseUrl`, an existing `credential` reference, optional `credentialHeaders`, `python` (Python 3.11+), and the loopback `paseoMcp.url`. The router base URL must use https unless its host is loopback (`127.0.0.1`, `localhost`, `::1`), because the key travels as a Bearer header. Credentials resolve at request time through an existing text, env, env-file, JSON, TOML or command source.

**Command credentials.** A `command` source, `{"kind": "command", "argv": [...]}`, keeps the value in an OS secret store: `credential.py` runs that fixed argv without a shell and reads one line from stdout, which goes only to Pi; stderr is dropped and nothing is cached, so a rotation applies to the next request. The program must be an absolute path to an allowlisted helper: macOS `security find-generic-password ... -w` (Keychain), Linux `systemd-creds decrypt ...` ending in `-` (decrypt to stdout), or a Python interpreter running a helper script file (for example one unwrapping a Windows DPAPI copy), never `-c` or `-m`. The allowlist checks only the program file name and shape, since the source host checks every host's runtime; a wrong path fails on the target at request time. A Python helper runs whatever script you name with your authority, and argv is stored in `runtime.json` and visible in the process list, so never pass a value in argv.

**Credential refresh.** Pi itself would run the command once for the router key and once per `credentialHeaders` header on every request, one 10 s try, so a loaded host could fail a turn. So before each model request of a run, each manual or automatic compaction and each branch summary, `fleet-routing.mjs` runs the router's `credential.py` command itself, without a shell: up to 3 tries of at most 15 s, 1 s and then 2 s apart, handing the value to Pi as the router key and headers in that Pi process's memory only. When every try fails it reuses its last successful read for at most 15 minutes; without one, Pi runs the command itself and, failing that, fails the request (`Failed to resolve API key`). A run keeps the value lent until it ends, a compaction until it succeeds or fails, and a branch summary (whose end Pi does not announce) while its refresh runs plus a 30 s lease; after that, or once the held value is 15 minutes old, Pi runs the command itself again. The value is never written to a file, a log, argv or the environment. Route evidence gets a `credential` row only for an outcome other than a first-try read: `read-after-retry`, `last-good` (with its age), `unavailable`, `expired` or `override-failed`.

**Fleet compaction.** For a router model the extension writes the compaction summary itself with Pi's own `compact()`, using the lent credential and the headers Pi's own summary request carries (service tier, client request id), with at most 2 retries:

- Thinking level: the lower of the agent's level and `compaction.thinking` (default `medium`), clamped to the model's levels as Pi clamps its own. `compaction.lengthBound` (default: under 8,000 words, finished items dropped) is appended to any `/compact` instructions. Both are optional `runtime` keys: `thinking` is a Pi level (`off` to `max`), `lengthBound` one line of at most 1000 characters. Pi's prompts, split-turn summary and file lists otherwise stay as in its own compaction.
- File lists: before every compaction, on any provider, the extension adds the previous fleet summary's lists to Pi's preparation, and keeps at most `compaction.maxFiles` paths per list (optional `runtime` key, a whole number from 0 to 100000, default 100, 0 keeps all), most recent first by the last call that touched each path. A path is in exactly one list, modified if among the kept modified paths, else read. This applies to Pi's default compaction too. A fleet summary that dropped paths ends with one line giving the count; the previous summary's file block and count line are removed before summarizing, so each summary carries one block and at most one line, at the end.
- compact() is used only from a tested Pi version (1.0.0) with its known shape, and Pi saves the result. If that summary fails or comes back empty, Pi's default compaction runs as a second full attempt, and a `compact_failed` row with `fallback: "pi-default"` records the first failure (`errorKind` `unavailable` when compact() could not be loaded or has another shape).
- Evidence: each saved summary gets a `compact` row with its reason, `fromExtension`, model, thinking level, `outputTokens` (reasoning included), `summaryChars` and `tokensBefore`. A failed compaction gets a `compact_failed` row with its reason, `aborted`, `errorKind` (`token-cap`, `aborted` or `upstream`), `httpStatus` (from Pi's `failed: NNN:` or a provider's `API error (NNN)` text, or null), session id, model and thinking level. Neither row holds summary or upstream error text.

Direct providers keep Pi's own per-request command and compaction.

**Gmail.** An optional `gmail` object (`email`, `home`, optional loopback callback `port`) adds a read-only Gmail MCP server from the `workspace-mcp` package installed in `home/venv`. `home` holds the OAuth client JSON and token, owner-only, never synced; on POSIX, configure refuses a group- or other-accessible `home`. Read-only is enforced three times: `--read-only` (the `gmail.readonly` scope), write and auth tools passed to `--disabled-tools`, and Pi exposing only an allowlist of read tools through Codemode. To use a shared Gmail server instead, remove this block and declare `mcpServers.gmail` in `client-config.json` (see [Fleet MCP servers](#fleet-mcp-servers)). Pi reads `mcp.json` at session start, so writing it needs no daemon reload.

**Direct providers.** An optional `directProviders` object adds OpenAI-compatible endpoints that bypass the router, such as a local model gate: `{"<name>": {"baseUrl": "https://gate.example.test/v1", "api": "openai-completions", "auth": "none", "models": [{"id", "name", "reasoning", "input", "contextWindow", "maxTokens", "cost", "thinkingLevelMap"}]}}`. Each model, listed once, becomes a `models.json` provider and a picker row `<name>/<id>` labeled with its `name`, with thinking options from the non-null `thinkingLevelMap` levels (Medium preferred as default). `auth` is `"none"`, which gives Pi the dummy key `local-no-auth`, or `{"credential": <source>}` for an endpoint that wants a Bearer token (`example/pi-provider-overlay.json` shows one backed by the macOS Keychain); Pi's key is then a `!command` running `credential.py` on that source per request, so Pi sends `Authorization: Bearer <value>` and the value never lands in `models.json`, `runtime.json`, agent copies or logs. The source must be an exact reference with only its kind's fields (`env`: `name`; `text`: `path`; `env-file`: `path`, `name`; `json`, `toml`: `path`, `keys`; `command`: `argv`) and no `prefix`; a literal value, a plain string, an unknown kind or any other key is refused. A missing or failed credential fails only that provider's requests (`Failed to resolve API key for provider "<name>"`). Use https or an already encrypted hop. Headers, `compat` flags, other APIs and the names `fleet`, `opencode` and `llama.cpp` are rejected. These routes have no service tier, so Fast is never offered. No key contents belong in this file.

**Codemode and skills.** Generated Pi settings fix built-in Codemode on with `defaultTools: ["+codemode"]`; no profile, feature or per-agent flag enables it. Sync validates these settings, the runtime fails closed if the effective session settings or active tools lack Codemode, and session evidence records the check. The skills sync discovers the configured official Pi home from the host provider command and installs the same selected, manifest-verified skills under `agent/skills`, which generated settings reference. Global instructions sync to `agent/AGENTS.md` and are copied into each agent home at launch. The settings carry the source provider's default model and thinking. Pi exposes only its supported thinking levels; Web models keep model-fixed thinking. Native `ultra` and `ultracode` selections need an explicit native fallback because Pi 1.0 has no such selector.

An optional `guard` object, `{"protectedServices": ["<launchd label>", "<systemd unit>", "<process name>"]}`, names the shared fleet services a Pi agent must not stop by hand: the model bridge, the router, a Paseo daemon, Tailscale serve. `service-guard.mjs`, which `fleet-routing.mjs` loads, checks every `bash` and `powershell` call (nested Codemode calls too) and refuses, with a reason naming the rule, a command that would stop one. The defaults `Paseo Daemon`, `Paseo Supervisor`, `paseo-daemon`, `@getpaseo/server`, `tailscaled` and `tailscale` always apply, and entries add to them. A name matches when a target contains it or, at 4 characters or more, is part of it, ignoring case, spaces and underscores, with Windows backslashes read as slashes. This is a backstop against a forged instruction, not a sandbox. It covers exactly the shapes listed below; everything else is a known gap.

Covers, for a protected name:

- Stop verbs: `launchctl bootout|unload|remove|kill|disable|stop` (and `launchctl bootout` of a whole domain such as `gui/<uid>`), `systemctl [--user] stop|disable|kill|mask|restart` (and `stop` of a unit glob with no literal part of 4 or more characters, such as `'*'`), `service ... stop|restart`, `brew services stop|restart`, Windows `Stop-Service` (`spsv`), `Restart-Service`, `Suspend-Service`, `Set-Service -Status Stopped` or `-StartupType Disabled`, `sc stop|config ... disabled`, `net stop`, `schtasks /end|/delete|/change /disable`, `Stop-ScheduledTask`, `Disable-ScheduledTask`, `Unregister-ScheduledTask`, `paseo daemon stop|restart|uninstall`, `paseo restart` (behind any global option such as `--host`), and `tailscale down|logout|switch`, `tailscale set --shields-up` or `tailscale serve|funnel ... off|reset`, with options anywhere.
- Kills: `kill`, `pkill`, `killall`, `taskkill` and `Stop-Process` of a protected name; of a PID whose command line (read with `ps`, or `Get-CimInstance` on Windows) names one, or that exists but cannot be read; `pkill`/`killall` patterns that match a protected process on the host (run as a regex in a `vm` context with a 250 ms limit; a pattern that runs over it is refused); `Stop-Process -Name` and `taskkill /IM` of an image name a protected process runs as (`node.exe` for a Paseo daemon); a `kill` of a PID read from a file the command reads (`kill $(cat <file>)`, `xargs kill < <file>`, `pkill -F <file>`) when that PID names one. Always refused: `kill -1`, `kill 0`, process groups (`kill -- -N`), and a `pkill`/`killall` that selects by user, group, session or terminal with no pattern (`pkill -u $USER`, `pkill -u501`).
- Host-wide stops, which stop every protected service: `reboot`, `shutdown` (except `-c`), `halt`, `poweroff`, `init` or `telinit` `0|1|6|s`, `systemctl reboot|poweroff|halt|kexec|soft-reboot|exit`, `launchctl reboot`, `loginctl terminate-user|kill-user|terminate-session|kill-session`, `shutdown.exe /r|/s`, `Restart-Computer`, `Stop-Computer`. Their refusal says a planned reboot of another host needs its owner or Config PM, or the OS update's maintenance window.
- Parsing like the shell: quotes (`'...'`, `"..."`, `$'...'`, PowerShell's), escapes, brace expansion, comments, heredocs and here-strings, `NAME=value` and `$HOME`/`$PWD` expansion, and operators splitting segments. `$(...)`, backticks, process substitutions and PowerShell `(...)` are checked as commands of their own. Wrappers (`sudo -u <user>`, `nice -n <n>`, `timeout`, `xargs`, `nohup`, `setsid`, `env`) are skipped with their option values.
- Command strings: `bash -c`, `su -c`, `eval`, PowerShell `Invoke-Expression`/`iex`, `env -S`, `pwsh -Command` and `-EncodedCommand`; `bash -c "$(cat <file>)"`, `eval "$(cat <file>)"` and a `$(cat <<EOF ...)` body are checked as that file or heredoc text.
- Text a shell reads: a heredoc into a shell, `bash|sh -s` or `-`, a shell with no script, `sudo -s`/`-i` (combined flags such as `-sE` too), `doas -s` and `su` with no command read stdin; their `<` file and the `echo`, `printf`, `cat` heredoc and `cat <file>` text of the whole upstream pipeline (through filters such as `cat`, `{ ...; }` groups and subshells) are checked, as are `bash <(...)`, `bash < <(...)`, `bash <<< "$(...)"`, `source <(...)` and `echo ... > >(sh)`.
- Scripts: a local script a command runs (`bash|sh|zsh <file>`, `source <file>`, `./file` behind wrappers, `pwsh -File <file>`, `& <file>`, `bash --rcfile <file>`, `rg --pre <file>`) is read and checked the same way, four levels deep: a script over 256 KB or nested deeper is refused, a binary is skipped, and a relative path is resolved against every directory the command may have moved to with `cd`, `pushd` or a subshell; a script whose name names a stop that cannot be located after an unfollowed `cd` is refused. A file the same command writes with `cat` or `tee` and a heredoc, `echo`/`printf` and a redirect, or a `tee` fed by a pipe (its `echo`/`printf` text or the files it `cat`s) is checked as written when a later segment runs it.
- Remote commands: the command of `ssh <host> '<cmd>'` or `ssh <host> -- <cmd>`, and with no remote command or a remote command any segment of which runs a shell reading stdin by the local rule above (behind `sudo`, with options, after `cd ... &&`), the `<` file and the piped text, are checked against the default fleet-wide entries only, since per-host lists, PIDs and processes are local. So is the local copy of a script that a remote segment runs by the local rule, quoted or not (`ssh <host> 'bash stop.sh'`, `ssh <host> bash stop.sh`, `sudo bash ./stop.sh`, after `cd ... &&`).
- Computed targets: a refused verb whose target is not written out (a substitution, variable, glob, `xargs` placeholder or piped input) is refused when any argument names a protected service (4+ character parts and glob fragments count, as in `kill $(pgrep -f Paseo)` or `Get-Process *paseo* | Stop-Process`) or a `pgrep` pattern in it matches a protected process.
- Mentions: text in quotes is also checked, where only a literal protected name refuses: `echo "launchctl bootout <protected label>"` is refused, `git commit -m "pkill on server shutdown"` is not. A path in quoted text is not read as a script (`python3 -c "...open('$F')..."`). So is a heredoc or here-string read by a compound command (`while read ...; done <<EOF`), a computed command name (`"$SHELL" -s`), a command with a shell, `ssh` or `su` among its arguments (`pkexec bash`, `docker exec -i <c> sh`, `sshpass -p <pw> ssh <host>`), a program whose stdout is piped on, `source`, `.`, `eval`, `read`, `mapfile`, `at`, `batch`, `crontab`, `busybox`, `toybox`, `parallel`, `script`, `make`, `expect` or `osascript`, or by `cat` or `tee` that writes a file or sits in a substitution outside a data command. A refusal that only a mention found adds a tip to put the text in a file and pass the file; a finding from a real command (`bash -c`, `eval`, `su -c`, `ssh <host> '...'`) wins over it. The `$(...)` and backticks of a heredoc with an unquoted delimiter are checked as commands wherever it goes.

Data, never checked as commands: the arguments of `grep`, `egrep`, `fgrep`, `rg`, `ag`, `ack` and `journalctl`, the messages of `git commit`, `git tag` and `git notes` (by git's subcommand), the arguments and stdin (a message given as `-`) of the message senders `paseo send`, `paseo agent send`, `fleet-send` and `codex-send`, and a heredoc or here-string read by any other program (`python3 -`, `node -`, `cat` to the terminal or in a substitution inside a data command), so `journalctl -u tailscaled | grep -i kill`, `git commit -m "docs: tailscale down"`, `fleet-send <id> "...restart tailscale..."` and `python3 - <<'EOF'` with such text pass. Their substitutions, `env -S` strings and other segments still are, and a segment that defines a function (`grep() { ...; }`) is never data. A sender call is data only when the whole command (each text the guard parses, through the rest of the check) has no function or alias definition, `source`, `.`, `eval`, `hash`, `enable`, `PATH` assignment or export, other segment naming a file called like a sender, or subshell or `{ }` group piped on, and the call itself is the bare name (no path, `paseo` only for `send` or `agent send` with no word `daemon`) behind nothing but assignments, `env` without `-S` or `nice` (so not `sudo`, `watch`, `timeout` or `xargs`), with its stdout neither piped nor redirected anywhere but `/dev/null` or stderr, and outside any substitution of a segment that is not data; otherwise it is checked as any other command. Allowed: `kill $!` (or a variable holding `$!`) after a `&` in the same command, the command's own background job, as in `mkdocs serve & sleep 2; kill $!`.

The one exception is a repair script run detached from Pi, started from the `bash` tool (a repair started from the `powershell` tool is always refused), with no `trap` anywhere in the command, and with stdout and stderr both redirected to a file or `/dev/null` (`>file 2>&1`, `>/dev/null 2>&1`, `&>file`; the path is resolved, with `~` expanded, and must not be under `/dev/` or `/proc/` other than `/dev/null`, so not `/dev/stderr`, `/./dev/stderr` or `/dev/fd/N`, nor a process substitution such as `> >(tee log)`; a `~user` target never counts, and after a `cd` the guard could not follow only an absolute or `~/` target does): either `nohup <cmd> &` as the last segment of the whole command with no other job in it left in the background, such as `nohup bash fix.sh >log 2>&1 &`, or `setsid -f <cmd>` (or `setsid <cmd> &`). Pi stops tracking the shell once it exits, so a job it leaves behind survives a later cancel; anything after the backgrounded `nohup` (`& wait`, `; echo`, `&& ...`) keeps the call open, so a cancel or timeout kills the script halfway, and without both redirects it dies of SIGPIPE once Pi stops reading. Inside the script each stop must be undone by its pair, in order, with a target that equals the protected entry once a domain such as `gui/<uid>/`, the directory, `.plist` and `.service` are stripped (`bootstrap` and `load` need a `.plist` path): `bootout`, `unload` or `remove` by `bootstrap` or `load`; `unload -w` by `load -w`, or by `enable` and then `bootstrap` or `load`; `disable` by `enable`, then `bootstrap`, `kickstart` or `start`; `mask` by `unmask`, then `start`; `stop` or a kill by `start`, `restart` or `kickstart`; `paseo daemon stop` by `paseo daemon start|restart`; `tailscale down` by `tailscale up`; `Stop-Service` by `Start-Service`; a `restart` is its own pair. Then a health check must follow (`curl`, `wget`, `nc`, `pgrep`, `paseo daemon status`, `paseo ls`, `launchctl print`, `systemctl is-active|status`, `tailscale status`, `Invoke-WebRequest`, `Get-Service`). Restarts and health checks count only as the command, with the restart verb as its subcommand, of an unconditional top-level segment, behind no wrapper other than `sudo` (without `-l`, `-v` or `-k`), `env` and `nice`: not after `&&` or `||`, not in an `if`, `while`, `until`, `for` or `case` block, a `{ ...; }` group opened after `&&` or `||`, a function body (its `{` on the header's line or the next) or a subshell. An `exit`, `return`, `logout`, `exec <cmd>`, `kill $$`, `source` or `.` between the stop and the health check, or errexit before it (`set -e`, `set -o errexit`, the runner's `bash -e` or `-o errexit`, a shebang with `-e`, or `SHELLOPTS` naming `errexit`), voids the exception. Write such a script with the write tool: a heredoc that writes it is refused because its body names the stop.

Known gaps, which pass: a command name built at run time (`"$(echo launchctl)" bootout ...`); a default expansion such as `${X:-launchctl} bootout ...`; a verb built by a substitution (`launchctl $(echo bootout) ...`); `printf` formats (`printf 'kill %s' <pid> | sh`); an interpreter other than a POSIX shell or PowerShell (`python -c`, `node -e`, `busybox sh`); a binary; an MCP tool; a package script (`npm run stop`); `find ... -exec sh {} \;`; `git rebase --exec`, `git bisect run`, `git -c core.editor=...` and `GIT_EDITOR`; editors and other tools that run commands; `ssh -o RemoteCommand=...` or `ProxyCommand`, `tailscale ssh` and `mosh`; a file recorded by this command and then moved or copied (`mv a.sh b.sh && bash b.sh`), and a file copied in the command (`cp stop.sh s.sh && bash s.sh`, `cat stop.sh > s.sh; bash s.sh`); in a repair script, a `sleep`, `tail -f` or `wait` between the stop and its restart, and a redirect target that reaches `/dev/` through a symlink; a `kill` of a port lookup such as `kill $(lsof -ti :<port>)` when nothing in the command names a protected service; a script named only inside a quoted argument of a tool that runs it through a shell (`watch "bash stop.sh"`); a file another program writes from a heredoc and the command then runs (`sponge s.sh <<EOF`, `python3 - <<EOF`); for the `nohup` form, a background job started inside a `bash -c` string or a script the command runs (`bash -c 'yes &'; nohup ...`), which keeps the call open; ssh options after the host, which hide the remote command (`ssh <host> -t reboot`, `ssh <host> -o HostName=... reboot`); `watch` running a data command through a shell (`watch git commit -m '; ...'`); and a data command's output piped to a shell (`grep -h . <<< '...' | sh`).

Known over-refusals: `echo` or `printf` text or a quoted `ssh` remote command naming a refused form with a protected target, and a heredoc with such text that a mention consumer above reads (`cat > notes.md <<EOF`, `cat <<EOF | python3 -`, `X="$(cat <<EOF ...)"`, `while read ...; done <<EOF`).

Sync refuses a `guard` that is not exactly `protectedServices`, a list of names of 3 or more characters; at runtime a missing or invalid list keeps the defaults, warns on stderr and writes a `service-guard-config` row to route evidence, and never turns the guard off. The sync writes `service-guard.mjs` before `fleet-routing.mjs`, and `launch.mjs` refuses to start Pi when it is missing. Any sandbox profile used with `pi-isolated` must allow reading `PI_ROOT/service-guard.mjs`, or every sandboxed launch exits 1 because `fleet-routing.mjs` cannot import it. Each refusal writes a `service-guard` row with the tool, the reason and the first 120 characters of the command with `NAME=value`, `Bearer`/`Basic`/`Token` values, API key and cookie headers, `--token`/`--password`-style options and URL userinfo masked; the session's `codemode-check` row records `guardSha256`. Run as `node service-guard.mjs [--runtime <runtime.json>]`, it reads one JSON object on stdin (`{"command": ...}` or a Claude Code PreToolUse payload) and exits 2 with the reason on stderr to refuse, 0 to allow.

**Tool output masking.** `fleet-routing.mjs` masks secret-shaped text in every tool result before the model sees it and before Pi saves it in the session: each text part, and the strings in `details` and `structuredContent`, for every tool, nested Codemode calls included (so a script sees masked text too), and the live progress a running tool streams to Pi's client (Paseo). Live progress is masked only for complete tokens, so a token printed in two chunks can show as a raw prefix in the live view while the tool runs; the session and the final result are masked. A string of 20 or more characters under a `refresh_token` key in `details` or `structuredContent` is masked too. Each match of the security audit's patterns (Anthropic, OpenAI, GitHub, Slack, AWS, Google refresh, access and API keys, Tailscale, Hugging Face, Bitwarden access tokens, Telegram bot tokens, Cloudflare tunnel tokens, and a JSON `refresh_token` value, whose key stays) becomes `[REDACTED:<kind>]`, and route evidence gets one `redact` row per masked result with the tool and counts by kind, never a value. Only what Pi passes on changes: the tool's real effects stay as they were, so a file it wrote and output a command piped or redirected keep the real value. A `write` or `edit` whose new text contains such a mask is refused, so the model cannot write the mask over the real secret; it must leave the value as it is or change the file with a command that does not print it. If masking fails, the result passes unmasked and a `redact` row with `status: "failed"` records it. Known gaps: a secret of a shape outside these patterns and a token typed into the command itself, which stays in the assistant's tool call.

To store a token for a `command` source, run one step per host as the user the Paseo daemon runs as, with the value in an environment variable (`EXAMPLE_GATE_TOKEN` here, for example from your secret runner) so it never appears in process arguments or output. `printf` is a shell builtin, and `security -i` reads its command from stdin:

```sh
# macOS Keychain; argv: ["/usr/bin/security", "find-generic-password", "-s", "example-gate", "-a", "EXAMPLE_GATE_TOKEN", "-w"]
printf 'add-generic-password -U -s example-gate -a EXAMPLE_GATE_TOKEN -w %s\n' "$EXAMPLE_GATE_TOKEN" | /usr/bin/security -i
# Linux systemd-creds; argv: ["/usr/bin/systemd-creds", "decrypt", "--user", "--name=example-gate", "/home/me/.config/example-gate/token.cred", "-"]
(umask 077; mkdir -p ~/.config/example-gate && printf %s "$EXAMPLE_GATE_TOKEN" | systemd-creds encrypt --user --name=example-gate - ~/.config/example-gate/token.cred)
```

On Windows, use a Python helper script that keeps a DPAPI (current user) copy and prints it for a `print` argument; argv `["C:\\Users\\me\\AppData\\Local\\Programs\\Python\\Python312\\python.exe", "C:\\Users\\me\\.local\\share\\example-gate\\token-helper.py", "print"]`. Store the copy from a shell in the daemon's own logon session. Check a stored value by length only, for example `/usr/bin/security find-generic-password -s example-gate -a EXAMPLE_GATE_TOKEN -w | wc -c`.

### Install, apply and rollback

Install official Pi 1.0.0 first with the reviewed `scripts/pi/apply.sh` (POSIX) or `apply.ps1` (PowerShell), a generated per-host proposal and a fresh `--state` file. `plan`, `apply`, and `rollback` require a reachable stock daemon reporting a release version in `>=0.15.0 <0.16.0`; `--activate` reloads only that daemon. Enable daemon MCP and injection through the reviewed apply proposal. The installed package is kept for later reapply.

- **Apply** backs up the daemon config and records, per runtime file, its prior bytes and the hash of what it writes, before writing. A config change another controller makes meanwhile is merged into, and that revision is backed up and recorded instead.
- **Launcher command.** A Pi command already wrapped by the providers step's `mcp-env.cjs` (`<node> mcp-env.cjs -- <command>` or `<node> mcp-env.cjs --provider pi -- <command>`) keeps its wrapper, and the command after `--` stays byte for byte when it already runs this root's `launch.mjs` with node; otherwise apply writes the command the providers step builds, `node <root>/launch.mjs`, with the root expanded as that step expands it. So a reapply never drops per-launch token loading. An unwrapped Pi command is replaced whole. The launcher accepts a resume that passes `--session` without `--model`, because Paseo applies the model over RPC.
- **Rollback** verifies the backup and refuses unrelated config changes. It checks every runtime file first: each must still hold what apply found or wrote, as a regular file with no symlink or junction up to the runtime root, so an edit made since apply, even to a file rollback would delete, stops it. It restores runtime files atomically and verifies them, checks again that the config is still apply's or the original revision and the backup is intact, then restores it and reloads. A failed partial apply can be rolled back with the same state. A state without per-file hashes is refused; restore its runtime by hand after checking the files.
- Both stage the daemon config in an unpredictable, exclusively created temp file beside it, refuse a config that is a link, a reparse point, or not a regular file, and verify the installed config's digest. A runtime path with a symlink, or on Windows any reparse point, is refused before anything is written.

The provider sync needs the installed package. It generates runtime helpers and catalog together, backs up changed files (see [Backup retention](#backup-retention)), then merges provider rows. Each real agent gets a stable private `PI_CODING_AGENT_DIR` and an MCP endpoint carrying its caller ID. A scoped stdio bridge exposes the daemon tools through Codemode and fills omitted child provider/model/thinking from the current parent snapshot, keeping explicit overrides.

### Per-agent overlays

To change one Pi agent only, for example a context-window trial, write `models.overlay.json` or `settings.overlay.json` into `<pi root>/agents/<agent id>/`. Each launch or resume rebuilds that agent's `models.json` and `settings.json` from the shared `agent/` copies and applies the overlay on top. It applies at the next launch or `paseo agent reload <id>`, and deleting the overlay restores the shared values the same way. The syncs never write or remove files under `agents/`, and probes and launches without a caller ignore overlays. Only this allowlist is accepted:

- `models.overlay.json`: exactly `{"providers": {"<provider>": {"models": [{"id": "<model id>", "contextWindow": n, "maxTokens": n}]}}}`.
- `settings.overlay.json`: exactly `{"compaction": {"enabled": true|false, "reserveTokens": n, "keepRecentTokens": n, "modelOverrides": {"<provider>/<model id>": {"reserveTokens": n, "keepRecentTokens": n}}}, "skillsExclude": ["<skill name>"]}`.
- Every field other than `id` is optional, but each object, list and model entry needs at least one; `n` is a positive integer, each model `id` a non-empty string, each `modelOverrides` key `<provider>/<model id>`.
- A model entry or `modelOverrides` key naming a model not in the shared `models.json` (since retired, or whose provider left) is checked and then skipped with exactly one stderr line, `Pi launch: model override "<provider>/<model id>" not in models.json, using default`; every other entry still applies.
- Each `skillsExclude` entry is unique and only the name of a skill directory holding a `SKILL.md` (no paths, globs or `..`) directly under exactly one root Pi loads skills from: the shared `agent/skills`, the agent's own `agents/<agent id>/skills`, or `~/.agents/skills`, where Paseo installs its skills (`$HOME`, else the OS home, so `%USERPROFILE%\.agents\skills` on Windows). A name in two roots is refused; a name in none (a skill retired since) excludes nothing, with one stderr warning. Project `.pi/skills` and `.agents/skills` load only for a trusted project, which the fleet's `defaultProjectTrust: "never"` rules out in RPC mode, so they are not roots. The launcher appends Pi's exact exclusion `-<that root>/<name>` to `skills`, removing only that skill from the agent's skill list and `/skill:` commands, for example `{"skillsExclude": ["<skill name>", "paseo-advisor"]}` to keep skills out of a PM's index. The skills step reports any agent whose `skillsExclude` names a skill it retires and never edits the overlay (see `Local-edit protection` in `SKILL.md`).
- Any other key, a wrong JSON type or bad value, an unreadable file or invalid JSON refuses the launch and leaves the agent's files as they were. On every row the launcher opens an overlay without following links and without blocking: a symbolic link refuses, and anything not a regular file, a FIFO included, refuses at once.

Example, a 1M window: `{"providers": {"fleet": {"models": [{"id": "<model id>", "contextWindow": 1000000}]}}}` with `{"compaction": {"modelOverrides": {"fleet/<model id>": {"reserveTokens": 40960}}}}`.

### Picker defaults, OPC routes and Fast

`isDefault` selects a model within a provider; Paseo has no daemon-wide default provider. Web UI clients store their new-agent preference in `@paseo:create-agent-preferences`, client-local, so each client selects Pi in its picker; a headless host cannot set that through daemon config.

OPC resolves its fixed role labels and Worker classes from the target Pi catalog at spawn time; missing or ambiguous labels fail clearly, and a model or effort the catalog does not serve stops the lane. The class table, defaults and owner rules are defined in [OPC routing](../../opc/references/routing.md). Pi has no plan mode or permission-mode controls, and its tools execute with the host user's authority.

Fast on Pi is the agent label `opc.service-tier` on GPT routes, and Fast is off by default fleet-wide. With no label (or `inherit`), a GPT route whose router catalog lists the `priority` tier sends an explicit `service_tier: default` (Standard), and route evidence records `tierStatus: fleet-default-standard`; a route whose catalog lacks `priority` or cannot be read sends no tier (`inherited`). Only an explicit `fast`/`priority` or `ultrafast` label turns it on; the Fast toggle's On writes `fast` and Off writes `standard`. A tier label on a route without service tiers (an agent swapped from GPT to Claude) is ignored: no tier is sent and evidence records `ignored-untiered`. For a Fast route the router extension requests `service_tier: priority`; acceptance does not prove priority was granted. Private per-session evidence records the requested and reported tier, without headers or transcript contents.

### Isolated Pi provider

An optional `pi.isolated` object (top level or in a host's `pi`) adds a second Paseo provider for agents that must not reach live tools, such as an eval replaying an old task. It has three keys; any other key refuses:

- `providerId`: the new provider's id, default `pi-isolated`. It must match Paseo's `[a-z][a-z0-9-]*`, differ from `pi` and every Paseo built-in provider, and not be in the host's `providers` or `disabledProviders`.
- `sandboxProfile`: optional path to a macOS `sandbox-exec` profile, absolute or starting with `~/`, expanded on the host.
- `sandboxProfileRoot`: optional directory, absolute or starting with `~/`, expanded on the host, under which each agent names its own profile (see Per-agent profiles). A block with both refuses at sync.

Only `macos` hosts take `pi.isolated`: a `linux` or `windows` host refuses it at sync, the merge refuses it off macOS, and the launcher refuses an isolated launch off macOS (on Linux a per-agent `LD_PRELOAD` would run inside the dynamically linked `/usr/bin/env` before its scrub; Windows has no `/usr/bin/env`; the sandbox is macOS only).

The providers step writes `agents.providers.<providerId>` with `extends: "pi"`, the label "Pi isolated", `paseoTools: {"enabled": false}`, the same picker rows and `options` as the generated Pi row, and the command `/usr/bin/env -u <var> ... <this host's absolute node> <pi root>/launch.mjs --loadout-isolated`, plus `--loadout-sandbox-profile <expanded path>` or `--loadout-sandbox-root <expanded dir>`. Isolation lives in the command because a per-agent request (`paseo run --env`, `create_agent_request.env`, a plugin hook) can override a provider's env, kept on resume, but not its command; the absolute node path and the env scrub stop that env from choosing the `node` or files Node, OpenSSL or the dynamic loader read before any JavaScript runs. The scrub (`ISOLATED_SCRUBBED_ENV` in `scripts/paseo_providers.py`) clears every variable that loads code, modules, config or data files, or changes module resolution, as documented by:

- Node.js 24 and 26 `doc/api/cli.md`: `NODE_OPTIONS`, `NODE_PATH`, `NODE_REPL_EXTERNAL_MODULE`, `NODE_ICU_DATA`, `NODE_COMPILE_CACHE` and its `_PORTABLE` and `_READONLY` variants, `NODE_EXTRA_CA_CERTS`, `NODE_PRESERVE_SYMLINKS`, and ICU's `ICU_TIMEZONE_FILES_DIR`;
- OpenSSL 3.5 `openssl-env(7)` (Node reads `OPENSSL_CONF` at startup): `OPENSSL_CONF`, `OPENSSL_CONF_INCLUDE`, `OPENSSL_CONFIG`, `OPENSSL_ENGINES`, `OPENSSL_MODULES`, `CTLOG_FILE`, `RANDFILE`, `SSL_CERT_DIR`, `SSL_CERT_FILE`;
- glibc `ld.so(8)`: every `LD_*` variable it lists, plus `GCONV_PATH`, `GLIBC_TUNABLES`, `LOCPATH`, `NLSPATH` and `HOSTALIASES`;
- macOS `dyld(1)`: the library and framework path variables and `DYLD_INSERT_LIBRARIES` (`/usr/bin/env` also purges every `DYLD_*`);
- every `JITI_*` variable (Pi's extension loader) in Pi 1.0.0's packages, and Pi's `PI_PACKAGE_DIR` and `PI_CODING_AGENT_SESSION_DIR`.

An isolated launch refuses when any of these, or any other `LD_*`, `DYLD_*`, `OPENSSL_*` or `JITI_*` variable, is still set, which catches a row without the scrub; if the daemon's own environment sets one, every isolated launch refuses until it is removed. Output-only and behavior variables (`NODE_DEBUG`, `NODE_V8_COVERAGE`, `TZ` and the like) stay; the scrub covers the documented variables, not every way an env can change a process. The launcher ignores `LOADOUT_PI_ISOLATED` and `LOADOUT_PI_SANDBOX_PROFILE` in the env, and an isolated launch refuses when either is set, even empty, except `LOADOUT_PI_SANDBOX_PROFILE` on a row with `--loadout-sandbox-root`. The row is never wrapped in `mcp-env.cjs`, so neither MCP bearer env nor `launch.pi` settings reach it, and with Paseo's tools off Paseo injects no `paseo` MCP server or capability token. Without `pi.isolated` the payload and config are unchanged. Removing the key removes the row, and removing `sandboxProfile` or `sandboxProfileRoot` drops it from the command, on the next sync (the result line reports `removed [...]`). The main Pi provider is unchanged either way.

The launcher reads the `--loadout-*` markers only at the start of its arguments and strips them before Pi sees them; a marker anywhere else, a profile or profile root without `--loadout-isolated`, or both, refuses. An isolated launch needs a Paseo caller: without `PASEO_AGENT_ID` it has no agent home and refuses. The isolated row's `--mode rpc` probe (model catalog, and Paseo's MCP-support check) runs on the shared agent dir with `--no-approve --no-extensions` and every extension but built-in MCP loaded explicitly, so Paseo sees no MCP support and refuses MCP servers requested for an isolated agent. For an agent the launch:

- writes no `mcp.json` to the agent home and deletes one left by an earlier launch before Pi starts;
- copies the shared settings (with any settings overlay) with `-builtin:mcp` added to `extensions`, so nothing reads an `mcp.json`, extension-registered servers are never connected, and Codemode has no MCP namespace;
- puts `--no-approve` first, so a project's `.pi/settings.json`, `.pi/mcp.json` and `.pi/extensions` never load (the shared settings already default `defaultProjectTrust` to `never`);
- refuses, with one stderr line and nothing started, `--mcp-config` (what Paseo passes when it detects `pi-mcp-adapter`), `--approve`, `-e builtin:mcp`, and an `extensions` directory in the agent home;
- drops `LOADOUT_PI_MCP_URL`, so the routing extension reads no agent labels and Fast labels are ignored.

With a profile, every launch, probe included, runs as `/usr/bin/sandbox-exec -f <profile> -D CWD=<cwd> -D PI_HOME=<agent home, or the shared agent dir for the probe> -D PI_ROOT=<Pi root> <node> <Pi cli> ...`. Off macOS, without an executable `/usr/bin/sandbox-exec`, or when the profile is not a readable regular file, the launch refuses with one stderr line; it never runs Pi unsandboxed. Signals and the exit code pass through.

#### Per-agent profiles

With `sandboxProfileRoot`, each agent brings its own profile, for example one an eval runner writes per unit. Only on a row whose command carries `--loadout-sandbox-root` does the launcher read the per-agent env var `LOADOUT_PI_SANDBOX_PROFILE` (set with `paseo run --env` or `create_agent_request.env`; Paseo reapplies it on every resume). It checks the value at every launch, after the env scrub, and accepts it only when:

- the root is an absolute path to an existing directory;
- the value is an absolute path without `.` or `..` parts that equals its real path as stored on disk, so no symbolic link at any level and no other letter case or Unicode form (macOS volumes are case-insensitive by default);
- it names a readable regular file under the root's real path;
- that file is outside the agent's working directory and outside the Pi root, which holds every agent home.

The launcher checks only the launching agent's own working directory, so lay out the root so that no sandboxed agent can write the root or any directory between it and a profile (for example, keep each unit's profile beside its `work/` folder, not inside any agent's).

A missing, empty or failing value refuses the launch with one stderr line, resumes and reloads included. Only the checked path reaches `sandbox-exec -f`, and the variable is removed from Pi's env. Paseo's catalog probe carries no per-agent env, so a `--mode rpc` probe without the variable runs under a built-in profile (`PROBE_PROFILE`, as `sandbox-exec -p`): no network, no AppleEvents and no keychain service; writes only under the shared agent dir it reads; and no reads under the account's home (from the user database, not the env), the temp folders or `/Volumes`, except the cwd itself, the Node install, `PI_ROOT/app`, `fleet-routing.mjs`, `service-guard.mjs` and the shared agent dir without its `mcp.json`. A probe that does carry the variable uses that profile. Because the built-in profile grants reads of the Node install prefix (the folder above `bin/node`), such a probe refuses when that prefix is or contains the home folder, the Pi root, `~/.config`, `~/.ssh` or `~/.codex`, as with a node at `~/bin/node` or `~/.local/bin/node`; install Node in its own folder instead.

#### What a sandboxed launch does for Pi

A useful profile denies Pi the credential files, its own `!command` credential helper and the system temp folders, so for every isolated launch with a profile (fixed or per-agent) the launcher also:

- reads the router key before `sandbox-exec` by running the router's `credential.py` command itself: the argv `fleet-routing.mjs` derives from the router provider's `apiKey`, with its timeout and retries and no shell. The helper runs outside the sandbox without the per-agent env: `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, `HOME` from the user database, and, for an `env` credential source only, that one named variable (no `DEVELOPER_DIR`, `PYTHON*` or per-agent `HOME`). Python runs isolated (`-I`: no user site, no `PYTHON*` variables, no cwd on `sys.path`). The runtime's `python` must be an absolute path; a bare name refuses. Prefer a real interpreter over `/usr/bin/python3`, the macOS `xcrun` shim. A failed read refuses the launch. Pi gets the value only in its env, as `LOADOUT_PI_ROUTER_KEY`, and the agent home's `models.json` sets the router provider's `apiKey` and credential headers to `$LOADOUT_PI_ROUTER_KEY`, so it is never on disk or argv; a rotated key applies from the next launch. The agent's own tools (`bash`) can read it too; the profile's network rule (the model route only) limits its use. `directProviders` keys keep their `!command`, which fails inside such a profile;
- sets `TMPDIR`, `TMP` and `TEMP` to `<PI_HOME>/tmp`, created owner-only (0700) through a descriptor opened without following links; an existing `tmp` that is not a plain directory refuses;
- reads the agent's `models.overlay.json` and `settings.overlay.json` as on every row, and a parse error reports only the path and "invalid JSON", never the file's text;
- refuses, before Pi starts, an extension in the settings it loads (the agent's, or the shared ones for the probe) that is not a built-in and does not resolve to `PI_ROOT/fleet-routing.mjs` or under `PI_ROOT/app`, and refuses any Pi `packages`;
- copies Paseo's per-session integration extension into the agent home and passes the copy instead. Paseo writes it to `<its temp folder>/paseo-pi-extension-*/paseo-integration.mjs` and passes it with `--extension`, which a profile denying the temp folders cannot read. The launcher accepts it only when the folder, as given, is a real `paseo-pi-extension-*` folder (no symbolic link) directly under the macOS per-user temp folder (`getconf DARWIN_USER_TEMP_DIR`, which ignores the env; a launchd-started daemon gets it as its `TMPDIR`), and the file is a regular file owned by the user with a single link, read without following a link; after the open, the folder must still be a real directory and the name must still be the opened file. A directory where the copy goes refuses. It writes the bytes fresh to `<PI_HOME>/paseo-integration.mjs` (0600) on every launch. A symbolic link, a non-regular file, or any other `--extension` or `-e` value that is not a built-in and does not resolve to `PI_ROOT/fleet-routing.mjs` or under `PI_ROOT/app` refuses. A daemon started with another `TMPDIR` has its extension refused; start it from launchd or with that folder.

Sandboxed agents compact with Pi's default compaction, not the fleet compaction: their `models.json` names the key variable instead of the credential command, so the extension does not treat their router provider as the fleet route.

A profile should allow only what Pi needs:

- reading and executing the Node binary and its libraries;
- reading, under `PI_ROOT`, only `app/` (the Pi package), `agent/skills`, `fleet-routing.mjs` and the `service-guard.mjs` it imports, not the rest of `PI_ROOT`, which holds every other agent's home and the shared `agent/mcp.json`;
- reading and writing `PI_HOME` (sessions, settings, route evidence, `tmp`) and `CWD`;
- nothing in the system temp folders (Pi's own temp files go to `PI_HOME/tmp`), and never writes there: Pi keeps Node's compile cache in the temp directory, shared with the unsandboxed main Pi rows;
- network to the model route's port only; deny the daemon's listen port.

The repository ships no profile; test one by hand before using it.

What isolation does not cover: Pi's built-in `read`, `write`, `edit` and `bash` tools stay, with the user's file access outside any profile, and the network stays open unless the profile denies it. Without a profile, `bash` can reach any service the host can, including the Paseo daemon's loopback port (open without auth when the daemon has no password, so an agent could start a non-isolated agent with the `paseo` CLI), and can run the MCP reader command or read its env files. Use the profile to close what an agent must not reach.

### Provider catalog without a runtime install

A providers-only host can set its host `pi` descriptor to `{"catalogOnly": true}`. This derives Pi's models from the same catalog sources but emits only the `models` field, keeps the local command, availability and environment, and writes no Pi agent home or binary. It does not activate Pi on a host where it is unavailable.

## client-config.json

Optional. `python3 scripts/client_config.py [--dry-run] [--host <name>] [--update-claude]` reads it and updates hosts whose `sync` includes `client-config`. Each host gets the base settings, then its role's, then its own `hosts.<name>` overrides. It holds router URLs, so it stays in the private fleet directory.

- `token_file`: optional path, on the source host, to a secret file. Its contents go to hosts whose settings name a `claude.token_env`, over SSH stdin only. A token file inside the fleet directory stays there: the fleet push never copies it, and refuses to run while `token_file` resolves to a file it publishes. The token is never passed as an argument, stored in this file, or printed.
- `codex`: managed keys for Codex `config.toml`.
  - `top`: top-level keys. Missing keys are inserted before the blank lines that precede the first section header.
  - `sections`: named sections such as `model_providers.<id>`, each a map of keys. A missing section is appended.
  - `reportOnly`: top-level keys that are printed per host and never written.
  - `removeTop`: top-level keys an earlier sync managed and this one drops, such as `["model_provider"]`. Each is deleted, with its whole value, where it is set before the first table header. List only keys the sync once wrote: a listed key is removed whoever set it, and keys not listed are never touched.
  - Key, section, and `reportOnly` names are bare TOML keys, optionally dotted (letters, digits, `_`, `-`); a host refuses any other name and writes nothing.
  - Values are strings, numbers, or booleans. The merge is line-based and keeps CRLF, comments, and every other key and section. It reads headers with trailing comments, array tables, quoted keys, and values that span lines, and replaces a managed key's whole value. Where a construct could define, shadow, or duplicate a managed key path (a top-level key, or a managed section plus one of its keys), it refuses with nothing written and reports `unsupported TOML, edit by hand`: an inline table, a dotted key, or a multi-line value at, inside, or over a managed key path; a table header at or under a managed key path, such as `[model_providers.example.base_url]`; an array table at or over a managed section; and a key outside a managed section that defines part of it. Other keys and deeper tables in a managed section are left alone, such as `[model_providers.example.http_headers]` under a managed `[model_providers.example]`. It also refuses an unreadable file, and a result in which a managed key would appear more than once or outside its own table, or a table or key would be defined twice.
- `claude`: managed parts of Claude Code `~/.claude/settings.json`.
  - `settings`: top-level keys, each replaced whole.
  - `env`: keys merged into `env`.
  - `token_env`: an `env` name to fill from `token_file`, or `null`. This puts the token in the global `settings.json`, which every terminal session also reads; to route only Paseo-launched Claude, leave it unset and use `launch.claude.tokenFiles` in `paseo-providers.json`.
  - `removeEnv`: `env` names an earlier sync managed and this one drops, such as `["ANTHROPIC_BASE_URL", "ANTHROPIC_AUTH_TOKEN"]`, with the same rule as `removeTop`.
  - Removal waits for the providers step: on a host with the `providers` scope a listed key goes only once the providers step has written that host's current `paseo-providers.json` settings and reloaded its daemon, with no reload owed or in flight since (a failed reload never counts). That is recorded on the source host in `provider-activations.json` beside `provider-reloads.json`. Until then the keys stay, the host reports `routing removal HELD` with the reason, its cell reads `held`, and the run exits 1; run the providers step for the host, then client-config again. This applies to every run, including `--only client-config`. A host without the `providers` scope removes them at once.
  - Removal lists from the base, role and host layers add up. A name the same host also manages (`codex.top`, `claude.env` or `token_env`) is refused.
  - `minVersion`: base only. Hosts below it are reported, and `--update-claude` runs `claude update` on them. Versions compare like `sort -V`.
- `roles.local`, `roles.remote`: layers with `codex` (`top`, `sections`, `removeTop`) and `claude` (`settings`, `env`, `token_env`, `removeEnv`). The source host is `local` and every other host `remote`.
- `hosts.<name>`: the same layer for one host, plus an optional `role` that overrides the default.

Only these keys are written; everything else stays host-local, and a missing client is skipped. Each changed file is backed up in place as `<file>.bak-loadout-<stamp>-<random>`, a new file holding exactly the bytes the merge read (see [Backup retention](#backup-retention)). The write is an optimistic check: the result goes to an exclusive, fsynced temp file, then the file is read again and the temp renamed over it only if it still holds the bytes the merge read. Otherwise the temp and backup are removed and the merge runs once more on the new revision; a second change fails the host and leaves the file as is. The daemon and editors take no lock, so this narrows the window for a lost concurrent edit but cannot close it. A second run reports `unchanged`.

### Fleet MCP servers

`client-config.json` accepts `mcpServers`, an object keyed by server name. Declare each Streamable HTTP endpoint once, for example (all addresses and host names here are made up):

```json
{
  "mcpServers": {
    "ebay-analyze": {
      "url": "http://192.0.2.40:8766/mcp",
      "bearerTokenEnvVar": "EBAY_ANALYZE_MCP_TOKEN",
      "envFile": "~/.config/ebay-analyze-mcp/mcp.env",
      "description": "Search marketplace listings and sold prices.",
      "hosts": { "laptop": true, "desktop": true }
    },
    "gmail": {
      "url": "http://192.0.2.10:8770/mcp",
      "bearerTokenEnvVar": "GMAIL_MCP_TOKEN",
      "hosts": { "laptop": { "url": "http://127.0.0.1:8770/mcp" }, "desktop": true }
    }
  }
}
```

- `url`: HTTP or HTTPS Streamable HTTP endpoint, without embedded credentials, query or fragment. Prefer HTTPS; use HTTP only on a trusted private network. If the server allowlists `Host`, use its allowed IP, not a DNS alias.
- `bearerTokenEnvVar`: uppercase environment variable name, never a token value.
- `envFile`: optional path, absolute or starting with `~/`; default `~/.config/<server>/mcp.env` (`%USERPROFILE%\.config\<server>\mcp.env` on Windows, where a server listing a Windows host needs the `~/` form). The file is delivered separately and holds one literal `VAR=value` line (blank and `#` lines aside), with no shell expansion, quoting or `export` prefix. It must pass the owner-only check of a `launch` token file (see `tokenFiles`); `scripts/new_token_file.ps1 -EnvName VAR` creates one on Windows. The sync never copies, sources, prints or puts its contents into client or daemon config. The launcher reads it afresh each time, so a rotation needs no daemon restart, and fails closed on a missing, linked, unsafe or empty file.
- `description`: optional one-line summary, at most 2000 characters, without control characters. It goes only into Pi's entries, the generated runtime and the official Pi home `agent/mcp.json`. Pi lists each Codemode server in its system prompt with one line, from `description` or, without it, from the server's instructions once it connects; a pinned `description` keeps that line stable from the first turn, so the prompt cache survives. Copy the server's own first instruction line to keep the line identical. Codex, Claude Code and `mcp-env.json` never get it.
- `hosts`: explicit `hosts.json` names mapped to `true`, `false` or `{"url": "<http(s) url>"}`. The object form enables the server on that host with its own URL, validated the same way; use it on the host that runs the server itself, over loopback. Missing hosts are untouched. All named hosts need both `client-config` and `providers`, Windows hosts included, since the providers step installs the launcher that reads each token; validation names a host that lacks `providers`, and the sync never widens a host's scopes. `false` disables the Codex and Pi entry, removes only that named Claude user entry, and stops loading that server's env file. Set `false` before retiring a previously enabled host; deleting the declaration alone does not retire its prior config.
- Names allow letters, digits, `_` and `-`, must be unique case-insensitively with `-`/`_` treated alike, and cannot be `paseo`. `gmail` is allowed only while no host listed under it, even as `false`, still has the read-only Pi `gmail` block in its effective `paseo-providers.json` `pi.runtime`; validation names any such host. To move a host to the shared server, remove its Pi block and list the host here in the same change; the next providers sync regenerates Pi `agent/mcp.json` without the old local server. Do not also manage the same Codex table through `codex.sections` or the same Pi server through `pi.runtime`.

`example/mcp-servers-overlay.json` shows the `mcpServers` block for a shared `gmail` server: the source host `laptop` runs it on the loopback URL, `desktop` uses the top-level URL, and neither keeps a Pi `gmail` block.

The providers step writes the non-secret `loadout/mcp-env.cjs` launcher and the `mcp-env.json` descriptor (`{"servers": [...], "providers": {...}}`, the latter holding the `launch` settings, plus `unnamed` during a rollout, see below) under the host config directory, after checking that each enabled server's env file is present and owner-only (without reading it); a real sync fails the host otherwise, before writing anything. It wraps the enabled Codex, Claude Code and Pi provider commands without changing their arguments, models, other environment keys or agent routes, with the usual reload and reload-owed handling.

**Bearers.** No MCP bearer is in any harness environment except Codex's. Codex reads an HTTP bearer only from its environment (`bearer_token_env_var`; its other options are `env_http_headers` and a static `http_headers`), so on a host with an enabled server the descriptor gets `mcpTokens: true` for the `codex` provider only, and Codex is wrapped as `node mcp-env.cjs --provider codex -- <command>`; the launcher reads every enabled server's env file at launch and sets its `bearerTokenEnvVar`, refusing the launch on a missing or unsafe file. For every other harness it sets none and removes any inherited variable named by a server, in any spelling on Windows. Claude Code and Pi read each bearer when they connect by running the launcher's reader, `node mcp-env.cjs --mcp-header claude|pi <server>`: it finds that enabled server in `mcp-env.json`, reads its env file with the same check, and prints exactly the header, `Bearer <value>` for Pi or `{"Authorization":"Bearer <value>"}` for Claude Code. The value must be printable ASCII without spaces, and only the server name is on its command line. A missing, unsafe or unreadable file, or an unknown or disabled server, prints nothing and exits 1, so no Authorization header is sent; it never falls back to an environment variable. A rotation reaches the next connection.

**Rollout bridge.** Claude Code's `~/.claude.json` (under `CLAUDE_CONFIG_DIR` when set) and Pi's runtime `agent/mcp.json` count as not moved while either still sends `Bearer ${VAR}` for an enabled server (for Pi whether or not this run writes its runtime). For such a client the step keeps the bearers in its environment, for both the command the daemon runs now and the one this run publishes: `mcpTokens: true` for a `--provider <id>` launch, and a top-level `unnamed: {"mcpTokens": true}` in `mcp-env.json` for a launch without `--provider`, such as the Pi row. It is written with the launcher, before the Pi runtime step and the config publish, so a failure there, or between this step and client-config, or a daemon not yet reloaded, leaves no client without a source. The report says `until ... uses the reader`. The first providers run after the file has moved drops the bridge, so a full sync is providers, client-config, then providers once more. A client with no provider row of its own is not wrapped for the bridge.

**Residual exposure.** The Codex process, and programs it starts outside tool shells (its `notify` program, hooks, its own git), keep the tokens in their environment, which another process of the same user can read (for example `ps eww` on macOS or `/proc/<pid>/environ` on Linux). Only a static `http_headers` entry in `config.toml` would avoid that, but it would copy the value into the config and every `config.toml.bak-loadout-*` backup, so it is not used. Codex's tool shells do not inherit them (see `shell_environment_policy` below). On Windows, until the values are deleted from `HKCU\Environment`, every process of the session still inherits them from there, the daemon included; the launcher only keeps them from Claude Code and Pi agents. On every OS a Codex launch fails while any enabled server's env file is missing or fails the owner-only check, so after each rotation check that `sync.py --dry-run --only providers --host <host>` shows every file `present, owner-only`.

The client-config step merges:

- Codex `config.toml`: `[mcp_servers.<name>]` with `url`, `bearer_token_env_var` and `enabled`, and `[shell_environment_policy]` `exclude`, listing every server's `bearerTokenEnvVar` on that host, so Codex tool shells drop them. Other keys of that table, and subtables such as `[shell_environment_policy.set]`, stay host-local. A host-local `exclude` written on one line as plain strings is kept, with the server variables added after its entries; any other form is refused. Declaring `shell_environment_policy.exclude` in `codex.sections` is refused.
- Claude Code user-scope `~/.claude.json` (`$CLAUDE_CONFIG_DIR/.claude.json` with a custom config directory): `mcpServers.<name>` with `type: "http"`, `url`, and `headersHelper`, the reader command `"<node>" "<config dir>/loadout/mcp-env.cjs" --mcp-header claude <name>`. User-scope servers need no workspace trust for `headersHelper`. `managed-mcp.json` would impose exclusive system-managed servers and displace users' own servers, so the sync does not use it. Other user servers and unrelated user state are preserved.
- The configured official Pi home's `agent/mcp.json`, discovered from the daemon's Pi launch command: `description` when declared, `url`, `headers.Authorization` set to the same reader command with `pi` and a leading `!` (Pi runs it at each connection), `enabled` and `exposure: "codemode"`. The providers step writes the same native HTTP entries into the Pi runtime it generates, and gives the built-in `paseo` entry a fixed generic `description` so its prompt line is stable too; the scoped loopback Paseo stdio bridge and read-only Gmail server are not repurposed as HTTP proxies. A missing client is reported as absent.

The reader command names this host's Node (the one the sync ran) and launcher by absolute path, each in double quotes. It runs in the harness's shell: `/bin/sh` on POSIX; on Windows Git Bash (or `cmd.exe` without it) for Pi and `cmd.exe` for Claude Code. All of them read a double-quoted word alike only while it holds no `"`, `` ` ``, `$`, `%`, `!` or control character, nor on POSIX a backslash, so a path with one is refused and the host fails. Because the reader lives in the launcher, client-config refuses a host, writing nothing, until the providers step has installed the launcher this sync publishes (checked by SHA256); a dry run reports `MCP launcher waits for the providers step` and previews the rest.

Client files hold variable names and the reader command only. The provider dry run reports each URL, credential variable, env-file presence and owner-only check (without reading it), and any wrapper files it would write; it never connects to an MCP endpoint or runs a search. For a complete proposal, run `python3 scripts/sync.py --dry-run --only providers,client-config` against the private fleet, inspect every host, then wait for rollout approval. Pi loads new entries when a new session starts or after `/reload`.

Claude Code and Pi started by hand outside Paseo read the same user config, so they authenticate through the reader with no wrapper. A standalone Codex needs the loader with its provider id, for example `node "${XDG_CONFIG_HOME:-$HOME/.config}/loadout/mcp-env.cjs" --provider codex -- codex`, or on Windows `node "%APPDATA%\loadout\mcp-env.cjs" --provider codex -- codex`; a raw `codex` has no token unless it inherits `VAR`. The sync does not edit shell startup files, global launch services or credential stores. Connection smoke checks should call `tools/list` only, never a marketplace search.

## Backup retention

Each sync writer that backs a file up beside itself keeps only that file's newest 5 backups of its own naming pattern, counting the one it just wrote, and deletes older ones after the write succeeds. Age is the stamp in the name, not the file time. The patterns are:

- client-config step (`client_config_merge.js`), each changed client file: `<file>.bak-loadout-<YYYYMMDD-HHMMSS>-<8 hex>`.
- providers step (`paseo_providers_merge.js`): `config.json.bak-loadout-<YYYYMMDD-HHMMSS>-<8 hex>`, and for the MCP env files `<file>.bak-loadout-<YYYYMMDD-HHMMSS>-<16 hex>`.
- Pi runtime files (`pi/configure.py`, run by the providers step and by `pi/deploy.py` apply): `<file>.bak-<YYYYMMDDTHHMMSSffffffZ>` (UTC, microseconds).
- skills step, managed-settings `claudeMd` (`skills_sync_remote.js`): `<file>.bak-<YYYYMMDDTHHMMSSZ>` (UTC), removed through `sudo -n` when the write needed it.

Only a sibling of the same file whose whole name matches, with a real date, and that is a regular file counts; a symlink is never followed or removed. Hand-made backups (`.before-*`, `.bak-pr*`, any other suffix) and backups in an older format (such as `.bak-loadout-<stamp>` with no random part) are never touched; delete those by hand. A dry run prunes nothing. A failed prune never fails the write: the host reports a `backup prune failed, kept: ...` line and the files stay. `pi/deploy.py` apply's own daemon config backups (`.before-pi-*`) are rollback state and are not pruned; its rollback restores from the state record, not from `.bak-*` files.
