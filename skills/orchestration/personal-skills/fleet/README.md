# Fleet format

A fleet describes the hosts that `personal-skills` syncs. Sync it with `python3 scripts/sync.py --dry-run`, then `python3 scripts/sync.py`; the per-file tools named below are the steps it runs. The public `example/` folder shows the format with made-up values. Your real fleet lives in a private fleet directory with the same layout, outside this repository.

```
example/                     public, made up
  hosts.json
  paseo-providers.json       optional
  client-config.json         optional
  global/AGENTS.md           optional
  bin/common/hello-fleet    optional helper example
<fleet directory>/           yours, private (copy example/ here and edit)
  hosts.json
  paseo-providers.json       optional
  client-config.json         optional
  global/AGENTS.md           optional
  skills/<name>/SKILL.md     optional private skills (the overlay)
  bin/common/               optional helpers for every host
  bin/macos/                optional macOS helpers
  bin/linux/                optional Linux helpers
  bin/windows/              optional Windows helpers
```

## Where the fleet lives

`python3 scripts/fleet.py resolve` prints the directory in use. The first match wins:

1. `$LOADOUT_FLEET`, a directory. If it is set but missing, resolution fails instead of falling back.
2. `${XDG_CONFIG_HOME:-~/.config}/loadout/fleet/`. On Windows, `%APPDATA%\loadout\fleet\`.

Edit the fleet only on the source host. `python3 scripts/fleet.py push [--dry-run] [--host <name>]` copies its published files, `hosts.json`, `paseo-providers.json`, `client-config.json`, `global/AGENTS.md`, and `bin/`, to `~/.config/loadout/fleet/` (`%APPDATA%\loadout\fleet\` on Windows) on every other `ssh` host, and every sync run does this first. Every other file in the fleet directory, such as a token file, a pairing offer, a backup, or notes, stays on the source host; a file an earlier push copied and the push no longer publishes is removed from a host whose copy is unedited. Each copy carries a `.loadout-sync.json` record of the hashes last synced. A host's copy is replaced only while it still matches that record. Before it writes, a push also records there the versions of the published files it is about to write, so a push cut off part way recognizes its own writes. A hand-edited, added, or unrecorded differing file is a conflict, and nothing is written on that host until you resolve it, usually by deleting the host's copy. Each published file and the record are written through a uniquely named, exclusively created temp file, and the record is read back. Each write and removal checks its file and the directories from the home directory down again right before it, and a removal first moves the file aside and verifies it, so a linked `~/.config` or a file edited during the push stops the host and keeps the edit. Hosts need `node`.

With none of these, `fleet.py resolve` reports `fleet: none (current host only)`, and `sync.py` and every step stop with nothing synced until you create a fleet. To sync only this host, create one whose `hosts.json` lists just this host as `source_host`.

The optional private `bin/` holds portable plain files only. The skills step installs `common/` plus the host's `os` folder flat into `~/.local/bin` (`%USERPROFILE%\.local\bin` on Windows), with verified bytes and local-edit protection recorded in `loadout/global-sync.json`; identical existing files are adopted (an identical destination symlink is atomically replaced by a regular file without changing its target), differing unrecorded files are conflicts, and only recorded, unedited files retire on a full run. On macOS/Linux, extensionless files and `.sh` files are `0755`, others `0644`. Duplicate common/OS names, links, nested directories and nonportable names stop the run. Fleet push carries these helpers just like global instructions; real helpers stay in the private fleet, never in this public repository.

## Private skills

Put skills that must stay private (personal, account-bound, or holding credentials) in `skills/<name>/` inside the fleet directory on the source host, laid out like any installed package with a `SKILL.md`. The skills step installs them with the published ones, with the same `--skills` and `exclude_skills` selection and the same local-edit protection:

- A name that is also a published skill stops the run; rename one of them.
- Every overlay file hash a host has accepted is recorded in `skills/.loadout-overlay.json`, so a newer version replaces an older installed one while a hand edit on a host stays a conflict. A skill that moved here from the public repository also replaces its last published copy.
- A skill removed from the overlay is retired from hosts like an unpublished package (see `Local-edit protection` in `SKILL.md`), so keep the overlay complete on the source host and check `--dry-run` first. Set `skills_overlay: true` in `hosts.json` when the fleet keeps an overlay: then a missing `skills/`, or one that is not a directory, stops all retirement on every host, each reported as `blocked`. To retire every overlay skill, leave an empty `skills/` directory.
- Hosts install overlay files owner-only: on macOS and Linux as `0600` files in `0700` directories the sync creates, and a replaced file keeps stricter permissions it already had; overlay files and directories an earlier sync installed lose group and other access. On Windows they inherit the user profile's ACL (the user, SYSTEM and Administrators by default).
- `__pycache__`, `.pyc`, and `.DS_Store` are skipped; symlinks are errors.
- The fleet push does not copy `skills/` to other hosts; skill bytes travel only through the skills step.

## hosts.json

`python3 scripts/fleet.py validate` checks the file and prints each host's transport and sync scopes. Unknown keys and values are errors.

- `schema_version`: `2`. A file without it is version 1: `transport` is free text, every host is reached over SSH, and hosts have no `transport` or `sync` of their own.
- `source_host`: name of the host whose checkout is the sync source. It runs locally, so it must use `ssh`.
- `transport`: default for every host; `ssh`, the only value. Record host names, not IP addresses that may change.
- `notes`: optional free text.
- `skills_overlay`: optional, `true` or `false` (default). `true` says this fleet keeps private skills in `skills/`, so the skills step stops all retirement while that directory is missing or not a directory.
- `hosts[]`: one entry per host.
  - `name`: address used by the transport; for `ssh`, the SSH alias. Letters, digits, `.`, `_` and `-`, not starting with `-`.
  - `os`: `macos`, `windows`, or `linux`.
  - `transport`: optional, overrides the top-level value.
    - `ssh`: files and commands travel over SSH.
  - `paseo_offer`: path to a file holding the host's Paseo pairing offer. Optional; when set, the providers step reloads that host's daemon through the offer instead of over SSH. A relative path resolves inside the fleet directory. Keep offers private: the fleet push never copies an offer to other hosts, and refuses to run while an offer resolves to one of the files it publishes.
  - `paseo_home`: optional Paseo home for this host's daemon, a path that is absolute on that host or starts with `~`, which the host expands. The plugins and providers steps use it for that host only: plugin config reads, settings backups, installs, reloads and `plugin ls` confirmations, and the provider config merge and reload. The skills step still finds a Pi runtime from the default `~/.paseo/config.json`. A `PASEO_HOME`, `PASEO_HOST`, `PASEO_AGENT_ID` or `PASEO_AGENT_CWD` the sync inherits (from an agent session, a scratch daemon, or a host's shell profile) is always cleared first, so without `paseo_home` the default `~/.paseo` and the daemon it names are used. A host with `paseo_offer` reloads through its offer whatever this says.
  - `sync`: optional list of scopes from `skills`, `plugins`, `providers`, `client-config`. Default: `skills`, plus `plugins` when `paseo` is present. Each sync skips a host outside its scope and reports it as skipped, not failed. `providers` (Paseo provider pickers) and `client-config` (managed Codex and Claude Code settings) are opt-in.
  - `exclude_skills`: optional skill names the skills sync leaves alone on this host, such as a package you keep a private version of.
  - `checkout`: path to a local Git checkout of this repository, or `null` (the default). A host without a checkout receives verified bytes from the source host and reverifies them.
  - `clients`: clients to sync, from `codex`, `claude`, `opencode`. Required when `sync` includes `skills`. Absent clients are skipped and reported.
  - `paseo`: optional. Paseo plugin sync for this host's daemon. Required when `sync` includes `plugins`.
    - `plugin_root`: directory where verified plugin sources are staged, one subdirectory per plugin ID. Changing it for a host with installed plugins needs the manual move in the `Paseo plugins` section of `SKILL.md`.
    - `stage`: plugin IDs whose verified source is copied to `plugin_root`, installed with `npm ci`, and checked.
    - `install`: plugin IDs, a subset of `stage`, authorized for `paseo plugin install` on this daemon. List a plugin here only after its host-local settings and arming have been decided.
- `global`: optional. Maps each client to where `global/AGENTS.md` is installed. A target is a path starting with `~`, `/`, `$VAR` or `${VAR}`, `%VAR%`, or a drive such as `C:\`, and must be absolute once the host expands it. `fleet.py validate` rejects anything else, and a host refuses a target that is not absolute or names a variable it does not set, so text is never written as a file.
  - `codex`: normally `$CODEX_HOME/AGENTS.md`.
  - `claude`: normally `~/.claude/CLAUDE.md`. For a managed deployment, `managed-settings:claudeMd` installs the instructions as the `claudeMd` string field of Claude Code's `managed-settings.json`: `/Library/Application Support/ClaudeCode/` on macOS, `/etc/claude-code/` on Linux, and `%ProgramFiles%\ClaudeCode\` on Windows (`C:\ProgramData\ClaudeCode\` only when that file exists and the Program Files one does not). Only `claudeMd` changes: the file is first backed up beside itself as `<file>.bak-<UTC stamp>` (newest 5 kept, see [Backup retention](#backup-retention)), then replaced atomically and checked. When the user cannot replace it, macOS and Linux use `sudo -n` and keep its owner and mode; if that needs a password, nothing is written. On Windows run the sync from an administrator shell. `--dry-run` reports whether elevation is needed. `LOADOUT_CLAUDE_MANAGED_SETTINGS` on the host overrides the file path, for tests.
  - `opencode`: normally `~/.config/opencode/AGENTS.md`.

Omit `global` or `global/AGENTS.md` to skip global instructions. Global instructions follow the same preflight: never overwrite a changed target that matches no known prior version. For `managed-settings:claudeMd` the preflight compares the field's value, a missing file or field is added, and unparseable JSON or a non-object is a conflict.

Plugin settings, plugin state, and the daemon's `pluginsEnabled` switch are host-local. The sync never writes them. See the `Paseo plugins` section of `SKILL.md`.

## paseo-providers.json

Optional. The Paseo provider-picker sync (`python3 scripts/paseo_providers.py`) reads it and updates hosts whose `sync` includes `providers`. It holds router URLs and host settings, so it stays in the private fleet directory.

- `providers`: pinned blocks keyed by Paseo provider, such as `claude` or `codex`. Each block's fields replace the same fields in the host's `agents.providers.<provider>`; other fields there are kept. `models[]` rows need a unique `id` and a `label` that is a name only: no digits and not the model ID.
- `env`: optional default environment per provider, merged into `agents.providers.<provider>.env` on every host. A value's `%VAR%` is expanded from the host environment and written in plain text to `config.json` and its backups, so `%VAR%` must never name a secret; names containing KEY, TOKEN, SECRET, PASSWORD, CREDENTIAL or AUTH are refused with nothing written.
- `launch`: optional launch settings for the `claude`, `codex` and `pi` providers, so routing reaches only Paseo-launched agents while a terminal `claude` or `codex` keeps the user's own login. The providers step wraps each provider that has settings in the `loadout/mcp-env.cjs` launcher as `node mcp-env.cjs --provider <id> -- <command>` and records the settings in `loadout/mcp-env.json`; both are non-secret. The directory is `${XDG_CONFIG_HOME:-~/.config}/loadout` on POSIX and `%APPDATA%\loadout` on Windows. A provider with no `command` set, Paseo's default, is wrapped as its bare name, and a `claude` or `codex` with settings but no row in the host config gets a row holding just that wrapped command; `pi` settings need a `pi` row. On Windows the launcher resolves that name as Paseo does: each `PATH` directory in order (surrounding quotes removed) with the `PATHEXT` extensions, then winget package executables. It runs a `.exe` such as `claude.exe` directly. For an npm `.cmd` shim such as `codex.cmd` it runs what the shim runs, without `cmd.exe`: the shim's Node script under the shim's `node.exe`, or this Node when it has none, or the shim's `.exe`. So stdio and `app-server` work unchanged and no argument is expanded. Any other `.cmd` or `.bat` runs through `cmd.exe`, refused when an argument holds `%`, `!`, `^`, `&`, `|`, `<`, `>`, `(`, `)` or a control character. Example: `example/routed-launch-overlay.json`.
  - `tokenFiles`: env name to a file on the host, absolute or starting with `~/` or `~\` (the user's home, `%USERPROFILE%` on Windows), such as `{"ANTHROPIC_AUTH_TOKEN": "~/.config/example-router/api-key"}`. The file holds the bare value on one line and is delivered separately. On POSIX it is owned by the harness user with mode `0600`. On Windows its ACL must have inheritance off, an owner that is the current user, SYSTEM or Administrators, allow rules only for those or OWNER RIGHTS, and an allow rule for the current user, compared by SID. The launcher checks that ACL on the handle it reads the value through, opened so the file cannot be replaced, renamed or written meanwhile, and refuses a link, junction or other reparse point anywhere on the path. The sync never copies or reads the value; it checks only that the file is present and owner-only, reported per host, and a real sync fails the host otherwise. No link or junction may sit anywhere on its path. The launcher reads it into the child environment at launch time, failing closed on a missing, linked or unsafe file. The value is never written to `config.json`, `mcp-env.json`, or any client file, so it cannot go in `env`. Keep the non-secret `ANTHROPIC_BASE_URL` in `env`.
  - `args`: strings the launcher puts right after the executable, so they are global flags before any subcommand Paseo adds, such as `["-c", "model_provider=\"example_router\""]` for `codex app-server`. The host's provider command must then be the executable alone. The named provider section (`[model_providers.example_router]`) must exist in that host's `~/.codex/config.toml`, for example through `client-config.json`.
  - A host's `hosts.<name>.launch.<provider>` replaces the top-level entry for that provider; `{}` drops it. Dropping a provider's settings unwraps its command on the next sync unless fleet MCP env files still need the launcher. Without `launch` settings, Windows provider commands stay unwrapped.

To create a Windows token file, run `scripts/new_token_file.ps1` as the user the Paseo daemon runs as, under the secret runner so the value arrives in an environment variable and is never typed or printed (`ROUTER_KEY` stands for that variable):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\new_token_file.ps1 `
  -Path "$env:USERPROFILE\.config\example-router\api-key" -FromEnv ROUTER_KEY
```

It refuses an existing file and any link or junction on the path, creates the file with a protected ACL granting only the current user's SID, reads that ACL back from the open handle, and stops before writing the value, removing the empty file, if anything differs. To replace a value, delete the file first.

- `disabledProviders`: optional list of provider ids to turn off, such as `["example-retired"]`. Each listed id gets `enabled: false` in `agents.providers.<id>`, keeps its other fields, and loses its `models` key, so its picker shows none. Removing a block from `providers` alone leaves the host's old block as it was. An id may not also be in the host's effective `providers`, and `pi`, `claude` and `codex` are refused. The dry run and the result line name only the ids that run turns off (enabled or missing before); a host whose listed rows are already off names none.
- `hosts`: optional settings by host name, each for a host with the `providers` scope.
  - `disabledProviders`: replaces the top-level list for this host; `[]` disables none.
  - `launch`: per-provider launch settings layered over the default, as above.
  - `env`: per-provider values layered over the default.
  - `inherit_env`: `false` skips the default `env`, so the host keeps its own values.
  - `required_env`: per-provider variable names that must be set after the merge, or the host fails without a write.

## Pi surface on stock Paseo

The optional `example/pi-provider-overlay.json` illustrates the Pi fields to add to your existing provider catalog. `paseo-providers.json` may contain `pi` with `root`, `catalogSources` (normally `claude` and `codex`), `defaultSourceProvider`, and `runtime`. Hosts can override `pi`; the provider step generates Pi's `models.json` from the same provider rows on every selected host. Do not maintain a separate Pi model list. Canonical labels are Opus, Sonnet, Fable, Haiku, Astra, Sol, Luna, Web Extra, Web Pro. Use one row per label. An optional `pi.claudeApiKeyRoute` of `{"prefix": "api", "labelSuffix": "API"}` adds a second Pi entry per Claude row, labeled for example "Opus API", whose model ID is `<prefix>/<apiModelId>`. Use it when the router pins that prefix to a pay-per-use API key while plain IDs keep the subscription logins. The entry copies the Claude row's transport, context window, output limit and thinking options, so verify the key's real context window first. It applies to Pi only, never to the native Claude provider. Each entry sits directly after its base row. An optional `pi.contextWindows`, for example `{"Opus": 400000}`, sets Pi's context window per canonical label (API entries included) when the backend's effective cap is below the catalog default (1,000,000 for Claude rows, 272,000 otherwise). Pi's context meter and compaction trigger both read it; Pi compacts above the window minus `compaction.reserveTokens`, and the summary may use 80 percent of the reserve up to the model's 32,768 output tokens, so keep a reserve of at least 40,960 when summaries need that full cap. An optional `pi.maxTokens`, for example `{"Opus": 65536}`, sets the output cap per canonical label (API entries included) in place of the default 32,768, validated like `pi.contextWindows`. Pi caps a compaction summary at min(0.8 x `reserveTokens`, `maxTokens`), thinking included, so a long session whose summary outgrows 32,768 tokens fails and retries the whole request. Raising `maxTokens` alone does not help: also raise `compaction.modelOverrides.<model>.reserveTokens` in the Pi settings, keyed by the exact `provider/modelId` (for example `fleet/<apiModelId>`, and `fleet/api/<apiModelId>` for an API entry), to at least 1.25 x the new cap (81,920 for 65,536). Pi then compacts earlier, at the context window minus that reserve. An optional `pi.labelOrder`, for example `["Fable", "Opus", "Sonnet"]`, puts those labels first in Pi only, each followed by its API entry; unlisted labels keep their catalog order and direct provider rows stay last, and new picker rows need a daemon config reload. An optional `pi.options` object becomes the generated Pi row's Paseo provider options (`agents.providers.pi.options`), for example `{"rpcTimeoutMs": 900000}` to let Pi acknowledge a prompt after a long pre-prompt compaction instead of failing at Paseo's 60-second default. Paseo validates the fields (Paseo accepts `sessionDir`, `rpcTimeoutMs` and `extensionTimeoutMs`) and applies them to Pi sessions started after the reload; a running Pi agent keeps its old values until `paseo agent reload <id>` or a daemon restart. `rpcTimeoutMs` bounds every Pi RPC, so a hung Pi process also takes that long to fail. Removing `pi.options` later leaves the host's existing value in place, like other provider fields. A row may include `api` and `apiModelId` when the backend requires a different API or catalog ID than the native CLI. Copy the backend ID from its model list. For example, a native Claude catalog can retain its context suffix while the same row records the router's exact unsuffixed ID. Native routes remain available.

`runtime` describes the router `route` (TOML path and key path) or `baseUrl`, existing `credential` reference, optional `credentialHeaders`, `python` (Python 3.11+), and the loopback `paseoMcp.url`. The router base URL must use https unless its host is loopback (`127.0.0.1`, `localhost`, `::1`), because the key travels as a Bearer header. Credentials resolve at request time through an existing text, env, env-file, JSON, TOML or command source. A `command` source, `{"kind": "command", "argv": [...]}`, keeps the value in an OS secret store instead of a plain-text file: `credential.py` runs that fixed argv without a shell and reads one line from its stdout, which goes only to Pi; the helper's stderr is dropped and `credential.py` caches nothing, so a rotated value applies to the next request. Pi runs that command synchronously once for the router key and once for each `credentialHeaders` header on every request, with one 10 s try, so a host under heavy load could fail a turn although the credential was fine. So before each model request of a run, before each manual or automatic compaction and before a branch summary, the `fleet-routing.mjs` extension runs the router's `credential.py` command itself, without a shell: up to 3 tries of at most 15 s each, 1 s and then 2 s apart. It hands the value to Pi as the router key and those headers, in that Pi process's memory only, so Pi starts no helper of its own. When every try fails it reuses the value of its last successful read, for at most 15 minutes after that read. Without such a value Pi runs the command itself and, if that fails too, fails the request as before (`Failed to resolve API key`). Each successful read replaces the held value, so a rotation still applies to the next request. A run keeps the value lent until it ends and a compaction until it succeeds or fails; a branch summary, whose credential Pi reads once as it starts and whose failure or cancel Pi does not announce, keeps it lent while its refresh runs and then for a 30 s lease. Once none of these holds it, and once the held value is 15 minutes old, Pi runs the command itself again. The value is never written to a file, a log, argv or the environment. Route evidence gets a `credential` row only for an outcome other than a first-try read: `read-after-retry`, `last-good` (with its age), `unavailable`, `expired` or `override-failed`. A failed compaction gets a `compact_failed` row with its reason, `aborted`, `errorKind` (`token-cap`, `aborted` or `upstream`), `httpStatus` (from Pi's `failed: NNN:` or a provider's `API error (NNN)` text, or null), session id, model and thinking level, and never any upstream error text. For a router model the extension also writes the compaction summary itself with Pi's own `compact()`: its thinking level is the lower of the agent's level and `compaction.thinking` (default `medium`), and `compaction.lengthBound` (default: under 8,000 words, finished items dropped) is appended to any `/compact` instructions. Both are optional `runtime` keys: `thinking` is a Pi level (`off` to `max`) and `lengthBound` one line of at most 1000 characters. The level is clamped to the model's levels as Pi clamps its own. Pi's prompts, its split-turn summary and its file lists stay as in its own compaction. Pi carries file lists only from its own summaries, so before every compaction, on any provider, the extension adds the previous fleet summary's lists to Pi's preparation. Pi never drops a path from those lists, so the extension also keeps at most `compaction.maxFiles` paths per list (an optional `runtime` key, a whole number from 0 to 100000, default 100, 0 keeps all), most recent first by the last call in the session that touched each path, so the summarized span's paths always win; Pi's own summaries store their lists sorted, so their order is never taken as recency. A path is in exactly one list, modified if it is among the kept modified paths, else read. This applies to Pi's default compaction too. A fleet summary that dropped paths ends with one line giving the count, so an agent knows the lists are partial; Pi's default summary is capped the same way but has no such line. The previous summary's file block and count line are removed before it is summarized, so each summary carries one block and at most one line, at the end. The request uses the lent credential and the headers Pi's own summary request carries (service tier, client request id), with at most 2 retries. compact() is used only from a tested Pi version (1.0.0) with its known shape, and Pi saves the result. If that summary fails or comes back empty, Pi's default compaction runs as before, a second full attempt, and a `compact_failed` row with `fallback: "pi-default"` records the first failure (`errorKind` `unavailable` when compact() could not be loaded or has another shape). Each saved summary gets a `compact` row with its reason, `fromExtension`, model, thinking level, `outputTokens` (reasoning included), `summaryChars` and `tokensBefore`, never its text. Direct providers keep Pi's own per-request command and Pi's own compaction. The program must be an absolute path to an allowlisted helper: macOS `security find-generic-password ... -w` (Keychain), Linux `systemd-creds decrypt ...` ending in `-` so it decrypts to stdout (an encrypted credential), or a Python interpreter running a helper script file (for example one that unwraps a Windows DPAPI copy), never `-c` or `-m`. The allowlist checks the program file name and shape only, POSIX and Windows paths alike, because the provider sync checks every host's runtime on the source host; a wrong path fails on the target at request time. A Python helper runs whatever script you name with your authority, and argv is stored in `runtime.json` and visible in the process list, so never pass a value in argv. An optional `gmail` object (`email`, `home`, optional loopback callback `port`) adds a read-only Gmail MCP server from the `workspace-mcp` package installed in `home/venv`. `home` holds the OAuth client JSON and token, owner-only, and is never synced; on POSIX, configure refuses a group- or other-accessible `home`. Read-only is enforced three times: the server runs with `--read-only` (the `gmail.readonly` scope), write and auth tools are passed to `--disabled-tools`, and Pi hides the server except for an allowlist of read tools, which are reachable through Codemode. To use a shared Gmail server instead, remove this block and declare `mcpServers.gmail` in `client-config.json` (see Fleet MCP servers). Pi reads `mcp.json` at session start, so writing it needs no daemon reload. An optional `directProviders` object adds OpenAI-compatible endpoints that bypass the router, such as a local model gate: `{"<name>": {"baseUrl": "https://gate.example.test/v1", "api": "openai-completions", "auth": "none", "models": [{"id", "name", "reasoning", "input", "contextWindow", "maxTokens", "cost", "thinkingLevelMap"}]}}`. Each model is listed once; it becomes a `models.json` provider and a picker row `<name>/<id>` labeled with its `name`, with thinking options from the non-null `thinkingLevelMap` levels (Medium preferred as default). `auth` is `"none"`, which gives Pi the dummy key `local-no-auth`, or `{"credential": <source>}` for an endpoint that wants a Bearer token (`example/pi-provider-overlay.json` shows one backed by the macOS Keychain). Pi's key is then a `!command` that runs `credential.py` on that source for every request, so Pi sends `Authorization: Bearer <value>` and the value never lands in `models.json`, `runtime.json`, agent copies or logs. The source must be an exact reference with only its kind's fields (`env`: `name`; `text`: `path`; `env-file`: `path`, `name`; `json`, `toml`: `path`, `keys`; `command`: `argv`) and no `prefix`; a literal value, a plain string, an unknown kind or any other key is refused. A missing or failed credential fails only that provider's requests, with Pi's `Failed to resolve API key for provider "<name>"` error; other providers keep working. The token travels in a request header, so use https or a hop that is already encrypted. Headers, `compat` flags, other APIs and the names `fleet`, `opencode` and `llama.cpp` are rejected. These routes have no service tier, so Fast is never offered. New picker rows need a daemon config reload. No key contents belong in this file. Generated Pi settings fix built-in Codemode on with `defaultTools: ["+codemode"]`; no profile, feature or per-agent flag enables it. Sync validates these settings and the runtime fails closed if the effective session settings or active tools lack Codemode. Session evidence records the check. The skills sync discovers the configured official Pi home from the host provider command and installs the same selected, manifest-verified skills under `agent/skills`; generated settings reference that shared directory. Global instructions sync to `agent/AGENTS.md` and are copied into each agent home at launch. No Claude-only tool is required to discover and read these skill files. The settings carry the source provider's default model and thinking. Pi exposes only its supported thinking levels; Web models retain model-fixed thinking. Native `ultra` and `ultracode` selections need an explicit native fallback because Pi 1.0 has no such selector.

An optional `guard` object, `{"protectedServices": ["<launchd label>", "<systemd unit>", "<process name>"]}`, names the shared fleet services a Pi agent must not stop by hand: the model bridge, the router, a Paseo daemon, Tailscale serve. `service-guard.mjs`, which `fleet-routing.mjs` loads, checks every `bash` and `powershell` call (nested Codemode calls too) and refuses, with a reason naming the rule (one detached `nohup` script that changes, restarts, health-checks and rolls back), a command that would stop one: `launchctl bootout|unload|remove|kill|disable|stop` (and `launchctl bootout` of a whole domain such as `gui/<uid>`), `systemctl [--user] stop|disable|kill|mask|restart`, `service ... stop|restart`, `brew services stop|restart`, Windows `Stop-Service` (`spsv`), `Restart-Service`, `Suspend-Service`, `Set-Service -Status Stopped` or `-StartupType Disabled`, `sc stop|config ... disabled`, `net stop`, `schtasks /end|/delete|/change /disable`, `Stop-ScheduledTask`, `Disable-ScheduledTask` and `Unregister-ScheduledTask` of a protected name; `kill`, `pkill`, `killall`, `taskkill` and `Stop-Process` of a protected name, of a PID whose command line (read with `ps`, or PowerShell `Get-CimInstance` on Windows, a few seconds at most) names one, or of a PID that exists but cannot be read; `pkill`/`killall` patterns that match a protected process on the host; `kill -1`, `kill 0`, process groups (`kill -- -N`) and a `pkill`/`killall` that selects by user, group, session or terminal with no pattern (`pkill -u $USER`) always; a `kill` of a PID read from a file the command reads (`kill $(jq -r .pid ~/.paseo/paseo.pid)`, `$(cat <file>)`, `xargs kill < <file>`, `pkill -F <file>`) when that PID names one; `Stop-Process -Name` and `taskkill /IM` of an image name a protected process runs as (`node.exe` for a Paseo daemon); `paseo daemon stop|restart|uninstall` with options anywhere; host reboot or shutdown (`reboot`, `shutdown` except `-c`, `halt`, `poweroff`, `systemctl reboot|poweroff|halt|kexec`, `shutdown.exe /r|/s`, `Restart-Computer`, `Stop-Computer`), which stops every protected service; and `tailscale down|logout|switch`, `tailscale set --shields-up` or `tailscale serve|funnel ... off|reset`, with options anywhere. It parses the command like the shell does: quotes (`'...'`, `"..."`, `$'...'`, PowerShell's), escapes, brace expansion, comments, heredocs and here-strings, `NAME=value` and `$HOME`/`$PWD` expansion, and operators split it into segments. `$(...)`, backticks and PowerShell `(...)` are checked as commands of their own and leave a placeholder in their word; `bash -c`, `su -c`, `eval`, PowerShell `Invoke-Expression`/`iex`, `env -S`, `pwsh -Command` and `-EncodedCommand` strings, a heredoc into a shell (`sudo -s` and `sudo -i` with no command and `su` count as shells), and `echo`, `printf` or a `cat` heredoc piped into a shell are checked as commands; wrappers (`sudo -u <user>`, `nice -n <n>`, `timeout`, `xargs`, `nohup`, `env`) are skipped with their option values. The remote command of `ssh <host> '<cmd>'` or `ssh <host> -- <cmd>` is checked like `bash -c`, against the default fleet-wide entries only, since per-host lists, PIDs and processes are local. The arguments of `grep`, `egrep`, `fgrep`, `rg`, `ag`, `ack` and `journalctl` and the messages of `git commit` and `git tag` are data and never checked, so `journalctl -u tailscaled | grep -i kill` and `git commit -m "docs: tailscale down"` pass; their substitutions and other segments still are. Text in quotes is also checked as a mention, where only a literal protected name refuses: `echo "launchctl bootout <protected label>"` is refused, `git commit -m "pkill on server shutdown"` is not. A refused verb whose target is not written out (a substitution, variable, glob, `xargs` placeholder or piped input) falls back to the whole command: refused when any argument names a protected service (4+ character parts and glob fragments count, as in `kill $(pgrep -f Paseo)` or `Get-Process *paseo* | Stop-Process`) or a `pgrep` pattern in it matches a protected process. A file the same command writes with `cat`/`tee` and a heredoc or `echo`/`printf` and a redirect is checked as written when a later segment runs it. A local script a command runs (`bash|sh|zsh <file>` with any options, `bash < file`, `cat file | bash`, `source <file>`, `./file` behind wrappers, `pwsh -File <file>`, `& <file>`) is read and checked the same way, four levels deep: a script over 256 KB or nested deeper is refused, a binary is skipped, and a relative path is resolved against every directory the command may have moved to with `cd`, `pushd` or a subshell; a script whose name names a stop that cannot be located after an unfollowed `cd` is refused. The one exception is a script run detached: either `nohup <cmd> &` as the last segment of the whole command with stdout and stderr both redirected away from the tool (`>file 2>&1`, `>/dev/null 2>&1`, `&>file`), such as `nohup bash fix.sh >log 2>&1 &`, or `setsid -f ...` (or `setsid ... &`) anywhere. Pi stops tracking the shell once it exits, so a job it leaves behind survives a later cancel; anything after the backgrounded `nohup` (`& wait`, `& sleep`, `; echo`, `&& ...`) keeps the call open, so a cancel or timeout kills the script halfway, and without both redirects the script dies of SIGPIPE once Pi stops reading, which `nohup` does not ignore. On Windows only the bash tool's `nohup` form counts (Git Bash has `nohup`); PowerShell `Start-Process` is not recognized, so a PowerShell repair of a protected service is always refused. Every stop in the script must be followed by a restart naming the whole protected entry (`launchctl kickstart|bootstrap|load`, `systemctl start|restart`, `paseo daemon start|restart`, `tailscale up`, `Start-Service`, `Restart-Service`) and then a health check (`curl`, `wget`, `nc`, `pgrep`, `paseo daemon status`, `paseo ls`, `launchctl print`, `systemctl is-active|status`, `tailscale status`, `Invoke-WebRequest`, `Get-Service`). Both count only as the command of a segment that runs: comments, a verb after `:` or `echo`, a branch skipped by `false &&` or `true ||`, and anything after an unconditional `exit`, `return` or `exec` never count, and `launchctl enable` is not a restart. Write such a script with the write tool: a heredoc that writes it is refused because its body names the stop. A `pkill` pattern runs as a regex in a `vm` context with a 250 ms limit; a pattern that runs over it is refused. The defaults `Paseo Daemon`, `Paseo Supervisor`, `paseo-daemon`, `@getpaseo/server`, `tailscaled` and `tailscale` always apply, and entries add to them. A name matches when a target contains it or, at 4 characters or more, is part of it, ignoring case, spaces and underscores, with Windows backslashes read as slashes. `kill $!` (or a variable holding `$!`) after a `&` in the same command kills the command's own background job and is allowed, as in `mkdocs serve & sleep 2; kill $!`. Sync refuses a `guard` that is not exactly `protectedServices`, a list of names of 3 or more characters; at runtime a missing or invalid list keeps the defaults, warns on stderr and writes a `service-guard-config` row to route evidence, and never turns the guard off. The sync writes `service-guard.mjs` before `fleet-routing.mjs`, and `launch.mjs` refuses to start Pi when it is missing. Any sandbox profile used with `pi-isolated` must allow reading `PI_ROOT/service-guard.mjs`, or every sandboxed launch exits 1 because `fleet-routing.mjs` cannot import it. Each refusal writes a `service-guard` row with the tool, the reason and the first 120 characters of the command with `NAME=value`, `Bearer`/`Basic`/`Token` values, API key and cookie headers, `--token`/`--password`-style options and URL userinfo masked; the session's `codemode-check` row records `guardSha256`. Run as `node service-guard.mjs [--runtime <runtime.json>]`, it reads one JSON object on stdin (`{"command": ...}` or a Claude Code PreToolUse payload) and exits 2 with the reason on stderr to refuse, 0 to allow. This is a backstop against a forged instruction, not a sandbox: a command name built at run time (`"$(echo launchctl)" bootout ...`), an interpreter other than a shell (`python -c`, `node -e`), a binary, an MCP tool, a default expansion such as `${X:-launchctl} bootout ...`, a verb built by a substitution (`launchctl $(echo bootout) ...`), a package script (`npm run stop`), `find ... -exec sh {} \;`, and a `kill` of a port lookup such as `kill $(lsof -ti :<port>)` when nothing in the command names a protected service all pass. Known over-refusals: `echo` or `printf` text naming a refused form with a protected target, and a heredoc that writes such text to a file.

To store a token for a `command` source, run one step per host as the user the Paseo daemon runs as, with the value in an environment variable (`EXAMPLE_GATE_TOKEN` here, for example from your secret runner) so it never appears in process arguments or output. `printf` is a shell builtin, and `security -i` reads its command from stdin:

```sh
# macOS Keychain; argv: ["/usr/bin/security", "find-generic-password", "-s", "example-gate", "-a", "EXAMPLE_GATE_TOKEN", "-w"]
printf 'add-generic-password -U -s example-gate -a EXAMPLE_GATE_TOKEN -w %s\n' "$EXAMPLE_GATE_TOKEN" | /usr/bin/security -i
# Linux systemd-creds; argv: ["/usr/bin/systemd-creds", "decrypt", "--user", "--name=example-gate", "/home/me/.config/example-gate/token.cred", "-"]
(umask 077; mkdir -p ~/.config/example-gate && printf %s "$EXAMPLE_GATE_TOKEN" | systemd-creds encrypt --user --name=example-gate - ~/.config/example-gate/token.cred)
```

On Windows, use a Python helper script that keeps a DPAPI (current user) copy and prints it for a `print` argument; argv `["C:\\Users\\me\\AppData\\Local\\Programs\\Python\\Python312\\python.exe", "C:\\Users\\me\\.local\\share\\example-gate\\token-helper.py", "print"]`. Store the copy from a shell in the daemon's own logon session. Check a stored value by length only, for example `/usr/bin/security find-generic-password -s example-gate -a EXAMPLE_GATE_TOKEN -w | wc -c`.

Install official Pi 1.0.0 first using the reviewed `scripts/pi/apply.sh` (POSIX) or `apply.ps1` (PowerShell), with a generated per-host proposal and a fresh `--state` file. `plan`, `apply`, and `rollback` require a reachable stock daemon reporting a release version in `>=0.15.0 <0.16.0`. The launcher also accepts a resume that passes `--session` without `--model`, because Paseo applies the model over RPC. `--activate` reloads only that selected daemon. Apply backs up the daemon config and records, for each runtime file, its prior bytes and the hash of what apply writes there, before writing. A config change another controller makes during apply is merged into, not overwritten, and that revision is backed up and recorded instead. When the Pi provider's command already runs through the providers step's `mcp-env.cjs` launcher (`<node> mcp-env.cjs -- <command>` or `<node> mcp-env.cjs --provider pi -- <command>`), apply keeps that wrapper. It keeps the command after `--` as well, byte for byte, when that command already runs this root's `launch.mjs` with node; otherwise it writes there the command the providers step builds, `node <root>/launch.mjs`, with the root expanded as that step expands it. So a reapply never drops the per-launch token loading, and the next providers step finds the command unchanged. An unwrapped Pi command is replaced whole, as before. Rollback verifies the backup and refuses unrelated config changes. It then checks every runtime file before changing anything: each must still hold what apply found or what it wrote, as a regular file with no symlink or junction up to the runtime root, so an edit made since apply, even to a file rollback would delete, stops it. It restores runtime files atomically and verifies them, then checks again, right before restoring the daemon config, that the config is still apply's or the original revision and the backup is intact, and only then restores it and reloads. Apply and rollback stage the daemon config in an unpredictable, exclusively created temp file beside it, refuse a config that is a link, a reparse point, or not a regular file, and verify the installed config's digest. A runtime path with a symlink, or on Windows any reparse point such as a junction, is refused before anything is written. A failed partial apply can be rolled back with the same state. A state written before these per-file hashes is refused; restore its runtime by hand after checking the files. The installed package is retained for later reapply.

The interim stdio bridge, added because an older Paseo (0.10.3) rejected official Pi through its `mcpServers` API, exposes the daemon tools through Codemode and fills omitted child provider/model/thinking from the current parent snapshot, while preserving explicit overrides. To change one Pi agent only, for example a context-window trial, write `models.overlay.json` or `settings.overlay.json` into `<pi root>/agents/<agent id>/`. Each launch or resume rebuilds that agent's `models.json` and `settings.json` from the shared `agent/` copies and applies the overlay on top. Only this allowlist is accepted: `models.overlay.json` is exactly `{"providers": {"<provider>": {"models": [{"id": "<model id>", "contextWindow": n, "maxTokens": n}]}}}`, and `settings.overlay.json` is exactly `{"compaction": {"enabled": true|false, "reserveTokens": n, "keepRecentTokens": n, "modelOverrides": {"<provider>/<model id>": {"reserveTokens": n, "keepRecentTokens": n}}}, "skillsExclude": ["<skill name>"]}`, where every field other than `id` is optional but each object, list and model entry needs at least one, `n` is a positive integer, each model `id` is a non-empty string, and each `modelOverrides` key has the form `<provider>/<model id>`. A model entry or `modelOverrides` key naming a model that is not in the shared `models.json`, such as one since retired from the catalog (or whose whole provider left it), is checked like any other entry and then skipped: the launcher prints exactly one stderr line, `Pi launch: model override "<provider>/<model id>" not in models.json, using default`, that model keeps the shared `models.json` and `settings.json` values, every other entry still applies, and the launch continues, so retiring a model never stops an agent from starting. Each `skillsExclude` entry is unique and is only the name of a skill directory holding a `SKILL.md` (no paths, globs or `..`) directly under exactly one root Pi loads skills from: the shared `agent/skills`, the agent's own `agents/<agent id>/skills`, or `~/.agents/skills`, where Paseo installs its skills (`$HOME`, else the OS home, so `%USERPROFILE%\.agents\skills` on Windows). A name in two of them is refused. A name in none of them, such as a skill retired since the overlay was written, excludes nothing: the launcher prints one warning line naming it to stderr and the launch continues, so retiring a skill never stops an agent from starting. The skills step reports, per host, any agent whose `skillsExclude` names a skill it retires, and never edits the overlay (see `Local-edit protection` in `SKILL.md`). Project `.pi/skills` and `.agents/skills` load only for a trusted project, which the fleet's `defaultProjectTrust: "never"` rules out in RPC mode, so they are not roots. The launcher appends Pi's exact exclusion `-<that root>/<name>` to `skills`, which removes only that skill from the agent's skill list and `/skill:` commands, for example `{"skillsExclude": ["<skill name>", "paseo-advisor"]}` to keep skills out of a PM's index while workers keep them. Any other key, a wrong JSON type or a bad value, an unreadable file or invalid JSON refuses the launch and leaves the agent's files as they were. On every row, sandboxed or not, the launcher opens an overlay without following links and without blocking: an overlay that is a symbolic link refuses the launch, and one that is not a regular file, a FIFO included, refuses at once instead of hanging it. For example, a 1M window: `{"providers": {"fleet": {"models": [{"id": "<model id>", "contextWindow": 1000000}]}}}` with `{"compaction": {"modelOverrides": {"fleet/<model id>": {"reserveTokens": 40960}}}}`. It applies at the agent's next launch or `paseo agent reload <id>`, and deleting the overlay restores the shared values the same way. The syncs never write or remove files under `agents/`, and probes and launches without a caller ignore overlays.

### Isolated Pi provider

An optional `pi.isolated` object (top level or in a host's `pi`) adds a second Paseo provider for agents that must not reach live tools, such as an eval replaying an old task. It has three keys; any other key refuses:

- `providerId`: the new provider's id, default `pi-isolated`. It must match Paseo's `[a-z][a-z0-9-]*`, differ from `pi` and every Paseo built-in provider, and not be in the host's `providers` or `disabledProviders`.
- `sandboxProfile`: optional path to a macOS `sandbox-exec` profile, absolute or starting with `~/`, expanded on the host. Only `macos` hosts accept it.
- `sandboxProfileRoot`: optional directory, absolute or starting with `~/`, expanded on the host, under which each agent names its own profile (see Per-agent profiles). It excludes `sandboxProfile`: a block with both refuses at sync.

Only `macos` hosts take `pi.isolated`. A `linux` or `windows` host refuses it at sync, the merge refuses it off macOS, and the launcher refuses an isolated launch off macOS. On Linux `/usr/bin/env` is dynamically linked, so a per-agent `LD_PRELOAD` would run inside it before its scrub; Windows has no `/usr/bin/env`; and the sandbox is macOS only.

The providers step then writes `agents.providers.<providerId>` with `extends: "pi"`, the label "Pi isolated", `paseoTools: {"enabled": false}`, the same picker rows and `options` as the generated Pi row, and the command `/usr/bin/env -u <var> ... <this host's absolute node> <pi root>/launch.mjs --loadout-isolated`, plus `--loadout-sandbox-profile <expanded path>` with a profile or `--loadout-sandbox-root <expanded dir>` with a profile root. Isolation lives in the command because Paseo lets a per-agent request (`paseo run --env`, `create_agent_request.env`, a plugin hook) override a provider's env, and keeps it on resume, but not its command. That env still reaches the process that runs the command, so it could pick which `node` runs, or name files that Node, OpenSSL or the dynamic loader read before any JavaScript runs. The absolute node path and the env scrub close that. The scrub (`ISOLATED_SCRUBBED_ENV` in `scripts/paseo_providers.py`) clears every variable that loads code, modules, config or data files, or changes module resolution, from these sources:

- Node.js 24 and 26 `doc/api/cli.md`, Environment variables: `NODE_OPTIONS`, `NODE_PATH`, `NODE_REPL_EXTERNAL_MODULE`, `NODE_ICU_DATA`, `NODE_COMPILE_CACHE` and its `_PORTABLE` and `_READONLY` variants, `NODE_EXTRA_CA_CERTS`, `NODE_PRESERVE_SYMLINKS`, and ICU's `ICU_TIMEZONE_FILES_DIR` (Node embeds ICU);
- OpenSSL 3.5 `openssl-env(7)` (Node reads `OPENSSL_CONF` at startup and can load a provider module from it): `OPENSSL_CONF`, `OPENSSL_CONF_INCLUDE`, `OPENSSL_CONFIG`, `OPENSSL_ENGINES`, `OPENSSL_MODULES`, `CTLOG_FILE`, `RANDFILE`, `SSL_CERT_DIR`, `SSL_CERT_FILE`;
- glibc `ld.so(8)` (kept for a launcher run without the macOS row): every `LD_*` variable it lists, plus `GCONV_PATH`, `GLIBC_TUNABLES`, `LOCPATH`, `NLSPATH` and `HOSTALIASES`;
- macOS `dyld(1)`: the library and framework path variables and `DYLD_INSERT_LIBRARIES` (running through `/usr/bin/env` also purges every `DYLD_*`);
- jiti, Pi's extension loader: every `JITI_*` variable in Pi 1.0.0's installed packages;
- Pi 1.0.0: `PI_PACKAGE_DIR` and `PI_CODING_AGENT_SESSION_DIR`.

An isolated launch refuses when any of these, or any other `LD_*`, `DYLD_*`, `OPENSSL_*` or `JITI_*` variable, is still set, which catches a row without the scrub; if the daemon's own environment sets one, every isolated launch refuses until it is removed. Output-only and behavior variables (`NODE_DEBUG`, `NODE_V8_COVERAGE`, `TZ` and the like) stay. This covers the documented variables, not every way an env can change a process. The launcher also ignores `LOADOUT_PI_ISOLATED` and `LOADOUT_PI_SANDBOX_PROFILE` in the env, and an isolated launch refuses when either is set, even empty; the one exception is `LOADOUT_PI_SANDBOX_PROFILE` on a row with `--loadout-sandbox-root`. The row is never wrapped in the `mcp-env.cjs` launcher, so neither the rollout bridge's MCP bearer env nor `launch.pi` settings reach it. With Paseo's tools off, Paseo injects no `paseo` MCP server and no capability token into the agent's integration extension. Without `pi.isolated` the payload and the config are exactly what they were before this key existed. Removing the key removes the row, and removing `sandboxProfile` or `sandboxProfileRoot` drops it from the command, on the next sync (the result line reports `removed [...]`). The main Pi provider is unchanged either way.

The launcher reads the `--loadout-*` markers only at the start of its arguments and strips them before Pi sees them; a marker anywhere else, a profile or profile root without `--loadout-isolated`, or both a profile and a profile root, refuses. An isolated launch needs a Paseo caller: without `PASEO_AGENT_ID` it has no agent home and refuses. The isolated row's `--mode rpc` probe (model catalog, and Paseo's MCP-support check) runs on the shared agent dir with `--no-approve --no-extensions` and every extension but built-in MCP loaded explicitly, so Paseo sees no MCP support and refuses MCP servers requested for an isolated agent. For an agent the launch:

- writes no `mcp.json` to the agent home and deletes one left by an earlier launch before Pi starts;
- copies the shared settings (with any settings overlay) with `-builtin:mcp` added to `extensions`, so Pi's built-in MCP support does not load: nothing reads an `mcp.json`, servers an extension registers are never connected, and Codemode has no MCP namespace;
- puts `--no-approve` first, so a project's `.pi/settings.json`, `.pi/mcp.json` and `.pi/extensions` never load (the shared settings already default `defaultProjectTrust` to `never`);
- refuses, with one stderr line and nothing started, `--mcp-config` (what Paseo passes when it detects `pi-mcp-adapter`), `--approve`, `-e builtin:mcp`, and an `extensions` directory in the agent home;
- drops `LOADOUT_PI_MCP_URL`, so the routing extension reads no agent labels and Fast labels are ignored.

With a profile, every launch, probe included, runs as `/usr/bin/sandbox-exec -f <profile> -D CWD=<cwd> -D PI_HOME=<agent home, or the shared agent dir for the probe> -D PI_ROOT=<Pi root> <node> <Pi cli> ...`. Off macOS, without an executable `/usr/bin/sandbox-exec`, or when the profile is not a readable regular file, the launch refuses with one stderr line; it never runs Pi unsandboxed. Signals and the exit code pass through as before.

#### Per-agent profiles

With `sandboxProfileRoot`, each agent brings its own profile, for example one an eval runner writes per unit. Only on a row whose command carries `--loadout-sandbox-root` does the launcher read the per-agent env var `LOADOUT_PI_SANDBOX_PROFILE` (set with `paseo run --env` or `create_agent_request.env`; Paseo reapplies it on every resume). It checks the value at every launch, after the env scrub, and accepts it only when:

- the root is an absolute path to an existing directory;
- the value is an absolute path without `.` or `..` parts that equals its real path as stored on disk, so no symbolic link at any level and no other letter case or Unicode form (macOS volumes are case-insensitive by default);
- it names a readable regular file under the root's real path;
- that file is outside the agent's working directory and outside the Pi root, which holds every agent home.

The launcher checks only the launching agent's own working directory, so lay out the root so that no sandboxed agent can write the root or any directory between it and a profile (for example, keep each unit's profile beside its `work/` folder, not inside any agent's).

A missing, empty or failing value refuses the launch with one stderr line, resumes and reloads included. Only the checked path reaches `sandbox-exec -f`, and the variable is removed from Pi's env. Paseo's catalog probe carries no per-agent env, so a `--mode rpc` probe without the variable runs under a built-in profile instead (`PROBE_PROFILE`, as `sandbox-exec -p`): no network, no AppleEvents and no keychain service; writes only under the shared agent dir it reads, where Pi keeps the probe's session; and no reads under the account's home (taken from the user database, not the env), the temp folders or `/Volumes`, except the cwd itself, the Node install, `PI_ROOT/app`, `fleet-routing.mjs`, `service-guard.mjs` and the shared agent dir without its `mcp.json`. A probe that does carry the variable uses that profile. The built-in profile grants reads of the Node install prefix (the folder above `bin/node`), so such a probe refuses when that prefix is the home folder or contains it, the Pi root, `~/.config`, `~/.ssh` or `~/.codex`, as with a node at `~/bin/node` or `~/.local/bin/node`; install Node in its own folder instead.

#### What a sandboxed launch does for Pi

A useful profile denies Pi the credential files, its own `!command` credential helper and the system temp folders, so for every isolated launch with a profile (fixed or per-agent) the launcher also:

- reads the router key before `sandbox-exec`, by running the router's `credential.py` command itself: the argv `fleet-routing.mjs` derives from the router provider's `apiKey`, with its timeout and retries (up to 3 tries of at most 15 s) and no shell. The helper runs outside the sandbox, so it never gets the per-agent env: it runs with `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, `HOME` set to the account's home from the user database, and, for an `env` credential source only, that one named variable; nothing else (no `DEVELOPER_DIR`, `PYTHON*` or per-agent `HOME`). Python runs in isolated mode (`-I`: no user site, no `PYTHON*` variables, no cwd on `sys.path`). The program must be an absolute path, so the runtime's `python` must be one; a bare name refuses. Prefer a real interpreter over `/usr/bin/python3`, which on macOS is the `xcrun` shim (and may be too old for `credential.py`). A failed read refuses the launch; there is no fallback. Pi gets the value only in its env, as `LOADOUT_PI_ROUTER_KEY`, and the agent home's `models.json` sets the router provider's `apiKey` and its credential headers to `$LOADOUT_PI_ROUTER_KEY`, so the value is never written to disk or argv. Pi reads it once per launch, so a rotated key applies from the next launch. The agent's own tools (`bash`) can read it from their env too; the profile's network rule, the model route only, is what limits its use. `directProviders` keys keep their `!command`, which fails inside such a profile, so those routes fail there;
- sets `TMPDIR`, `TMP` and `TEMP` to `<PI_HOME>/tmp`, created owner-only (0700) through a descriptor opened without following links; an existing `tmp` that is not a plain directory refuses;
- reads the agent's `models.overlay.json` and `settings.overlay.json` without following links, as on every row: a symbolic link refuses, and a parse error reports only the path and "invalid JSON", never the file's text;
- refuses, before Pi starts, an extension in the settings it loads (the agent's settings, or the shared ones for the probe) that is not a built-in and does not resolve to `PI_ROOT/fleet-routing.mjs` or under `PI_ROOT/app`, and refuses any Pi `packages`, since a profile lets Pi read nothing else under the Pi root;
- copies Paseo's per-session integration extension into the agent home and passes the copy instead. Paseo writes it to `<its temp folder>/paseo-pi-extension-*/paseo-integration.mjs` and passes that path with `--extension`, which a profile denying the temp folders cannot read. The launcher accepts it only when the folder, as given, is a real `paseo-pi-extension-*` folder (no symbolic link) directly under the macOS per-user temp folder (`getconf DARWIN_USER_TEMP_DIR`, which ignores the env, so a per-agent `TMPDIR` cannot move it; a launchd-started daemon gets this folder as its `TMPDIR`), and the file is a regular file owned by the user with a single link, read without following a link; after the open, the folder must still be a real directory and the name must still be the opened file. A directory where the copy goes refuses. It writes the bytes fresh to `<PI_HOME>/paseo-integration.mjs` (0600) on every launch and replaces the argument. A symbolic link, a non-regular file, or any other `--extension` or `-e` value that is not a built-in and does not resolve to `PI_ROOT/fleet-routing.mjs` or under `PI_ROOT/app` refuses. Paseo's model-catalog and MCP-support probes pass no extension. A daemon started with another `TMPDIR` has its extension refused; start it from launchd or with that folder.

Sandboxed agents compact with Pi's default compaction, not the fleet compaction in `fleet-routing.mjs`: their `models.json` names the key variable instead of the credential command, so the extension does not treat their router provider as the fleet route.

A profile should allow only what Pi needs:

- reading and executing the Node binary and its libraries;
- reading, under `PI_ROOT`, only `app/` (the Pi package), `agent/skills`, `fleet-routing.mjs` and the `service-guard.mjs` it imports (without it the extension does not load), not the rest of `PI_ROOT`, which holds every other agent's home and the shared `agent/mcp.json`. Pi needs no credential file or helper: the launcher reads the key;
- reading and writing `PI_HOME` (sessions, settings, route evidence, `tmp`) and `CWD`;
- nothing in the system temp folders: the launcher copies Paseo's integration extension into `PI_HOME`, and Pi's own temp files go to `PI_HOME/tmp`. Never grant writes there: Pi keeps Node's compile cache in the temp directory, shared with the unsandboxed main Pi rows;
- network to the model route's port only. Deny the daemon's listen port; allow only the model route port.

The repository ships no profile; test one by hand before using it.

What isolation does not cover: Pi's built-in `read`, `write`, `edit` and `bash` tools stay, with the user's file access outside any profile, and the network stays open unless the profile denies it. Without a profile, `bash` can reach any service the host can, including the Paseo daemon's loopback port (open without auth when the daemon has no password, so an agent could start a non-isolated agent with the `paseo` CLI), and can run the MCP reader command or read its env files. Use the profile to close what an agent must not reach.

## client-config.json

Optional. `python3 scripts/client_config.py [--dry-run] [--host <name>] [--update-claude]` reads it and updates hosts whose `sync` includes `client-config`. Each host gets the base settings, then its role's, then its own `hosts.<name>` overrides. It holds router URLs, so it stays in the private fleet directory.

- `token_file`: optional path, on the source host, to a secret file. Its contents go to hosts whose settings name a `claude.token_env`, over SSH stdin only. A token file inside the fleet directory stays there: the fleet push never copies it, and refuses to run while `token_file` resolves to one of the files it publishes. The token is never passed as an argument, stored in this file, or printed.
- `codex`: managed keys for Codex `config.toml`.
  - `top`: top-level keys. Missing keys are inserted before the blank lines that precede the first section header.
  - `sections`: named sections such as `model_providers.<id>`, each a map of keys. A missing section is appended.
  - `reportOnly`: top-level keys that are printed per host and never written.
  - `removeTop`: top-level keys an earlier sync managed and this one drops, such as `["model_provider"]`. Each is deleted, with its whole value, where it is set before the first table header; the changed file is backed up first, as for any change. List only keys the sync once wrote: a listed key is removed whoever set it, and keys not listed are never touched.
  - Key, section, and `reportOnly` names are bare TOML keys, optionally dotted (letters, digits, `_`, `-`); a host refuses any other name and writes nothing.
  - Values are strings, numbers, or booleans. The merge is line-based and keeps CRLF, comments, and every other key and section. It reads headers with trailing comments, array tables, quoted keys, and values that span lines (multiline strings, arrays), and replaces a managed key's whole value. Where a construct could define, shadow, or duplicate a managed key path (a top-level key, or a managed section plus one of its keys), it refuses with nothing written and reports `unsupported TOML, edit by hand`: an inline table, a dotted key, or a value spanning lines at, inside, or over a managed key path; a table header at or under a managed key path, such as `[model_providers.example.base_url]`; an array table at or over a managed section; and a key outside a managed section that defines part of it. Other keys and deeper tables in a managed section are left alone, such as an unmanaged key whose value is an inline table, or `[model_providers.example.http_headers]` under a managed `[model_providers.example]`. It also refuses a file it cannot read, and a result in which a managed key would appear more than once, outside its own table, or a table or key would be defined twice.
- `claude`: managed parts of Claude Code `~/.claude/settings.json`.
  - `settings`: top-level keys, each replaced whole.
  - `env`: keys merged into `env`.
  - `token_env`: an `env` name to fill from `token_file`, or `null`. This puts the token in the global `settings.json`, which every terminal session also reads; to route only Paseo-launched Claude, leave it unset and use `launch.claude.tokenFiles` in `paseo-providers.json`.
  - `removeEnv`: `env` names an earlier sync managed and this one drops, such as `["ANTHROPIC_BASE_URL", "ANTHROPIC_AUTH_TOKEN"]`, deleted from `env` with the usual backup. The same rule as `removeTop` applies.
  - Removal waits for the providers step. These lists drop terminal routing that Paseo's provider settings take over, so on a host with the `providers` scope a listed key goes only once the providers step has written that host's current `paseo-providers.json` settings and reloaded its daemon, with no reload owed or in flight since; a failed reload never counts, even when the config was already current. That is recorded on the source host in `provider-activations.json` beside `provider-reloads.json`. Until then the keys stay, the host reports `routing removal HELD` with the reason, its cell reads `held`, and the run exits 1; run the providers step for the host, then client-config again. The check applies to every run, including `--only client-config`. A host without the `providers` scope removes them at once.
  - Removal lists from the base, role and host layers add up. A name that the same host also manages (`codex.top`, `claude.env` or `token_env`) is refused.
  - `minVersion`: base only. Hosts below it are reported, and `--update-claude` runs `claude update` on them. Versions compare like `sort -V`.
- `roles.local`, `roles.remote`: layers with `codex` (`top`, `sections`, `removeTop`) and `claude` (`settings`, `env`, `token_env`, `removeEnv`). The source host is `local` and every other host `remote`.
- `hosts.<name>`: the same layer for one host, plus an optional `role` that overrides the default.

Only these keys are written. Everything else stays host-local. A missing client is skipped. Each changed file is backed up in place as `<file>.bak-loadout-<stamp>-<random>`, a new file that never overwrites an earlier backup, holding exactly the bytes the merge read; the newest 5 are kept (see [Backup retention](#backup-retention)). The write is an optimistic check: the result goes to an exclusive temp file, which is fsynced, then the file is read again and the temp renamed over it at once only if it still holds the bytes the merge read. If anyone else changed it, the temp and backup are removed and the read and merge run once more, merging onto the new revision; a second change fails the host and leaves the file as is. This narrows the window for a lost concurrent edit to the moment between that re-read and the rename, but cannot close it, because the daemon and editors take no lock. A second run reports `unchanged`.


### Fleet MCP servers

`client-config.json` accepts `mcpServers`, an object keyed by server name. Declare each Streamable HTTP endpoint once, for example (all addresses and host names here are made up):

```json
{
  "mcpServers": {
    "ebay-analyze": {
      "url": "http://192.0.2.40:8766/mcp",
      "bearerTokenEnvVar": "EBAY_ANALYZE_MCP_TOKEN",
      "envFile": "~/.config/ebay-analyze-mcp/mcp.env",
      "description": "Search marketplace listings and sold prices.",
      "hosts": { "laptop": true, "desktop": true }
    },
    "gmail": {
      "url": "http://192.0.2.10:8770/mcp",
      "bearerTokenEnvVar": "GMAIL_MCP_TOKEN",
      "hosts": { "laptop": { "url": "http://127.0.0.1:8770/mcp" }, "desktop": true }
    }
  }
}
```

- `url`: HTTP or HTTPS Streamable HTTP endpoint, without embedded credentials, query or fragment. Prefer HTTPS; use HTTP only on a trusted private network. If the server allowlists `Host`, use its allowed IP, not a DNS alias.
- `bearerTokenEnvVar`: uppercase environment variable name, never a token value.
- `envFile`: optional path, absolute or starting with `~/`; defaults to `~/.config/<server>/mcp.env`. A server that lists a Windows host needs the `~/` form, which there means `%USERPROFILE%`, so the default is `%USERPROFILE%\.config\<server>\mcp.env`. The file is delivered separately and holds one literal `VAR=value` line (blank and `#` lines aside), with no shell expansion, quoting or `export` prefix. On POSIX it is owned by the harness user with mode `0600`. On Windows its ACL must pass the same owner-only check as a `launch` token file: inheritance off, an owner that is the current user, SYSTEM or Administrators, allow rules only for those or OWNER RIGHTS, one for the current user, and no link or junction on the path; `scripts/new_token_file.ps1 -EnvName VAR` creates one. The sync never copies, sources, prints or puts its contents into client or daemon config. The launcher reads it afresh each time, so a rotation needs no daemon restart, and it fails closed on a missing, linked, unsafe or empty file.
- `description`: optional one-line summary of what the server offers, at most 2000 characters, without control characters. It goes only into Pi's entries, the generated runtime and the official Pi home `agent/mcp.json`. Pi lists each Codemode server in its system prompt with one line, taken from `description` or, without it, from the server's instructions once it connects; a pinned `description` keeps that line the same from the first turn, so the prompt cache survives the connection. Copy the server's own first instruction line to keep the rendered line identical (Pi shortens both alike). Codex, Claude Code and `mcp-env.json` never get it.
- `hosts`: explicit `hosts.json` names mapped to `true`, `false` or `{"url": "<http(s) url>"}`. The object form enables the server on that host with its own URL instead of the top-level `url`, validated the same way; use it on the host that runs the server itself, which reaches it over loopback. Missing hosts are untouched. All named hosts need both `client-config` and `providers`, Windows hosts included: the providers step installs the launcher that reads each token from its env file. Without it no harness gets a token. Validation names a listed host that lacks `providers`; add the scope to that host in `hosts.json` yourself, since the sync never widens a host's scopes. `false` disables the Codex and Pi entry, removes only that named Claude user entry, and stops loading that server's env file. Set `false` before retiring a previously enabled host; deleting the declaration alone does not retire its prior config.
- Names allow letters, digits, `_` and `-`, must be unique case-insensitively and with `-`/`_` treated alike, and cannot be `paseo`. `gmail` is allowed only while no host listed under it, even as `false`, still has the read-only Pi `gmail` block in its effective `paseo-providers.json` `pi.runtime`; validation names any such host. To move a host from the Pi block to the shared server, remove its Pi block and list the host here in the same change; the next providers sync regenerates Pi `agent/mcp.json` without the old local server, and each new Pi session copies that file. Do not also manage the same Codex table through `codex.sections` or the same Pi server through `pi.runtime`.

`example/mcp-servers-overlay.json` shows the `mcpServers` block to merge into `client-config.json` for a shared `gmail` server: the source host `laptop` runs it and uses the loopback URL, `desktop` uses the top-level URL, and neither host keeps a Pi `gmail` block.

The providers step writes the non-secret `loadout/mcp-env.cjs` launcher and the `mcp-env.json` descriptor (`{"servers": [...], "providers": {...}}`, the latter holding the `launch` settings, plus `unnamed` during a rollout, see below) under the host config directory, after checking that each enabled server's env file is present and owner-only (without reading it); a real sync fails the host otherwise, before writing anything. It wraps the existing enabled Codex, Claude Code and Pi provider commands without changing their arguments, models, other environment keys or agent routes, on Windows as on POSIX. The existing provider reload and reload-owed mechanism applies.

No MCP bearer is in any harness environment except Codex's. Codex reads an HTTP bearer only from its environment (`bearer_token_env_var`; its other options are `env_http_headers` and a static `http_headers`), so on a host with an enabled server the step writes `mcpTokens: true` into the descriptor for the `codex` provider only, and wraps Codex as `node mcp-env.cjs --provider codex -- <command>`. For that provider the launcher reads every enabled server's env file at launch and sets its `bearerTokenEnvVar`; a missing or unsafe file refuses the launch. For every other harness it sets none and removes any inherited variable named by a server, in any spelling on Windows, so a daemon, shell or Windows user environment that still holds one does not pass it on. Claude Code and Pi instead read each bearer when they connect, by running the launcher's reader, `node mcp-env.cjs --mcp-header claude|pi <server>`. It finds that enabled server in `mcp-env.json`, reads its env file with the same owner-only check, and prints exactly the header: `Bearer <value>` for Pi, `{"Authorization":"Bearer <value>"}` for Claude Code. The value must be printable ASCII without spaces. Only the server name is on its command line, never a value. A missing, unsafe or unreadable file, or an unknown or disabled server, prints nothing and exits 1, so the harness sends no Authorization header; it never falls back to an environment variable. A rotation reaches the next connection.

During a rollout the step bridges the clients whose MCP config has not moved yet. Claude Code's `~/.claude.json` (under `CLAUDE_CONFIG_DIR` when set) and Pi's runtime `agent/mcp.json` count as not moved while either still sends `Bearer ${VAR}` for an enabled server. That holds for Pi whether or not this run writes its runtime. For such a client the step keeps the bearers in its environment, as before this change, for both the command the daemon runs now and the one this run publishes:

- `mcpTokens: true` for a `--provider <id>` launch;
- a top-level `unnamed: {"mcpTokens": true}` in `mcp-env.json` for a launch without `--provider`, such as the Pi row.

It is written with the launcher, before the Pi runtime step and the config publish. A failure there, or between this step and client-config, therefore leaves no client with neither source, and neither does a daemon that has not reloaded yet. The report says `until ... uses the reader`. The first providers run after the file has moved drops the bridge. A full sync is therefore providers, client-config, then providers once more. A client with no provider row of its own is not wrapped for the bridge, just as it was not wrapped before.

Residual exposure: the Codex process, and the programs it starts outside tool shells (its `notify` program, hooks, its own git), keep the tokens in their environment, which another process of the same user can read (for example `ps eww` on macOS or `/proc/<pid>/environ` on Linux). Only a static `http_headers` entry in `config.toml` would avoid that, and it would copy the value into the config and every `config.toml.bak-loadout-*` backup, so it is not used. Codex's tool shells do not inherit them (see `shell_environment_policy` below). On Windows, until the values are deleted from `HKCU\Environment`, every process of the session still inherits them from there, the daemon included; the launcher only keeps them from Claude Code and Pi agents. On every OS a Codex launch fails while any enabled server's env file is missing or fails the owner-only check, not only that server's MCP. Before, Windows Codex fell back to the inherited value. So after each rotation check `sync.py --dry-run --only providers --host <host>` shows every file `present, owner-only`.

The generated Pi `agent/mcp.json` gets native HTTP entries with Codemode exposure, each with its `description` when declared. The built-in `paseo` entry carries a fixed generic `description`, so its system prompt line is stable from the first turn too. The scoped loopback Paseo stdio bridge and read-only Gmail configuration are unchanged, not repurposed as generic HTTP proxies.

The client-config step merges:

- Codex `config.toml`: `[mcp_servers.<name>]` with `url`, `bearer_token_env_var` and `enabled`, and `[shell_environment_policy]` `exclude`, listing every server's `bearerTokenEnvVar` on that host, so Codex tool shells drop them. Other keys of that table, and its subtables such as `[shell_environment_policy.set]`, stay host-local. A host-local `exclude` written on one line as plain strings is kept, with the server variables added after its entries; any other form of it is refused. Declaring `shell_environment_policy.exclude` in `codex.sections` is refused.
- Claude Code user-scope `~/.claude.json` (`$CLAUDE_CONFIG_DIR/.claude.json` with a custom config directory): `mcpServers.<name>` with `type: "http"`, `url`, and `headersHelper`, the reader command `"<node>" "<config dir>/loadout/mcp-env.cjs" --mcp-header claude <name>`. User-scope servers need no workspace trust for `headersHelper`. This is personal, cross-project user configuration, not project trust or machine-wide policy. `managed-mcp.json` would impose exclusive system-managed servers and displace users' own servers, so the sync deliberately does not use it. Other user servers and all unrelated user state are preserved.
- The configured official Pi home's `agent/mcp.json`: `description` when declared, `url`, `headers.Authorization` set to the same reader command with `pi` and a leading `!` (Pi runs it at each connection), `enabled` and `exposure: "codemode"`. It discovers that home from the daemon's Pi launch command. The providers step writes the same entries into the Pi runtime it generates. A missing client is reported as absent, not installed.

The reader command names this host's Node (the one the sync ran) and launcher by absolute path, each in double quotes. It runs in the harness's shell: `/bin/sh` on POSIX; on Windows Git Bash (or `cmd.exe` without it) for Pi and `cmd.exe` for Claude Code. All of them read a double-quoted word alike only while it holds no `"`, `` ` ``, `$`, `%`, `!` or control character, nor on POSIX a backslash, so a path with one is refused and the host fails. Because the reader lives in the launcher, client-config refuses a host, writing nothing, until the providers step has installed the launcher this sync publishes (checked by SHA256): run the providers step first, as the full sync does. A dry run, whose providers step installs nothing, reports `MCP launcher waits for the providers step` and previews the rest.

Changed client files retain the normal unique backup and optimistic replacement protection. JSON and TOML contain variable names and the reader command only. The provider dry run reports each URL, credential variable, env-file presence and owner-only check (without reading its contents), and any wrapper files it would write. It never connects to an MCP endpoint or runs a search. For a complete proposal, run `python3 scripts/sync.py --dry-run --only providers,client-config` against the private fleet, inspect every host, then wait for rollout approval. Pi loads the new entries when a new session starts or after `/reload`; existing sessions are not rewritten.

Claude Code and Pi started by hand outside Paseo read the same user config, so they authenticate through the reader with no wrapper. A standalone Codex needs the loader with its provider id, for example `node "${XDG_CONFIG_HOME:-$HOME/.config}/loadout/mcp-env.cjs" --provider codex -- codex`, or on Windows `node "%APPDATA%\loadout\mcp-env.cjs" --provider codex -- codex`; a raw `codex` has no token unless it inherits `VAR`. The sync does not edit shell startup files, global launch services or credential stores. Connection smoke checks should call `tools/list` only, never perform a marketplace search as a sync verification.

### Provider catalog without a runtime install

A providers-only host can set its host `pi` descriptor to `{"catalogOnly": true}`. This derives Pi's models from the same catalog sources, but emits only the `models` field. It preserves local command, availability and environment, and writes no Pi agent home or binary. Before syncing an older daemon, validate the generated rows with that version's schema, back up its config, and exercise a guarded provider-only rollback. This does not activate Pi on a host where it is unavailable.

## Backup retention

Each sync writer that backs a file up beside itself keeps only that file's newest 5 backups of its own naming pattern, counting the one it just wrote, and deletes older ones after the write succeeds. Age is the stamp in the name, not the file time. The patterns are:

- client-config step (`client_config_merge.js`), each changed client file: `<file>.bak-loadout-<YYYYMMDD-HHMMSS>-<8 hex>`.
- providers step (`paseo_providers_merge.js`): `config.json.bak-loadout-<YYYYMMDD-HHMMSS>-<8 hex>`, and for the MCP env files `<file>.bak-loadout-<YYYYMMDD-HHMMSS>-<16 hex>`.
- Pi runtime files (`pi/configure.py`, run by the providers step and by `pi/deploy.py` apply): `<file>.bak-<YYYYMMDDTHHMMSSffffffZ>` (UTC, microseconds).
- skills step, managed-settings `claudeMd` (`skills_sync_remote.js`): `<file>.bak-<YYYYMMDDTHHMMSSZ>` (UTC), removed through `sudo -n` when the write needed it.

Only a sibling of the same file whose whole name matches, with a real date, and that is a regular file counts; a symlink is never followed or removed. Hand-made backups (`.before-*`, `.bak-pr*`, any other suffix) and backups in an older format (such as `.bak-loadout-<stamp>` with no random part) are never touched; delete those by hand. A dry run prunes nothing. A failed prune never fails the write: the host reports a `backup prune failed, kept: ...` line and the files stay. `pi/deploy.py` apply's own daemon config backups (`.before-pi-*`) are rollback state and are not pruned; its rollback restores from the state record, not from `.bak-*` files.
