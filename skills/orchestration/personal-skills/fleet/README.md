# Fleet format

A fleet describes the hosts that `personal-skills` syncs. Sync it with `python3 scripts/sync.py --dry-run`, then `python3 scripts/sync.py`; the per-file tools named below are the steps it runs. The public `example/` folder shows the format with made-up values. Your real fleet lives in a private fleet directory with the same layout, outside this repository.

```
example/                     public, made up
  hosts.json
  paseo-providers.json       optional
  client-config.json         optional
  global/AGENTS.md           optional
  bin/common/hello-fleet    optional helper example
<fleet directory>/           yours, private (copy example/ here and edit)
  hosts.json
  paseo-providers.json       optional
  client-config.json         optional
  global/AGENTS.md           optional
  skills/<name>/SKILL.md     optional private skills (the overlay)
  bin/common/               optional helpers for every host
  bin/macos/                optional macOS helpers
  bin/linux/                optional Linux helpers
  bin/windows/              optional Windows helpers
```

## Where the fleet lives

`python3 scripts/fleet.py resolve` prints the directory in use. The first match wins:

1. `$LOADOUT_FLEET`, a directory. If it is set but missing, resolution fails instead of falling back.
2. `${XDG_CONFIG_HOME:-~/.config}/loadout/fleet/`. On Windows, `%APPDATA%\loadout\fleet\`.
3. `fleet/local/` beside the installed `SKILL.md`, the older location. It is ignored by Git and absent from the manifest.

Edit the fleet only on the source host. `python3 scripts/fleet.py push [--dry-run] [--host <name>]` copies its published files, `hosts.json`, `paseo-providers.json`, `client-config.json`, `global/AGENTS.md`, and `bin/`, to `~/.config/loadout/fleet/` (`%APPDATA%\loadout\fleet\` on Windows) on every other `ssh` host, and every sync run does this first. Every other file in the fleet directory, such as a token file, a pairing offer, a backup, or notes, stays on the source host; a file an earlier push copied and the push no longer publishes is removed from a host whose copy is unedited. Each copy carries a `.loadout-sync.json` record of the hashes last synced. A host's copy is replaced only while it still matches that record. Before it writes, a push also records there the versions of the published files it is about to write, so a push cut off part way recognizes its own writes. A hand-edited, added, or unrecorded differing file is a conflict, and nothing is written on that host until you resolve it, usually by deleting the host's copy. Each published file and the record are written through a uniquely named, exclusively created temp file, and the record is read back. Each write and removal checks its file and the directories from the home directory down again right before it, and a removal first moves the file aside and verifies it, so a linked `~/.config` or a file edited during the push stops the host and keeps the edit. `paseo-relay` hosts get no copy. Hosts need `node`.

With none of these, `fleet.py resolve` reports `fleet: none (current host only)`, and `sync.py` and every step stop with nothing synced until you create a fleet. To sync only this host, create one whose `hosts.json` lists just this host as `source_host`. To move an existing `fleet/local/`, copy it to the config directory, check `fleet.py resolve` reports `config`, then remove the old copy.

The optional private `bin/` holds portable plain files only. The skills step installs `common/` plus the host's `os` folder flat into `~/.local/bin` (`%USERPROFILE%\.local\bin` on Windows), with verified bytes and local-edit protection recorded in `loadout/global-sync.json`; identical existing files are adopted (an identical destination symlink is atomically replaced by a regular file without changing its target), differing unrecorded files are conflicts, and only recorded, unedited files retire on a full run. On macOS/Linux, extensionless files and `.sh` files are `0755`, others `0644`. Duplicate common/OS names, links, nested directories and nonportable names stop the run. Fleet push carries these helpers just like global instructions; real helpers stay in the private fleet, never in this public repository.

## Private skills

Put skills that must stay private (personal, account-bound, or holding credentials) in `skills/<name>/` inside the fleet directory on the source host, laid out like any installed package with a `SKILL.md`. The skills step installs them with the published ones, with the same `--skills` and `exclude_skills` selection and the same local-edit protection:

- A name that is also a published skill stops the run; rename one of them.
- Every overlay file hash a host has accepted is recorded in `skills/.loadout-overlay.json`, so a newer version replaces an older installed one while a hand edit on a host stays a conflict. A skill that moved here from the public repository also replaces its last published copy.
- A skill removed from the overlay is retired from hosts like an unpublished package (see `Local-edit protection` in `SKILL.md`), so keep the overlay complete on the source host and check `--dry-run` first. Set `skills_overlay: true` in `hosts.json` when the fleet keeps an overlay: then a missing `skills/`, or one that is not a directory, stops all retirement on every host, each reported as `blocked`. To retire every overlay skill, leave an empty `skills/` directory.
- Hosts install overlay files owner-only: on macOS and Linux as `0600` files in `0700` directories the sync creates, and a replaced file keeps stricter permissions it already had; overlay files and directories an earlier sync installed lose group and other access. On Windows they inherit the user profile's ACL (the user, SYSTEM and Administrators by default).
- `__pycache__`, `.pyc`, and `.DS_Store` are skipped; symlinks are errors.
- The fleet push does not copy `skills/` to other hosts; skill bytes travel only through the skills step.

## hosts.json

`python3 scripts/fleet.py validate` checks the file and prints each host's transport and sync scopes. Unknown keys and values are errors.

- `schema_version`: `2`. A file without it is version 1: `transport` is free text, every host is reached over SSH, and hosts have no `transport` or `sync` of their own.
- `source_host`: name of the host whose checkout is the sync source. It runs locally, so it must use `ssh`.
- `transport`: default for every host, `ssh` or `paseo-relay`. Record host names, not IP addresses that may change.
- `notes`: optional free text.
- `skills_overlay`: optional, `true` or `false` (default). `true` says this fleet keeps private skills in `skills/`, so the skills step stops all retirement while that directory is missing or not a directory.
- `hosts[]`: one entry per host.
  - `name`: address used by the transport; for `ssh`, the SSH alias. Letters, digits, `.`, `_` and `-`, not starting with `-`.
  - `os`: `macos`, `windows`, or `linux`.
  - `transport`: optional, overrides the top-level value.
    - `ssh`: files and commands travel over SSH.
    - `paseo-relay`: the host is reached only through its Paseo daemon via a pairing offer. There is no file transport, so it cannot take `skills` or `plugins`, and it needs an explicit `sync`.
  - `paseo_offer`: path to a file holding the host's Paseo pairing offer. Required for `paseo-relay`; optional for `ssh`, where it lets daemon commands go over the relay. A relative path resolves inside the fleet directory. Keep offers private: the fleet push never copies an offer to other hosts, and refuses to run while an offer resolves to one of the files it publishes.
  - `paseo_home`: optional Paseo home for this host's daemon, a path that is absolute on that host or starts with `~`, which the host expands. The plugins and providers steps use it for that host only: plugin config reads, settings backups, installs, reloads and `plugin ls` confirmations, and the provider config merge and reload. The skills step still finds a Pi runtime from the default `~/.paseo/config.json`. A `PASEO_HOME`, `PASEO_HOST`, `PASEO_AGENT_ID` or `PASEO_AGENT_CWD` the sync inherits (from an agent session, a scratch daemon, or a host's shell profile) is always cleared first, so without `paseo_home` the default `~/.paseo` and the daemon it names are used. A `paseo-relay` host's reload goes through its offer whatever this says.
  - `sync`: optional list of scopes from `skills`, `plugins`, `providers`, `client-config`, `mds-bye`. Default: `skills`, plus `plugins` when `paseo` is present. Each sync skips a host outside its scope and reports it as skipped, not failed. `providers` (Paseo provider pickers), `client-config` (managed Codex and Claude Code settings) and `mds-bye` (a read-only check, `macos` hosts only; see below) are opt-in. `paseo-relay` hosts can take only `providers`.
  - `exclude_skills`: optional skill names the skills sync leaves alone on this host, such as a package you keep a private version of.
  - `checkout`: path to a local Git checkout of this repository, or `null` (the default). A host without a checkout receives verified bytes from the source host and reverifies them.
  - `clients`: clients to sync, from `codex`, `claude`, `opencode`. Required when `sync` includes `skills`. Absent clients are skipped and reported.
  - `paseo`: optional. Paseo plugin sync for this host's daemon. Required when `sync` includes `plugins`.
    - `plugin_root`: directory where verified plugin sources are staged, one subdirectory per plugin ID. `null` means this host's plugins are managed outside the sync; the sync only reports whether they match the manifest. Changing it for a host with installed plugins needs `sync.py --migrate-path` once.
    - `stage`: plugin IDs whose verified source is copied to `plugin_root`, installed with `npm ci`, and checked.
    - `install`: plugin IDs, a subset of `stage`, authorized for `paseo plugin install` on this daemon. List a plugin here only after its host-local settings and arming have been decided.
- `global`: optional. Maps each client to where `global/AGENTS.md` is installed. A target is a path starting with `~`, `/`, `$VAR` or `${VAR}`, `%VAR%`, or a drive such as `C:\`, and must be absolute once the host expands it. `fleet.py validate` rejects anything else, and a host refuses a target that is not absolute or names a variable it does not set, so text is never written as a file.
  - `codex`: normally `$CODEX_HOME/AGENTS.md`.
  - `claude`: normally `~/.claude/CLAUDE.md`. For a managed deployment, `managed-settings:claudeMd` installs the instructions as the `claudeMd` string field of Claude Code's `managed-settings.json`: `/Library/Application Support/ClaudeCode/` on macOS, `/etc/claude-code/` on Linux, and `%ProgramFiles%\ClaudeCode\` on Windows (`C:\ProgramData\ClaudeCode\` only when that file exists and the Program Files one does not). Only `claudeMd` changes: the file is first backed up beside itself as `<file>.bak-<UTC stamp>`, then replaced atomically and checked. When the user cannot replace it, macOS and Linux use `sudo -n` and keep its owner and mode; if that needs a password, nothing is written. On Windows run the sync from an administrator shell. `--dry-run` reports whether elevation is needed. `LOADOUT_CLAUDE_MANAGED_SETTINGS` on the host overrides the file path, for tests.
  - `opencode`: normally `~/.config/opencode/AGENTS.md`.

Omit `global` or `global/AGENTS.md` to skip global instructions. Global instructions follow the same preflight: never overwrite a changed target that matches no known prior version. For `managed-settings:claudeMd` the preflight compares the field's value, a missing file or field is added, and unparseable JSON or a non-object is a conflict.

Plugin settings, plugin state, and the daemon's `pluginsEnabled` switch are host-local. The sync never writes them. See the `Paseo plugins` section of `SKILL.md`.

## mds-bye (macOS, verify only)

[`hosts/macos/mds-bye/`](../../../../hosts/macos/mds-bye/PROVENANCE.md) vendors [mds-bye](https://github.com/rayhanadev/mds-bye) (MIT) unmodified at upstream commit `18a3ada`. It keeps Spotlight, Siri and Apple Intelligence indexers disabled with a user LaunchAgent and a root LaunchDaemon. The sync never installs it: an owner runs its `install.sh` on a Mac by hand, with `sudo`, and updates the vendored copy only after Config review, since the daemon runs as root.

Add `mds-bye` to a `macos` host's `sync` list to have every sync check that install. `fleet.py validate` rejects the scope on any other OS, and the host program also refuses to run off macOS. The step (`scripts/mds_bye.py`, run last) reads the four installed files and compares them with the committed blobs at the synced `source_commit`:

| Installed file | Committed source | Mode | Owner |
|---|---|---|---|
| `~/.local/sbin/disable-indexers.sh` | `scripts/disable-indexers.sh` | `0755` | the user |
| `/usr/local/libexec/disable-indexers-system.sh` | `scripts/disable-indexers-system.sh` | `0755` | `root:wheel` |
| `~/Library/LaunchAgents/com.rayhanadev.disable-indexers.plist` | `launchd/com.rayhanadev.disable-indexers.agent.plist`, `__HOME__` replaced by the host's home as `install.sh` does | `0644` | the user |
| `/Library/LaunchDaemons/com.rayhanadev.disable-indexers.plist` | `launchd/com.rayhanadev.disable-indexers.daemon.plist` | `0644` | `root:wheel` |

Each file reports `same <file>` or `DRIFT <file>: <reason>` (missing, different bytes, mode, owner, symlink). The table shows `same` or `drift`; drift does not fail the sync or stop other scopes. The step never writes, never runs `install.sh`, and never uses `sudo`, so `--dry-run` runs the same check. To fix drift, review it and rerun `install.sh` by hand. `LOADOUT_MDS_BYE_ROOT`, set in the host's environment, prefixes every installed path for tests against a scratch fake root.

## paseo-providers.json

Optional. The Paseo provider-picker sync (`python3 scripts/paseo_providers.py`) reads it and updates hosts whose `sync` includes `providers`. It holds router URLs and host settings, so it stays in the private fleet directory.

- `providers`: pinned blocks keyed by Paseo provider, such as `claude` or `codex`. Each block's fields replace the same fields in the host's `agents.providers.<provider>`; other fields there are kept. `models[]` rows need a unique `id` and a `label` that is a name only: no digits and not the model ID.
- `env`: optional default environment per provider, merged into `agents.providers.<provider>.env` on every host. A value's `%VAR%` is expanded from the host environment and written in plain text to `config.json` and its backups, so `%VAR%` must never name a secret; names containing KEY, TOKEN, SECRET, PASSWORD, CREDENTIAL or AUTH are refused with nothing written.
- `launch`: optional launch settings for the `claude`, `codex` and `pi` providers, so routing reaches only Paseo-launched agents while a terminal `claude` or `codex` keeps the user's own login. The providers step wraps each provider that has settings in the `loadout/mcp-env.cjs` launcher as `node mcp-env.cjs --provider <id> -- <command>` and records the settings in `loadout/mcp-env.json`; both are non-secret. The directory is `${XDG_CONFIG_HOME:-~/.config}/loadout` on POSIX and `%APPDATA%\loadout` on Windows. A provider with no `command` set, Paseo's default, is wrapped as its bare name, and a `claude` or `codex` with settings but no row in the host config gets a row holding just that wrapped command; `pi` settings need a `pi` row. On Windows the launcher resolves that name as Paseo does: each `PATH` directory in order (surrounding quotes removed) with the `PATHEXT` extensions, then winget package executables. It runs a `.exe` such as `claude.exe` directly. For an npm `.cmd` shim such as `codex.cmd` it runs what the shim runs, without `cmd.exe`: the shim's Node script under the shim's `node.exe`, or this Node when it has none, or the shim's `.exe`. So stdio and `app-server` work unchanged and no argument is expanded. Any other `.cmd` or `.bat` runs through `cmd.exe`, refused when an argument holds `%`, `!`, `^`, `&`, `|`, `<`, `>`, `(`, `)` or a control character. Example: `example/routed-launch-overlay.json`.
  - `tokenFiles`: env name to a file on the host, absolute or starting with `~/` or `~\` (the user's home, `%USERPROFILE%` on Windows), such as `{"ANTHROPIC_AUTH_TOKEN": "~/.config/example-router/api-key"}`. The file holds the bare value on one line and is delivered separately. On POSIX it is owned by the harness user with mode `0600`. On Windows its ACL must have inheritance off, an owner that is the current user, SYSTEM or Administrators, allow rules only for those or OWNER RIGHTS, and an allow rule for the current user, compared by SID. The launcher checks that ACL on the handle it reads the value through, opened so the file cannot be replaced, renamed or written meanwhile, and refuses a link, junction or other reparse point anywhere on the path. The sync never copies or reads the value; it checks only that the file is present and owner-only, reported per host, and a real sync fails the host otherwise. No link or junction may sit anywhere on its path. The launcher reads it into the child environment at launch time, failing closed on a missing, linked or unsafe file. The value is never written to `config.json`, `mcp-env.json`, or any client file, so it cannot go in `env`. Keep the non-secret `ANTHROPIC_BASE_URL` in `env`.
  - `args`: strings the launcher puts right after the executable, so they are global flags before any subcommand Paseo adds, such as `["-c", "model_provider=\"example_router\""]` for `codex app-server`. The host's provider command must then be the executable alone. The named provider section (`[model_providers.example_router]`) must exist in that host's `~/.codex/config.toml`, for example through `client-config.json`.
  - A host's `hosts.<name>.launch.<provider>` replaces the top-level entry for that provider; `{}` drops it. Dropping a provider's settings unwraps its command on the next sync unless fleet MCP env files still need the launcher. Without `launch` settings, Windows provider commands stay unwrapped.

To create a Windows token file, run `scripts/new_token_file.ps1` as the user the Paseo daemon runs as, under the secret runner so the value arrives in an environment variable and is never typed or printed (`ROUTER_KEY` stands for that variable):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\new_token_file.ps1 `
  -Path "$env:USERPROFILE\.config\example-router\api-key" -FromEnv ROUTER_KEY
```

It refuses an existing file and any link or junction on the path, creates the file with a protected ACL granting only the current user's SID, reads that ACL back from the open handle, and stops before writing the value, removing the empty file, if anything differs. To replace a value, delete the file first.

- `disabledProviders`: optional list of provider ids to turn off, such as `["example-retired"]`. Each listed id gets `enabled: false` in `agents.providers.<id>`, keeps its other fields, and loses its `models` key, so its picker shows none. Removing a block from `providers` alone leaves the host's old block as it was. An id may not also be in the host's effective `providers`, and `pi`, `claude` and `codex` are refused. The dry run and the result line name only the ids that run turns off (enabled or missing before); a host whose listed rows are already off names none.
- `hosts`: optional settings by host name, each for a host with the `providers` scope.
  - `disabledProviders`: replaces the top-level list for this host; `[]` disables none.
  - `launch`: per-provider launch settings layered over the default, as above.
  - `env`: per-provider values layered over the default.
  - `inherit_env`: `false` skips the default `env`, so the host keeps its own values.
  - `required_env`: per-provider variable names that must be set after the merge, or the host fails without a write.

## Pi surface on stock Paseo 0.10.3

The optional `example/pi-provider-overlay.json` illustrates the Pi fields to add to your existing provider catalog. `paseo-providers.json` may contain `pi` with `root`, `catalogSources` (normally `claude` and `codex`), `defaultSourceProvider`, and `runtime`. Hosts can override `pi`; the provider step generates Pi's `models.json` from the same provider rows on every selected host. Do not maintain a separate Pi model list. Canonical labels are Opus, Sonnet, Fable, Haiku, Astra, Sol, Luna, Web Extra, Web Pro. Use one row per label. An optional `pi.claudeApiKeyRoute` of `{"prefix": "api", "labelSuffix": "API"}` adds a second Pi entry per Claude row, labeled for example "Opus API", whose model ID is `<prefix>/<apiModelId>`. Use it when the router pins that prefix to a pay-per-use API key while plain IDs keep the subscription logins. The entry copies the Claude row's transport, context window, output limit and thinking options, so verify the key's real context window first. It applies to Pi only, never to the native Claude provider. Each entry sits directly after its base row. An optional `pi.contextWindows`, for example `{"Opus": 400000}`, sets Pi's context window per canonical label (API entries included) when the backend's effective cap is below the catalog default (1,000,000 for Claude rows, 272,000 otherwise). Pi's context meter and compaction trigger both read it; Pi compacts above the window minus `compaction.reserveTokens`, and the summary may use 80 percent of the reserve up to the model's 32,768 output tokens, so keep a reserve of at least 40,960 when summaries need that full cap. An optional `pi.labelOrder`, for example `["Fable", "Opus", "Sonnet"]`, puts those labels first in Pi only, each followed by its API entry; unlisted labels keep their catalog order and direct provider rows stay last, and new picker rows need a daemon config reload. An optional `pi.options` object becomes the generated Pi row's Paseo provider options (`agents.providers.pi.options`), for example `{"rpcTimeoutMs": 900000}` to let Pi acknowledge a prompt after a long pre-prompt compaction instead of failing at Paseo's 60-second default. Paseo validates the fields (Paseo 0.11.1 accepts `sessionDir`, `rpcTimeoutMs` and `extensionTimeoutMs`) and applies them to Pi sessions started after the reload; a running Pi agent keeps its old values until `paseo agent reload <id>` or a daemon restart. `rpcTimeoutMs` bounds every Pi RPC, so a hung Pi process also takes that long to fail. Removing `pi.options` later leaves the host's existing value in place, like other provider fields. A row may include `api` and `apiModelId` when the backend requires a different API or catalog ID than the native CLI. Copy the backend ID from its model list. For example, a native Claude catalog can retain its context suffix while the same row records the router's exact unsuffixed ID. Native routes remain available.

### Native OpenCode Zen free models

Use `example/opencode-free-overlay.json` to pin the native `opencode` picker rows: `opencode/space-bunny-free` is SBF and `opencode/muse-spark-1.3-contributor-free` is MS. Merge the overlay into the existing catalog without replacing Claude/Codex rows, changing defaults or adding `opencode` to Pi's `catalogSources`. Apply the overlay only to approved hosts; host-specific `providers.opencode` blocks can keep excluded hosts untouched. Copy IDs verbatim from the target's `paseo provider models opencode`. Free rows must have no `service_tiers`, including an empty list.

These models use OpenCode Zen directly, not a fleet router or CLIProxyAPI. Zen uses `https://opencode.ai/zen/v1/chat/completions` for SBF and `https://opencode.ai/zen/v1/responses` for MS. OpenCode resolves its existing environment, config and auth sources; API auth normally resides in `${XDG_DATA_HOME:-~/.local/share}/opencode/auth.json`, under `opencode.key`, with `type: "api"`. It uses the non-secret `public` sentinel when free anonymous access is available. No new credentials, Pi login, auth migration or security change is required for the native path. Inspect only key names and lengths.

Direct Pi is not a supported fleet path for this pair: MS rejects non-OpenCode clients with HTTP 403 `FreeTierError` ("OpenCode's free tier can only be used from within OpenCode"). Do not impersonate OpenCode or bypass that restriction with headers. The native provider remains visible in the client picker and model-browser profiles; `pi/picker-patch.py` hides only Claude/Codex and preserves OpenCode. Keep Pi as the client default, while letting the owner select OpenCode and then SBF or MS. No preference migration or bundle reapply is needed if the current patch already passes the visibility check.

Standard means ordinary native OpenCode use with no tier setting. Do not enable Codex Fast for these models. The defensive Pi routing hooks ignore an explicit Standard, Fast or Ultrafast label on these untiered IDs (no wire tier is sent and route evidence records `ignored-untiered`), omit router metadata, and fail closed when label lookup fails or the label value is invalid. This guard does not make direct MS access supported. Free availability and IP limits remain upstream-controlled. MS is a contributor tier allowing upstream training on prompts and completions; see [Zen's current terms](https://opencode.ai/docs/zen/).

**MS is for non-sensitive work only.** Keep it as an explicit picker choice: never make it a default, route agents to it automatically, or use it for any agent that handles private, client or business data. SBF has no such restriction recorded, but the same caution applies to anything sent to a free upstream tier.

After approval, back up the private fleet file and merge the native rows for each approved host. Dry-run a provider-only sync, review the generated proposal, then apply at an approved runtime boundary. Verify exact native picker IDs and labels, lack of tiers, unchanged Pi defaults and client OpenCode visibility. Avoid changing native command, environment, auth, enabled state or active agents. If runtime helpers or renderer bundles need a change, coordinate that separately. Roll back only the new host-local `agents.providers.opencode.models` field from the recorded config backup after checking for unrelated edits; restore the private fleet file as well. Never restore an entire stale config over business-controller changes.

`runtime` describes the router `route` (TOML path and key path) or `baseUrl`, existing `credential` reference, optional `credentialHeaders`, `python` (Python 3.11+), and the loopback `paseoMcp.url`. The router base URL must use https unless its host is loopback (`127.0.0.1`, `localhost`, `::1`), because the key travels as a Bearer header. Credentials resolve at request time through an existing text, env, env-file, JSON or TOML source. An optional `gmail` object (`email`, `home`, optional loopback callback `port`) adds a read-only Gmail MCP server from the `workspace-mcp` package installed in `home/venv`. `home` holds the OAuth client JSON and token, owner-only, and is never synced; on POSIX, configure refuses a group- or other-accessible `home`. Read-only is enforced three times: the server runs with `--read-only` (the `gmail.readonly` scope), write and auth tools are passed to `--disabled-tools`, and Pi hides the server except for an allowlist of read tools, which are reachable through Codemode. To use a shared Gmail server instead, remove this block and declare `mcpServers.gmail` in `client-config.json` (see Fleet MCP servers). Pi reads `mcp.json` at session start, so writing it needs no daemon reload. An optional `directProviders` object adds unauthenticated OpenAI-compatible endpoints that bypass the router, such as a local model gate: `{"<name>": {"baseUrl": "http://gate.example.test:8080/v1", "api": "openai-completions", "auth": "none", "models": [{"id", "name", "reasoning", "input", "contextWindow", "maxTokens", "cost", "thinkingLevelMap"}]}}`. Each model is listed once; it becomes a `models.json` provider with a dummy `local-no-auth` key and a picker row `<name>/<id>` labeled with its `name`, with thinking options from the non-null `thinkingLevelMap` levels (Medium preferred as default). Credentials, headers, `compat` flags, other APIs and the names `fleet`, `opencode` and `llama.cpp` are rejected. These routes have no service tier, so Fast is never offered. New picker rows need a daemon config reload. No key contents belong in this file. Generated Pi settings fix built-in Codemode on with `defaultTools: ["+codemode"]`; no profile, feature or per-agent flag enables it. Sync validates these settings and the runtime fails closed if the effective session settings or active tools lack Codemode. Session evidence records the check. The skills sync discovers the configured official Pi home from the host provider command and installs the same selected, manifest-verified skills under `agent/skills`; generated settings reference that shared directory. Global instructions sync to `agent/AGENTS.md` and are copied into each agent home at launch. No Claude-only tool is required to discover and read these skill files. The settings carry the source provider's default model and thinking. Pi exposes only its supported thinking levels; Web models retain model-fixed thinking. Native `ultra` and `ultracode` selections need an explicit native fallback because Pi 1.0 has no such selector.

Install official Pi 1.0.0 first using the reviewed `scripts/pi/apply.sh` (POSIX) or `apply.ps1` (PowerShell), with a generated per-host proposal and a fresh `--state` file. `plan`, `apply`, and `rollback` require a reachable stock daemon reporting a release version in `>=0.10.3 <0.14.0`. On Paseo 0.11 the launcher also accepts a resume that passes `--session` without `--model`, because Paseo applies the model over RPC. `--activate` reloads only that selected daemon. Apply backs up the daemon config and records, for each runtime file, its prior bytes and the hash of what apply writes there, before writing. A config change another controller makes during apply is merged into, not overwritten, and that revision is backed up and recorded instead. Rollback verifies the backup and refuses unrelated config changes. It then checks every runtime file before changing anything: each must still hold what apply found or what it wrote, as a regular file with no symlink or junction up to the runtime root, so an edit made since apply, even to a file rollback would delete, stops it. It restores runtime files atomically and verifies them, then checks again, right before restoring the daemon config, that the config is still apply's or the original revision and the backup is intact, and only then restores it and reloads. Apply and rollback stage the daemon config in an unpredictable, exclusively created temp file beside it, refuse a config that is a link, a reparse point, or not a regular file, and verify the installed config's digest. A runtime path with a symlink, or on Windows any reparse point such as a junction, is refused before anything is written. A failed partial apply can be rolled back with the same state. A state written before these per-file hashes is refused; restore its runtime by hand after checking the files. The installed package is retained for later reapply.

The provider sync needs the existing package. It generates runtime helpers and catalog together, backs up changed files, then merges provider rows. Each real agent gets a stable private `PI_CODING_AGENT_DIR` and an MCP endpoint carrying its caller ID. Stock 0.10.3 rejects official Pi through its `mcpServers` API. The interim stdio bridge exposes the daemon tools through Codemode and fills omitted child provider/model/thinking from the current parent snapshot, while preserving explicit overrides. Enable daemon MCP and injection through the reviewed apply proposal.

To change one Pi agent only, for example a context-window trial, write `models.overlay.json` or `settings.overlay.json` into `<pi root>/agents/<agent id>/`. Each launch or resume rebuilds that agent's `models.json` and `settings.json` from the shared `agent/` copies and applies the overlay on top. Only this allowlist is accepted: `models.overlay.json` is exactly `{"providers": {"<provider>": {"models": [{"id": "<model id>", "contextWindow": n, "maxTokens": n}]}}}`, and `settings.overlay.json` is exactly `{"compaction": {"enabled": true|false, "reserveTokens": n, "keepRecentTokens": n, "modelOverrides": {"<provider>/<model id>": {"reserveTokens": n, "keepRecentTokens": n}}}, "skillsExclude": ["<skill name>"]}`, where every field other than `id` is optional but each object, list and model entry needs at least one, `n` is a positive integer, and each provider, model id and `<provider>/<model id>` must already exist in the shared `models.json`. Each `skillsExclude` entry is unique and is only the name of a skill directory holding a `SKILL.md` (no paths, globs or `..`) directly under exactly one root Pi loads skills from: the shared `agent/skills`, the agent's own `agents/<agent id>/skills`, or `~/.agents/skills`, where Paseo installs its skills (`$HOME`, else the OS home, so `%USERPROFILE%\.agents\skills` on Windows). A name in none of them, or in two, is refused. Project `.pi/skills` and `.agents/skills` load only for a trusted project, which the fleet's `defaultProjectTrust: "never"` rules out in RPC mode, so they are not roots. The launcher appends Pi's exact exclusion `-<that root>/<name>` to `skills`, which removes only that skill from the agent's skill list and `/skill:` commands, for example `{"skillsExclude": ["<skill name>", "paseo-advisor"]}` to keep skills out of a PM's index while workers keep them. Any other key, JSON type, provider or model, an unreadable file or invalid JSON refuses the launch and leaves the agent's files as they were. For example, a 1M window: `{"providers": {"fleet": {"models": [{"id": "<model id>", "contextWindow": 1000000}]}}}` with `{"compaction": {"modelOverrides": {"fleet/<model id>": {"reserveTokens": 40960}}}}`. It applies at the agent's next launch or `paseo agent reload <id>`, and deleting the overlay restores the shared values the same way. The syncs never write or remove files under `agents/`, and probes and launches without a caller ignore overlays.

`isDefault` selects a model within a provider; stock 0.10.3 has no daemon-wide default provider. Web UI clients store their new-agent preference in `@paseo:create-agent-preferences`. Emit a script with `node scripts/pi/app-defaults.mjs catalogs.json`, where the input maps provider names to verbatim `list_models` results' model arrays. Run it on that client's actual origin: it carries the saved model/thinking or source catalog default, preserves native preferences, and saves rollback bytes. Add `--rollback` to emit restoration. Native clients must select Pi in their picker. This preference is client-local and can affect all connected hosts, so apply it only when those hosts support Pi. A headless host cannot set every client's storage through daemon config.

OPC resolves fixed role labels from the target Pi catalog at spawn time; missing or ambiguous labels fail clearly. OPC Workers run on Pi. An owner-selected Worker model, effort, and Fast choice wins; without one, the nine classes are `code` on `Opus` `medium` (range medium..xhigh), read-only `ui-design` and `ui-check` on fixed `Fable` `high`, read-only `plan` and `review` on fixed `Sol` `xhigh`, `browser` on `Sol` `medium` (range medium..high), `browser-hard` on `Astra` `medium` (range medium..high), `smoke` on fixed `Luna` `low`, and `watcher` on fixed `Luna` `xhigh`. The PM selects `browser-hard` and records why for escalation; raise it to high for difficult multi-app work or troubleshooting. Aliases code-bounded, test-fix, automation and mechanical resolve to code; research to plan; review-critical and review-general to review; the old `ui` name to ui-design. Fable is only for real visual design (a new screen, a layout change or a new component): one `ui-design` lane returns a spec and static mockup at a scratch path, a `code` lane on Opus builds it and opens the PR with before and after screenshots, and an optional one-pass `ui-check` returns a fix list for the code lane. Copy, labels, states, error text, renames and guards with no layout change are `code` only. Fable runs only at high with Fast off. Opus and Fable routes have Fast off. Every GPT class and fixed role has Fast on. PMs stay on Opus and delegate browser, research and scouting to GPT lanes, and UI design to `ui-design`. The fixed planner is a read-only Sol Pi lane without a web or Opus fallback; Web Pro remains only for explicitly enabled browser review. Quota may raise an adjustable route but never lowers one. A model or effort the Pi catalog does not serve stops the lane. A native Codex or Claude Code Worker, including one needed for native plan or permission modes, requires an explicit owner authorization for that task. Pi has no plan mode or permission-mode controls and its tools execute with the host user's authority. Fast is the Pi Fast toggle label `opc.service-tier` on GPT routes, and Fast is the default: with no label (or `inherit`), a GPT route whose router catalog lists the `priority` tier sends `service_tier: priority`, and route evidence records `tierStatus: fleet-default-fast`. Only an explicit `standard` (or `default`) label turns it off; the Fast toggle's Off writes it, and OPC sets `fast` for a Fast Worker and `standard` for a Fast-off GPT Worker. A route whose catalog lacks `priority` or cannot be read still sends no tier with no label (`inherited`). A tier label on a route without service tiers (an agent swapped from GPT to Claude, for example) is ignored: no tier is sent and route evidence records `ignored-untiered`. For Fast Sol workers, requested or by default, the generated router extension requests `service_tier: priority`; request acceptance does not prove priority was granted. Its private per-session evidence records the requested and reported tier, without headers or transcript contents.

## client-config.json

Optional. `python3 scripts/client_config.py [--dry-run] [--host <name>] [--update-claude]` reads it and updates hosts whose `sync` includes `client-config`. Each host gets the base settings, then its role's, then its own `hosts.<name>` overrides. It holds router URLs, so it stays in the private fleet directory.

- `token_file`: optional path, on the source host, to a secret file. Its contents go to hosts whose settings name a `claude.token_env`, over SSH stdin only. A token file inside the fleet directory stays there: the fleet push never copies it, and refuses to run while `token_file` resolves to one of the files it publishes. The token is never passed as an argument, stored in this file, or printed.
- `codex`: managed keys for Codex `config.toml`.
  - `top`: top-level keys. Missing keys are inserted before the blank lines that precede the first section header.
  - `sections`: named sections such as `model_providers.<id>`, each a map of keys. A missing section is appended.
  - `reportOnly`: top-level keys that are printed per host and never written.
  - `removeTop`: top-level keys an earlier sync managed and this one drops, such as `["model_provider"]`. Each is deleted, with its whole value, where it is set before the first table header; the changed file is backed up first, as for any change. List only keys the sync once wrote: a listed key is removed whoever set it, and keys not listed are never touched.
  - Key, section, and `reportOnly` names are bare TOML keys, optionally dotted (letters, digits, `_`, `-`); a host refuses any other name and writes nothing.
  - Values are strings, numbers, or booleans. The merge is line-based and keeps CRLF, comments, and every other key and section. It reads headers with trailing comments, array tables, quoted keys, and values that span lines (multiline strings, arrays), and replaces a managed key's whole value. Where a construct could define, shadow, or duplicate a managed key path (a top-level key, or a managed section plus one of its keys), it refuses with nothing written and reports `unsupported TOML, edit by hand`: an inline table, a dotted key, or a value spanning lines at, inside, or over a managed key path; a table header at or under a managed key path, such as `[model_providers.example.base_url]`; an array table at or over a managed section; and a key outside a managed section that defines part of it. Other keys and deeper tables in a managed section are left alone, such as an unmanaged key whose value is an inline table, or `[model_providers.example.http_headers]` under a managed `[model_providers.example]`. It also refuses a file it cannot read, and a result in which a managed key would appear more than once, outside its own table, or a table or key would be defined twice.
- `claude`: managed parts of Claude Code `~/.claude/settings.json`.
  - `settings`: top-level keys, each replaced whole.
  - `env`: keys merged into `env`.
  - `token_env`: an `env` name to fill from `token_file`, or `null`. This puts the token in the global `settings.json`, which every terminal session also reads; to route only Paseo-launched Claude, leave it unset and use `launch.claude.tokenFiles` in `paseo-providers.json`.
  - `removeEnv`: `env` names an earlier sync managed and this one drops, such as `["ANTHROPIC_BASE_URL", "ANTHROPIC_AUTH_TOKEN"]`, deleted from `env` with the usual backup. The same rule as `removeTop` applies.
  - Removal waits for the providers step. These lists drop terminal routing that Paseo's provider settings take over, so on a host with the `providers` scope a listed key goes only once the providers step has written that host's current `paseo-providers.json` settings and reloaded its daemon, with no reload owed or in flight since; a failed reload never counts, even when the config was already current. That is recorded on the source host in `provider-activations.json` beside `provider-reloads.json`. Until then the keys stay, the host reports `routing removal HELD` with the reason, its cell reads `held`, and the run exits 1; run the providers step for the host, then client-config again. The check applies to every run, including `--only client-config`. A host without the `providers` scope removes them at once.
  - Removal lists from the base, role and host layers add up. A name that the same host also manages (`codex.top`, `claude.env` or `token_env`) is refused.
  - `minVersion`: base only. Hosts below it are reported, and `--update-claude` runs `claude update` on them. Versions compare like `sort -V`.
- `roles.local`, `roles.remote`: layers with `codex` (`top`, `sections`, `removeTop`) and `claude` (`settings`, `env`, `token_env`, `removeEnv`). The source host is `local` and every other host `remote`.
- `hosts.<name>`: the same layer for one host, plus an optional `role` that overrides the default.

Only these keys are written. Everything else stays host-local. A missing client is skipped. Each changed file is backed up in place as `<file>.bak-loadout-<stamp>-<random>`, a new file that never overwrites an earlier backup, holding exactly the bytes the merge read. The write is an optimistic check: the result goes to an exclusive temp file, which is fsynced, then the file is read again and the temp renamed over it at once only if it still holds the bytes the merge read. If anyone else changed it, the temp and backup are removed and the read and merge run once more, merging onto the new revision; a second change fails the host and leaves the file as is. This narrows the window for a lost concurrent edit to the moment between that re-read and the rename, but cannot close it, because the daemon and editors take no lock. A second run reports `unchanged`.


### Fleet MCP servers

`client-config.json` accepts `mcpServers`, an object keyed by server name. Declare each Streamable HTTP endpoint once, for example (all addresses and host names here are made up):

```json
{
  "mcpServers": {
    "ebay-analyze": {
      "url": "http://192.0.2.40:8766/mcp",
      "bearerTokenEnvVar": "EBAY_ANALYZE_MCP_TOKEN",
      "envFile": "~/.config/ebay-analyze-mcp/mcp.env",
      "hosts": { "laptop": true, "desktop": true }
    },
    "gmail": {
      "url": "http://192.0.2.10:8770/mcp",
      "bearerTokenEnvVar": "GMAIL_MCP_TOKEN",
      "hosts": { "laptop": { "url": "http://127.0.0.1:8770/mcp" }, "desktop": true }
    }
  }
}
```

- `url`: HTTP or HTTPS Streamable HTTP endpoint, without embedded credentials, query or fragment. Prefer HTTPS; use HTTP only on a trusted private network. If the server allowlists `Host`, use its allowed IP, not a DNS alias.
- `bearerTokenEnvVar`: uppercase environment variable name, never a token value.
- `envFile`: optional POSIX path, absolute or starting with `~/`; defaults to `~/.config/<server>/mcp.env`. The file is delivered separately, owned by the harness user, mode `0600`, with one literal `VAR=value` line. No shell expansion, quoting or `export` prefix. The sync never copies, sources, prints or puts its contents into client or daemon config. The launch wrapper reads it into the child process environment only, failing closed on missing, linked, unsafe or empty files. `envFile` is ignored on Windows, where the separately delivered user environment variable is used. A Windows daemon started before delivery must be restarted, not merely config-reloaded, to inherit it.
- `hosts`: explicit `hosts.json` names mapped to `true`, `false` or `{"url": "<http(s) url>"}`. The object form enables the server on that host with its own URL instead of the top-level `url`, validated the same way; use it on the host that runs the server itself, which reaches it over loopback. Missing hosts are untouched. All named hosts need `client-config`; POSIX hosts also need `providers` for launch wiring. `false` disables the Codex and Pi entry, removes only that named Claude user entry, and stops loading that server's env file. Set `false` before retiring a previously enabled host; deleting the declaration alone does not retire its prior config.
- Names allow letters, digits, `_` and `-`, must be unique case-insensitively and with `-`/`_` treated alike, and cannot be `paseo`. `gmail` is allowed only while no host listed under it, even as `false`, still has the read-only Pi `gmail` block in its effective `paseo-providers.json` `pi.runtime`; validation names any such host. To move a host from the Pi block to the shared server, remove its Pi block and list the host here in the same change; the next providers sync regenerates Pi `agent/mcp.json` without the old local server, and each new Pi session copies that file. Do not also manage the same Codex table through `codex.sections` or the same Pi server through `pi.runtime`.

`example/mcp-servers-overlay.json` shows the `mcpServers` block to merge into `client-config.json` for a shared `gmail` server: the source host `laptop` runs it and uses the loopback URL, `desktop` uses the top-level URL, and neither host keeps a Pi `gmail` block.

The providers step writes the non-secret `loadout/mcp-env.cjs` launcher and the `mcp-env.json` descriptor (`{"servers": [...], "providers": {...}}`, the latter holding the `launch` settings) under the host config directory. It wraps the existing enabled Codex, Claude Code and Pi provider commands without changing their arguments, models, other environment keys or agent routes. The existing provider reload and reload-owed mechanism applies. The wrapper loads credentials after the daemon starts, so POSIX needs no daemon restart just to pick up a token rotation. Only enabled server env files are loaded. Windows provider commands remain unchanged unless `launch` settings wrap them. The generated Pi `agent/mcp.json` gets native HTTP entries with Codemode exposure; the scoped loopback Paseo stdio bridge and read-only Gmail configuration are unchanged, not repurposed as generic HTTP proxies.

The client-config step merges:

- Codex `config.toml`: `[mcp_servers.<name>]` with `url`, `bearer_token_env_var` and `enabled`.
- Claude Code user-scope `~/.claude.json` (`$CLAUDE_CONFIG_DIR/.claude.json` with a custom config directory): `mcpServers.<name>` with `type: "http"`, `url`, and `headers.Authorization: "Bearer ${VAR}"`. This is personal, cross-project user configuration, not project trust or machine-wide policy. `managed-mcp.json` would impose exclusive system-managed servers and displace users' own servers, so the sync deliberately does not use it. Other user servers and all unrelated user state are preserved.
- The configured official Pi home's `agent/mcp.json`: `url`, the same unresolved Authorization header, `enabled` and `exposure: "codemode"`. It discovers that home from the daemon's Pi launch command. A missing client is reported as absent, not installed.

Changed client files retain the normal unique backup and optimistic replacement protection. JSON headers and TOML contain the variable name only. The provider dry run reports each URL, credential variable, env-file presence/permissions (without reading its contents), or Windows user-env length, and any wrapper files it would write. It never connects to an MCP endpoint or runs a search. For a complete proposal, run `python3 scripts/sync.py --dry-run --only providers,client-config` against the private fleet, inspect every host, then wait for rollout approval. Pi loads the new entries when a new session starts or after `/reload`; existing sessions are not rewritten.

For a standalone POSIX harness outside Paseo, use the generated loader, for example `node "${XDG_CONFIG_HOME:-$HOME/.config}/loadout/mcp-env.cjs" -- codex` (substitute `claude`, or the official Pi launch command). A raw CLI invocation bypasses the wrapper and must otherwise inherit `VAR`; the sync does not edit shell startup files, global launch services or credential stores. On Windows, start a new terminal/harness after user-env delivery. Connection smoke checks should call `tools/list` only, never perform a marketplace search as a sync verification.

### Desktop picker defaults and update guard

Generate `client-preferences.js` with `pi/app-defaults.mjs` from the same catalog rows used for the host. Pass it to `picker-patch.py APP_DIST apply --preferences-script client-preferences.js`. The patch state records the script's sha256 and refuses a later apply or reapply with a different script; after reviewing a regenerated script, accept it with `--preferences-sha256 HASH` (the refusal prints the hash). The renderer carries the previous provider's catalog label and thinking onto Pi before loading saved form preferences. It keeps a localStorage backup for the rollback script emitted by `app-defaults.mjs --rollback`. Bundle rollback restores the exact original bytes; preference rollback must run in each affected client origin. The patch state, the bundle, the entry, and the backups are each replaced atomically, the old state staying until the new one is on disk, and the state remembers earlier patch generations of the same original bytes. So a write cut off partway leaves every file holding bytes the state accounts for, and check, reapply, and rollback still work; bytes it does not recognize remain a client update and are never overwritten.

On Windows, point the existing Desktop shortcut to `picker-launch.ps1 -PreferencesScript SCRIPT` (add `-AppRoot APP_ROOT` when more than one install exists). It reapplies the supported picker patch before launch after an app update. If the reapply fails, for example because a per-machine install under Program Files is not writable without elevation, or the bundle shape is unsupported, it logs a warning to `%LOCALAPPDATA%\loadout\picker-launch.log` and still launches the unpatched client; run the logged reapply command from an elevated PowerShell afterwards. That command calls Python by the absolute path the guard resolved unelevated, not through PATH. Back up the shortcut before changing it and restore it on rollback. The app updater's immediate internal restart can bypass an OS shortcut; rerun this launch guard after that restart. Do not change daemon availability or native-agent settings to hide providers.

### Provider catalog without a runtime install

A providers-only host can set its host `pi` descriptor to `{"catalogOnly": true}`. This derives Pi's models from the same catalog sources, but emits only the `models` field. It preserves local command, availability and environment, and writes no Pi agent home or binary. Before syncing an older daemon, validate the generated rows with that version's schema, back up its config, and exercise a guarded provider-only rollback. This does not activate Pi on a host where it is unavailable.
