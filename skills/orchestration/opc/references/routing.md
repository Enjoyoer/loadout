# Worker routing

## Resolve

An owner-named model, effort, or Fast wins and is never adjusted. An owner-named model or a burn route holds only for that task or burn. When it ends, launch new workers on the OPC default route. Pi has Fast on GPT routes: `--owner-fast on` records it, and the Worker builder sets the `opc.service-tier` label that the composer's Fast pill shows. On Pi, Fast is the agent label `opc.service-tier=fast`, not a catalog model or thinking level, so the model catalog never lists it; outside the builder set it with `labels:{"opc.service-tier":"fast"}` on `create_agent` or `update_agent`, or on the CLI with `paseo run --label opc.service-tier=fast` or `paseo agent update <id> --label opc.service-tier=fast`, and read it back with `get_agent_status`. A Pi GPT route with no label runs Standard (no label means Fast off), except Luna: the Pi router sends Fast on every Luna turn whatever the label says (owner 2026-11-17); the builder still writes an explicit `opc.service-tier=standard` for a Fast-off GPT route. pi-fast-toggle applies the same label. Verify the label (`get_agent_status` or the Fast pill) before reporting a route. Never report Fast as unavailable on Pi, and never skip the builder with a raw `create_agent` for a Worker. Otherwise pick the task class below and resolve it with `resolveWorkerRoute` from `scripts/route.mjs`, or from a shell:

`node scripts/route.mjs --class <class|main-pm|opn-browser> [--task TASK_JSON --lane SLUG]`

It prints one human summary line to `stderr` and one JSON object to `stdout`: `{route, reason, provider, model, effort, fast, host, nextFallback, proofRequired}` (plus `fallbackChain` for `main-pm`). Bare `--class` applies the fresh trusted forcing switch, live Mac skip holds, and read-only parity peek without creating files or consuming turns; it separates policy selection (`proofRequired: true`) from exact target/workspace proof. Every fresh class-default or UI-class launch, brief, and record (`recordWorkerRoute`, `buildManagedWorkerRequest`, `buildInPlaceWorkerRequest`, `buildDelegatedBrief`, bound or unbound) requires a live route from `resolveWorkerRoute` in the same process, at most 60 seconds old, resolved for that exact task and lane (pass `task` and `lane` to `resolveWorkerRoute`), and only while the live Mac policy it read (switch, `devin-ready.json`, `agy-quota.json`, model holds, local daemon) is unchanged; pasted, cloned, remembered, other-lane, and stale routes are refused, an owner-named route is the owner's own, and missing/stale proof for an admitted agy selection fails closed without inventing Sol or silently substituting Opus. Add `--owner-model ID --owner-effort LEVEL [--owner-fast on|off]` for an owner-named route and `--catalog FILE` for saved Pi catalog rows (default: `paseo provider models pi --json`). With `--task` and `--lane` it records `{route, reason}` in the task's `routes` and returns an already recorded lane unchanged, so repairs and resumes keep their route; for a recorded lane it refuses `--class`, `--owner-model`, `--owner-effort`, or `--owner-fast` that would select another route, so resume it with no route flags or with the ones that selected it. A new route is checked against the class table once, when it is recorded; later reads check only its shape, so a later class change never strands a task. Pass `route` unchanged to `buildManagedWorkerRequest` and `reason` to `buildDelegatedBrief`. Give both builders the destination task as `task: readTask(taskPath)`, the lane (`buildDelegatedBrief` takes `lane` too; `buildManagedWorkerRequest` refuses a `taskId` other than the record's id), and the lane's class as `taskClass` (a UI task's lanes are `ui-design`, the default, or `ui-check`); pass the same `taskClass` when recording, and the Pi catalog rows as `catalog` to `buildDelegatedBrief` and `recordWorkerRoute` where you have them. With a task, an explicit `provider` is checked after the route and must be exactly the provider the validated route maps to, with its settings. Task records are bookkeeping, not routing authority: the source a route records grants nothing. Every route, recorded or fresh, keeps the owner's hard rules for its lane's class: `code` and its aliases never run a GPT or web model, `ui-design` and `ui-check` are exactly Fable high, Fast off (without a catalog the model id must name Fable), Fable never runs at another level in any lane, `smoke`, `sites` and a `watcher` route on Luna never run Fast off, and no route runs below its class minimum. Inside them an owner-named route keeps its model and effort. A task default runs its class's own model: with a catalog exactly the class's row, without one a model id that names the class's label. A lane with a recorded route takes only that route, on the request, brief, and recording paths. It rebuilds (repair, restart) as long as it still fits; a task default must also be the class's catalog label with the class's Fast (a GPT class lane keeps the Fast it was recorded with: Fast on from before Fast went off by default, or Fast off from before decision 327; a `review-security` Sol default only ever ran Fast on, so one recorded with Fast off is refused), at any effort from the class minimum up to its ceiling (code high..xhigh, so an earlier Opus xhigh lane rebuilds; a recorded Opus medium lane is below the minimum and stops, so start a new lane), which the Pi catalog must still serve. A `watcher` lane recorded as the former default Luna xhigh, Fast on, before watchers moved to Sol, still rebuilds on that route; a new `watcher` task default takes Sol low. A `review-security` lane recorded before decision 332, as the former default Opus high or Opus xhigh, Fast off, or as an owner-named non-GPT route at high or above (Opus, Sonnet, or Fable high, Fast off), still rebuilds on that route, and `route.mjs` replays it with the exact flags that recorded it (class or alias included); a new `review-security` task default takes Sol xhigh, Fast on, and a new owner-named `review-security` route, resolved alone or recorded, needs at least xhigh. A fresh lane's route is checked as new against today's table and its class. Kinds outside the table go to the owner.

Other Sol routes, Astra and Fable stay Fast off. PMs stay on Opus and delegate all browser, computer-use and scouting work to these GPT lanes, research to the `research` lane and planning to the `plan` lane, never doing it themselves; UI design goes to `ui-design` under the UI rule below. Default review uses `review` as a read-only Pi lane on the exact PR head, with [Simplifier remit](simplifier-review.md "runtime") as its brief. Pick `review-security` instead for a diff touching auth, secrets or credentials, permissions or sandboxing, firewall or network exposure, backups, or deletion and archive paths: a read-only Pi lane on Sol xhigh, Fast on (owner decision 332), escalated only as [below](#security-review-escalation "runtime"); its brief asks for a correctness review, and the builder prefixes that wording. Fast means Pi's Fast toggle on Pi GPT routes; native Codex browser lanes set `settings.features.fast_mode` from the route (true by default since decision 327) and an explicit unattended `settings.modeId`. A lane keeps the Fast it was recorded with through repairs and resumes: Fast on from before the Fast-off default, Fast off from before decision 327.

### Research

Owner item 111. A fresh `research` lane resolves to Pi `fleet/gpt-6.1-terra` (the catalog's Terra row), thinking high, Fast off (`node scripts/route.mjs --class research --task T --lane L`); the builder writes `opc.service-tier=standard`. It is read-only like `plan`: `buildDelegatedBrief` prefixes the read-only line and tells the Worker to return findings with sources and to ask Fable through `$ask-fable` (`python3 ~/.local/bin/fable-ask <question-file>`) for a judgment call, so Fable answers one question and never runs the lane. Work that writes files, builds, or changes a live system is never `research`; it is `code`. An owner-named route for `research` wins inside the hard rules above, so an owner-named Fable runs only at high with Fast off.

Until this split `research` was an alias of `plan`, so a research lane recorded before it carries `kind: plan` and the `plan` reason. It resumes and rebuilds as a `plan` lane, unchanged: `route.mjs --task T --lane L` with no route flags, or with `--class plan`, returns its recorded route, and the builders take `taskClass: 'plan'` for it. `--class research` on that lane exits non-zero (`would not select`), because `research` now selects another class; it never migrates the record. Only a fresh lane takes the Terra route.

### Security review escalation

Owner decision 332. A fresh `review-security` lane, alias `security` included, resolves to Pi `fleet/gpt-6.2-sol`, thinking xhigh, Fast on (`node scripts/route.mjs --class review-security --task T --lane L`); the builder sets `opc.service-tier=fast`, so check that label with `get_agent_status` before reporting the route. Only one security reviewer runs at a time, never two in parallel.

PM trigger: the Sol lane has ended in a terminal failure (a launch failure, a provider refusal, a rate limit or quota stop, or a failure that a continue follow-up under [Errors](#errors "runtime") did not clear), or it has returned a blocker verdict. Only then, after the Sol lane is terminal, may the PM start one separate read-only lane on Opus xhigh, Fast off, on the same exact head, with the same correctness brief, as a new lane named `security-escalation` (a later candidate in the same task takes `security-escalation-2`, then `-3`; lane slugs stay at most 40 characters) through the explicit escalation command:

`node scripts/route.mjs --class review-security --owner-model fleet/claude-opus-5-5 --owner-effort xhigh --owner-fast off --task T --lane security-escalation`

Decision 332 already authorizes this escalation after a terminal Sol failure or a Sol blocker verdict, so the PM runs it without asking the owner again; it records as an owner-named route, and nothing starts it on its own. A failed review, Sol or Opus, is never approval. The escalation lane does not clear a Sol blocker: every blocker stays open until it is fixed and passes the fix check under [review rule R1](web-reviewer.md#review-rules "branch:review"). If the Opus lane also fails, stop and report NOT APPROVED to the owner.

### OPN browser workers

Named `browser` exception (owner 2026-11-17, a recorded task-type exception, so the owner does not have to name the model): a fresh PM-started OPN browser worker, started in the PM's own workspace so it shares the Paseo browser and its signed-in tabs, resolves deterministically through `node scripts/route.mjs --class opn-browser` to native Codex `codex/gpt-6.2-sol`, thinking low, Fast on (owner decision 412a, 2026-11-27; replaces the Pi route of decision 327). Native Codex gets the Paseo MCP browser tools from its runtime Paseo MCP server. The resolver reads the native Codex catalog (`paseo provider models codex --json`; `--catalog FILE` and `resolveWorkerRoute`'s `catalog` hold those rows), and a Pi row such as `fleet/gpt-6.2-sol` never authorizes the lane. Pass the native Codex `inspect_provider` result, with its `list_models` rows as `models`, as `capabilities` to `buildInPlaceWorkerRequest` with `taskClass: 'opn-browser'`; both must serve exactly one unprefixed `gpt-6.2-sol` at low thinking, and the request runs the native Codex `full-access` mode, which must be advertised exactly once (stock Paseo may leave it unflagged) with no other unattended mode. The resolved route keeps its own class: with an omitted or other `taskClass` the in-place builder refuses it, and `recordWorkerRoute` and `buildManagedWorkerRequest` refuse it for any class. No caller override changes it: `--owner-model`, `--owner-effort`, `--owner-fast`, an `ownerRoute`, a different `provider` or `agentSettings`, a surface or native authorization, a remote target, or any workspace or placement key is refused, and `opn-browser` is never recorded as a lane. Native Codex `browser` and `browser-hard`, recorded lanes, and the `code` rules are unchanged, and no `code` GPT route is admitted.

## PMs

This file is the one model map for OPC and OPN. Every PM, main and child, runs on Opus high (Pi `fleet/claude-opus-5-5`, thinking high; owner 2026-11-18), unless the owner names another model for it. `node scripts/route.mjs --class main-pm` exposes the read-only `main-pm` policy ladder for the three main PMs (Config, Work, Personal): default Claude Opus high even off pace, then only Neon High or Opus High (owner 404b correction, 2026-11-25): native `agy-opc/gemini-4-neon-high` -> Cursor `cursor/gemini-4-neon` -> `agy-opc/claude-opus-5-5-high`, applying live Mac skip holds and Config's `agy-quota.json` projection to the agy steps without touching triggers, sessions, or CPA. Sol is never a main-PM fallback. Project PM and Worker routing do not change. Exactly two named starts fall back to Sol high (`pi/fleet/gpt-6.2-sol`, thinking high), only when Opus high is missing from the catalog, fails to start, or returns a quota error: the fresh PM that `unstuck` starts, and an OPN worker on the `code` class. OPC `code` lanes never take that fallback: they stop and report to their PM. A `review-security` lane that fails follows [Security review escalation](#security-review-escalation "runtime"). A PM's own model never passes to its lanes or workers; each takes its live resolved class route.

## Fable

Fable runs on the OPC `plan`, `ui-design` and `ui-check` lanes, or wherever the owner names it. A `research` lane runs on Terra and asks Fable only through `$ask-fable`, which starts no Fable agent. Implementers and reviewers use Opus or Sol, and no lane inherits Fable from its PM. At most 5 Fable agents run at once across the fleet, PMs and `plan` lanes included; before starting one, count the running Fable agents on every host. When the owner names Fable for a code lane, `buildDelegatedBrief` starts its brief with an ownership line (the owner and long-term maintainer of the codebase, its design up to it within the brief's permitted changes), per Anthropic's Fable 5.2 prompting guidance.

## UI work

Fable designs and checks; Opus builds. In UI work, Fable is only for real visual design: a new screen, a layout change, or a new component. Copy, labels, states, error text, renames, and guards with no layout change are `code` only, with no Fable lane.

1. `ui-design` (Fable high, Fast off, read-only) takes the current screens, as screenshots and code, and returns a short design spec plus a static mockup (HTML/CSS or images) at a scratch path the PM names. It makes no repository edits and opens no PR. At most one per task; a second needs the owner's OK.
2. A normal `code` lane (Opus high) builds: it implements the spec and mockup exactly, plus the logic, and opens the PR with [before and after screenshots](pr-evidence.md "branch:evidence").
3. `ui-check` (Fable high, Fast off, read-only) is optional and runs one pass: it compares the after-screenshots to the mockup and returns a fix list. The code lane applies the fixes.

The `ui-design` and `ui-check` lanes run in a UI task (the Fable `plan` lane does not), created with `createTask({..., ui: true})`; pass `ui: true` to `selectTopology`. Its lanes take only `ui-design` (the default when no `taskClass` is given) or `ui-check`, and the build runs in a separate normal `code` task. On pace (and whenever `antigravityFallback` is not forced on), both classes resolve to owner-explicit routes with reasons `ui-design: owner rule, Fable high, no GPT, read-only` and `ui-check: owner rule, Fable high, no GPT, read-only`; `buildDelegatedBrief` marks them read-only. UI work never uses a GPT or web model: no Sol, Luna, or Astra Worker, no Sol scouts, and no web reviewer in `ui-design` or `ui-check`. The one narrow exception is when trusted `antigravityFallback` is forced on (decision 366a): a new default (non-owner-named) `ui-design` or `ui-check` lane may record and launch on the exact [Antigravity replacement](#antigravity-replacement "runtime") or, only with positive fresh unavailable evidence on the local Mac target, the exact Sol medium off-pace backup, still read-only. The UI task still refuses browser review and scouts, `recordWorkerRoute` and the Worker builders given the task still refuse any other class and any non-off-pace route other than Fable high, Fast off, with a Fable model id. An explicit owner-named route (`ownerRoute`) is never replaced even while off pace, and an owner-named route for `ui-design` or `ui-check` other than Fable high, Fast off is still refused, so ask the owner to use the class instead. The old `ui` class name is an alias of `ui-design`.

## Cursor overflow

Owner rule (2026-11-21). Cursor's small monthly Other Models pool is overflow only, so it is never spent on work native Antigravity covers.

Cursor runs only on the configured Cursor host entry: in the private `~/.config/opc/neon-remote-targets.json`, the one target entry that adds `"cursorOverflow": true` to its `endpoint`, `platform` and `state`. That entry must also be `armed` with platform `linux`. No such entry, more than one, or one that is not armed linux means no Cursor host, and every Cursor lane fails closed. Host names live only in that file.

- The default overflow model is provider `cursor` with model `gemini-4-neon`. Use it only when native Antigravity is capped or unavailable.
- Use `cursor` with `claude-opus-5-5` only for a task that strictly requires Claude (a `code` or review Worker that must stay on Claude) while the Claude pool is at its cap.
- Always pass `--model` explicitly and keep the defaults: 300k context, Fast off, no 1M or Max mode. Never fall back to `Auto` for Claude-only work.
- Before starting either, check that the Other Models pool has room on `cursor.com/dashboard/spending`. If it is spent, wait for the Claude or Antigravity reset instead.
- Give each Cursor Worker one bounded task, label it `lane=cursor-overflow`, and archive it when done. Afterwards, restore the `~/.cursor/cli-config.json` model to `default` if it changed.
- If a create fails in under 2 seconds with `Authentication required`, refresh the `cursor` provider snapshot and retry once. Never run `cursor-agent login`.
- As Worker overflow, never use Cursor for a PM's own model (a main PM's only Cursor step is its [`main-pm` chain](#pms)), for Fable (no zero data retention), for a main lane, or for a payment-data project.
- Never turn on on-demand spending, and never accept a plan switch or a unify offer. A reply saying "Upgrade your plan to continue" means stop; do not retry.

## Settings

OPC routing reads one optional key of `~/.config/opc/routing.json`, `antigravityFallback`, and only for the off-pace and [code parity](#code-parity "runtime") routes below; its `pq` key and every other key belong to other readers and are never read or rewritten.

### Antigravity replacement

Settled precedence (owner decisions 314a, 390a, 393a, 397c, 398a, 399a):

Never emit `retry_at` or raw quota values; never access credentials or CPA; missing, stale, unsafe, or unready fails closed.
2. **Off-pace `code` ladder (393a/398a/399a)**: when Devin is not ready and trusted `antigravityFallback` is forced on (both booleans true), a new default `code` lane (aliases included) runs in strict order:

## Errors

Network and proxy errors, such as `Connection error` or a 502 `backend unavailable`, are retried on the same route by sending the same Worker a continue follow-up. They never change the model or effort. Rate limits, unavailable capabilities, and real launch failures still stop the lane; substitution requires a new explicit owner decision.
