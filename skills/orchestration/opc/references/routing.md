# Worker routing

## Resolve

An owner-named model, effort, or Fast wins and is never adjusted. An owner-named model or a burn route holds only for that task or burn. When it ends, launch new workers on the OPC default route. Pi has Fast on GPT routes: `--owner-fast on` records it, and the Worker builder sets the `opc.service-tier` label that the composer's Fast pill shows. On Pi, Fast is the agent label `opc.service-tier=fast`, not a catalog model or thinking level, so the model catalog never lists it; outside the builder set it with `labels:{"opc.service-tier":"fast"}` on `create_agent` or `update_agent`, or on the CLI with `paseo run --label opc.service-tier=fast` or `paseo agent update <id> --label opc.service-tier=fast`, and read it back with `get_agent_status`. A Pi GPT route with no label runs Standard (no label means Fast off), except Luna: the Pi router sends Fast on every Luna turn whatever the label says (owner 2026-11-17); the builder still writes an explicit `opc.service-tier=standard` for a Fast-off GPT route. pi-fast-toggle applies the same label. Verify the label (`get_agent_status` or the Fast pill) before reporting a route. Never report Fast as unavailable on Pi, and never skip the builder with a raw `create_agent` for a Worker. Otherwise pick the task class below and resolve it with `resolveWorkerRoute` from `scripts/route.mjs`, or from a shell:

`node scripts/route.mjs --class <class> [--task TASK_JSON --lane SLUG]`

It prints one JSON object, `{route, reason}` (also `provider` for browser defaults). Add `--owner-model ID --owner-effort LEVEL [--owner-fast on|off]` for an owner-named route and `--catalog FILE` for saved Pi catalog rows (default: `paseo provider models pi --json`). With `--task` and `--lane` it records `{route, reason}` in the task's `routes` and returns an already recorded lane unchanged, so repairs and resumes keep their route; for a recorded lane it refuses `--class`, `--owner-model`, `--owner-effort`, or `--owner-fast` that would select another route, so resume it with no route flags or with the ones that selected it. A new route is checked against the class table once, when it is recorded; later reads check only its shape, so a later class change never strands a task. Pass `route` unchanged to `buildManagedWorkerRequest` and `reason` to `buildDelegatedBrief`. Give both builders the destination task as `task: readTask(taskPath)`, the lane (`buildDelegatedBrief` takes `lane` too; `buildManagedWorkerRequest` refuses a `taskId` other than the record's id), and the lane's class as `taskClass` (a UI task's lanes are `ui-design`, the default, or `ui-check`); pass the same `taskClass` when recording, and the Pi catalog rows as `catalog` to `buildDelegatedBrief` and `recordWorkerRoute` where you have them. With a task, an explicit `provider` is checked after the route and must be exactly the provider the validated route maps to, with its settings. Task records are bookkeeping, not routing authority: the source a route records grants nothing. Every route, recorded or fresh, keeps the owner's hard rules for its lane's class: `code` and its aliases never run a GPT or web model, `ui-design` and `ui-check` are exactly Fable high, Fast off (without a catalog the model id must name Fable), Fable never runs at another level in any lane, `smoke`, `sites` and a `watcher` route on Luna never run Fast off, and no route runs below its class minimum. Inside them an owner-named route keeps its model and effort. A task default runs its class's own model: with a catalog exactly the class's row, without one a model id that names the class's label. A lane with a recorded route takes only that route, on the request, brief, and recording paths. It rebuilds (repair, restart) as long as it still fits; a task default must also be the class's catalog label with the class's Fast (a GPT class lane keeps the Fast it was recorded with: Fast on from before Fast went off by default, or Fast off from before decision 327; a `review-security` Sol default only ever ran Fast on, so one recorded with Fast off is refused), at any effort from the class minimum up to its ceiling (code high..xhigh, so an earlier Opus xhigh lane rebuilds; a recorded Opus medium lane is below the minimum and stops, so start a new lane), which the Pi catalog must still serve. A `watcher` lane recorded as the former default Luna xhigh, Fast on, before watchers moved to Sol, still rebuilds on that route; a new `watcher` task default takes Sol low. A `review-security` lane recorded before decision 332, as the former default Opus high or Opus xhigh, Fast off, or as an owner-named non-GPT route at high or above (Opus, Sonnet, or Fable high, Fast off), still rebuilds on that route, and `route.mjs` replays it with the exact flags that recorded it (class or alias included); a new `review-security` task default takes Sol xhigh, Fast on, and a new owner-named `review-security` route, resolved alone or recorded, needs at least xhigh. A fresh lane's route is checked as new against today's table and its class. Kinds outside the table go to the owner.

Local code lanes default to Opus high, `plan`, `ui-design` and `ui-check` run Fable high everywhere, and `research` runs Terra high. `code` and its aliases never run on a GPT model, and an owner-named GPT or web route for them is refused; the one exception is the recorded [off-pace backup](#antigravity-replacement "runtime") of a `code` lane. Planning and root cause use the read-only `plan` Worker class on Fable high, Fast off (owner 2026-11-18), and research and investigation the read-only `research` class; Opus implements the returned plan. A `plan` lane recorded as the former default Sol high, Fast off, still rebuilds on that route. The `scout` fixed role uses its row above. Unlike the Luna classes, these refuse nothing: an owner-named route with `--owner-fast off` stays allowed. `watcher` runs Sol low, Fast off (owner 2026-11-18), but a `watcher` route on Luna still runs Fast on. A `smoke` or `sites` route, or a `watcher` route on Luna, with Fast off is refused, so an owner-named route for them needs `--owner-fast on`; the Pi router sends Fast on every Luna turn in any lane. Other Sol routes, Astra and Fable stay Fast off. Fable always runs at high with Fast off; Fast on another Sol route or Astra is an owner-named exception for one task, such as the owner's 3D work on Astra: record it with `--owner-fast on`. PMs stay on Opus and delegate all browser, computer-use and scouting work to these GPT lanes, research to the `research` lane and planning to the `plan` lane, never doing it themselves; UI design goes to `ui-design` under the UI rule below. Default review uses `review` as a read-only Pi lane on the exact PR head, with [Simplifier remit](simplifier-review.md "runtime") as its brief. Pick `review-security` instead for a diff touching auth, secrets or credentials, permissions or sandboxing, firewall or network exposure, backups, or deletion and archive paths: a read-only Pi lane on Sol xhigh, Fast on (owner decision 332), escalated only as [below](#security-review-escalation "runtime"); its brief asks for a correctness review, and the builder prefixes that wording. Fast means Pi's Fast toggle on Pi GPT routes; native Codex browser lanes set `settings.features.fast_mode` from the route (true by default since decision 327) and an explicit unattended `settings.modeId`. A lane keeps the Fast it was recorded with through repairs and resumes: Fast on from before the Fast-off default, Fast off from before decision 327.

### Research

Owner item 111. A fresh `research` lane resolves to Pi `fleet/gpt-6.1-terra` (the catalog's Terra row), thinking high, Fast off (`node scripts/route.mjs --class research --task T --lane L`); the builder writes `opc.service-tier=standard`. It is read-only like `plan`: `buildDelegatedBrief` prefixes the read-only line and tells the Worker to return findings with sources and to ask Fable through `$ask-fable` (`python3 ~/.local/bin/fable-ask <question-file>`) for a judgment call, so Fable answers one question and never runs the lane. Work that writes files, builds, or changes a live system is never `research`; it is `code`. An owner-named route for `research` wins inside the hard rules above, so an owner-named Fable runs only at high with Fast off.

Until this split `research` was an alias of `plan`, so a research lane recorded before it carries `kind: plan` and the `plan` reason. It resumes and rebuilds as a `plan` lane, unchanged: `route.mjs --task T --lane L` with no route flags, or with `--class plan`, returns its recorded route, and the builders take `taskClass: 'plan'` for it. `--class research` on that lane exits non-zero (`would not select`), because `research` now selects another class; it never migrates the record. Only a fresh lane takes the Terra route.

### Security review escalation

Owner decision 332. A fresh `review-security` lane, alias `security` included, resolves to Pi `fleet/gpt-6.2-sol`, thinking xhigh, Fast on (`node scripts/route.mjs --class review-security --task T --lane L`); the builder sets `opc.service-tier=fast`, so check that label with `get_agent_status` before reporting the route. Only one security reviewer runs at a time, never two in parallel.

PM trigger: the Sol lane has ended in a terminal failure (a launch failure, a provider refusal, a rate limit or quota stop, or a failure that a continue follow-up under [Errors](#errors "runtime") did not clear), or it has returned a blocker verdict. Only then, after the Sol lane is terminal, may the PM start one separate read-only lane on Opus xhigh, Fast off, on the same exact head, with the same correctness brief, as a new lane named `security-escalation` (a later candidate in the same task takes `security-escalation-2`, then `-3`; lane slugs stay at most 40 characters) through the explicit escalation command:

`node scripts/route.mjs --class review-security --owner-model fleet/claude-opus-5-5 --owner-effort xhigh --owner-fast off --task T --lane security-escalation`

Decision 332 already authorizes this escalation after a terminal Sol failure or a Sol blocker verdict, so the PM runs it without asking the owner again; it records as an owner-named route, and nothing starts it on its own. A failed review, Sol or Opus, is never approval. The escalation lane does not clear a Sol blocker: every blocker stays open until it is fixed and passes the fix check under [review rule R1](web-reviewer.md#review-rules "branch:review"). If the Opus lane also fails, stop and report NOT APPROVED to the owner.

### OPN browser workers

Named `browser` exception (owner 2026-11-17, a recorded task-type exception, so the owner does not have to name the model): an OPN browser worker, started in the PM's own workspace so it shares the Paseo browser and its signed-in tabs, runs on Pi `fleet/gpt-6.2-sol`, thinking low, Fast on (owner decision 327, 2026-11-22), not on the native Codex `browser` route. `route.mjs` does not resolve this exception; start the worker on exactly this route.

## Web reviewer

The `reviewer` fixed role is separate: it is the one ChatGPT web lane (Web Pro) only for browser review explicitly enabled by the owner, not a Worker class, and the class table does not change it.

## PMs

This file is the one model map for OPC and OPN. Every PM, main and child, runs on Opus high (Pi `fleet/claude-opus-5-5`, thinking high; owner 2026-11-18), unless the owner names another model for it, and has no fallback. Exactly two named starts fall back when Opus high is unavailable: the fresh PM that `unstuck` starts, and an OPN worker on the `code` class. Each then starts on Sol high (Pi `fleet/gpt-6.2-sol`, thinking high). Opus high counts as unavailable only when it is missing from the catalog, or the agent fails to start or returns a quota error. Every other PM stays on Opus high; OPC `code` lanes never take that fallback: they stop and report to their PM. A `review-security` lane that fails follows [Security review escalation](#security-review-escalation "runtime"). A PM's own model never passes to its lanes or workers; each takes its class route.

## Fable

Fable runs on the OPC `plan`, `ui-design` and `ui-check` lanes, or wherever the owner names it. A `research` lane runs on Terra and asks Fable only through `$ask-fable`, which starts no Fable agent. Implementers and reviewers use Opus or Sol, and no lane inherits Fable from its PM. At most 5 Fable agents run at once across the fleet, PMs and `plan` lanes included; before starting one, count the running Fable agents on every host. When the owner names Fable for a code lane, `buildDelegatedBrief` starts its brief with an ownership line (the owner and long-term maintainer of the codebase, its design up to it within the brief's permitted changes), per Anthropic's Fable 5.2 prompting guidance.

## UI work

Fable designs and checks; Opus builds. In UI work, Fable is only for real visual design: a new screen, a layout change, or a new component. Copy, labels, states, error text, renames, and guards with no layout change are `code` only, with no Fable lane.

1. `ui-design` (Fable high, Fast off, read-only) takes the current screens, as screenshots and code, and returns a short design spec plus a static mockup (HTML/CSS or images) at a scratch path the PM names. It makes no repository edits and opens no PR. At most one per task; a second needs the owner's OK.
2. A normal `code` lane (Opus high) builds: it implements the spec and mockup exactly, plus the logic, and opens the PR with [before and after screenshots](pr-evidence.md "branch:evidence").
3. `ui-check` (Fable high, Fast off, read-only) is optional and runs one pass: it compares the after-screenshots to the mockup and returns a fix list. The code lane applies the fixes.

The `ui-design` and `ui-check` lanes run in a UI task (the Fable `plan` lane does not), created with `createTask({..., ui: true})`; pass `ui: true` to `selectTopology`. Its lanes take only `ui-design` (the default when no `taskClass` is given) or `ui-check`, and the build runs in a separate normal `code` task. Both classes resolve to owner-explicit routes with reasons `ui-design: owner rule, Fable high, no GPT, read-only` `ui-check: owner rule, Fable high, no GPT, read-only`; `buildDelegatedBrief` marks them read-only. UI work never uses a GPT or web model: no Sol, Luna, or Astra Worker, no Sol scouts, and no web reviewer in `ui-design` or `ui-check`. The UI task refuses browser review, `recordWorkerRoute` and the Worker builders given the task refuse any other class and anything but Fable high, Fast off, with a Fable model id, and the topology runs no scouts. An owner-named route still wins inside these rules; one for `ui-design` or `ui-check` other than Fable high, Fast off is refused, so ask the owner to use the class instead. The old `ui` class name is an alias of `ui-design`.

## Settings

OPC routing reads one optional key of `~/.config/opc/routing.json`, `antigravityFallback`, and only for the off-pace and [code parity](#code-parity "runtime") routes below; its `pq` key and every other key belong to other readers and are never read or rewritten.

### Antigravity replacement

Owner decision 314a (2026-11-21): while Claude is off pace, a new `code` Worker lane on the Opus high, Fast off default runs instead on the generic ACP provider `agy-opc`, model `gemini-4-neon-high`, thinking high, Fast off, in agy's native mode `auto` with the generic ACP feature `auto_accept` true (Paseo approves its ACP permission prompts). `default`, `accept-edits`, `plan`, any other mode, and any other or caller-set feature are refused. When pace recovers, new lanes take [code parity](#code-parity "runtime"); recorded lanes keep their route. Nothing else moves: PMs, owner-named routes, every other class (`review-security` and all reviews included), lanes with a recorded route, running agents, and excluded launchers, listed locally, with anything they launch (the launching `PASEO_AGENT_ID` and its parent chain are checked; an unreadable list or chain allows no off-pace route).

Off-pace backup (owner decisions 310 and 316): only with evidence that Neon cannot launch (newer than any fresh proof) does the lane run Pi `fleet/gpt-6.2-sol` at medium, Fast off (owner 2026-11-21), source `pace-backup`. A missing proof is not that evidence: off pace with neither a proof nor evidence stays Opus. It is the only GPT route a `code` lane may take: it records only through this admission, while off pace or on a [code parity](#code-parity "runtime") Neon turn, launches only from its own recorded lane, and every other GPT code route is still refused. A recorded lane never changes route, so after a Neon failure resolve a new lane with the evidence.

The switch is `antigravityFallback: {enabled, state: {off_pace, as_of, expires_at}}`, written only by Config's pace job. It is on only with both booleans true, RFC 3339 UTC times with `as_of <= now < expires_at`, on a Mac, in a regular file owned by the user and writable only by them, with no repeated key. Both booleans false, with the same time rules, is not forced: [code parity](#code-parity "runtime"). Absent, stale, unknown, unsafe, or one boolean true and the other false stays Opus, as does a missing or malformed local list of excluded launchers. Config owns `expires_at`; OPC sets no cap. Never copy its values into a reason, brief, record or log.

Invocation: pass `replacement: {task, lane, proof, target}` (Neon) or `{task, lane, target, unavailable}` (backup) to `resolveWorkerRoute` and `recordWorkerRoute`; `route.mjs --class code --task T --lane L` passes only `{task, lane}`, so it stays Opus. For Neon, call MCP `create_workspace`, then MCP `inspect_provider` for `agy-opc` on that workspace's server with the draft `settings: {modeId: 'auto', model: 'gemini-4-neon-high', thinkingOptionId: 'high', features: {auto_accept: true}}`, and MCP `list_models` for `agy-opc`. Pass `capabilities: {...inspect_provider result, models: list_models rows}`, `target`, and the unchanged `create_workspace` result as `workspace` to `buildManagedWorkerRequest`, with no `provider` or `agentSettings`. The backup launches like any Pi Worker.
- `target` `{daemon, local: true, platform: 'darwin'}`: the local daemon; `daemon` is the `serverId` that `create_workspace` returns.
- `unavailable` `{provider: 'agy-opc', target, checked_at, finding}`: what MCP `inspect_provider` and `list_models` showed on that target within the last hour, `finding` one of `missing`, `disabled`, `not-available`, `not-serving` (not the model at high with mode `auto`).
- `proof` `{provider, extends: 'acp', model, thinking, mode: 'auto', sandboxed: true, write: true, target, verified_at}`: the PM's attestation from a readback on that target within the last hour (the approved `agy-opc` row and a proof agent's status showing this runtime). Keep no raw snapshot or switch state.

The code enforces exact equality of these fields with the approved runtime; re-admission at recording; and at every launch and rebuild, that the record is exactly its approved runtime, that the workspace's `serverId` is the recorded target, that `inspect_provider` reports `agy-opc`, the model at high, mode `auto` and one `auto_accept` toggle set true, and that the request sends exactly those settings. These gates are bookkeeping, not a sandbox; the owner accepted that agy's sandbox may write outside the repository. The receipt binds task, lane, target and placement (the branch), never the switch state. A recorded off-pace lane resumes (`route.mjs --task T --lane L`, no route flags) and rebuilds on its route without reading the switch; if the record or the target no longer matches, the lane stops.

### Code parity

Owner decision 359: while the switch is valid, fresh and not forced (both booleans false), new eligible `code` lanes (aliases included) alternate between Opus high and Neon high, one each per launching agent, starting with Opus. A not-forced switch says only that the lane is not forced to Neon; it proves nothing about quota. The pace writer also writes both false when pace is unknown, so code parity cannot tell unknown from on pace; Config decided that unknown pace alternates too (neutral parity). Forced (both true) is the replacement above and takes no turn.

- For every fresh local `code` lane, resolve and record with the full context: `task`, `lane`, `target`, and the `proof` or `unavailable` evidence when you have them. Without the context a lane never alternates.
- Eligible: a fresh bound lane of a non-UI task, resolved and recorded through `resolveWorkerRoute` and `recordWorkerRoute` with the same `replacement` context as Neon, whose `target.daemon` is the local daemon's own `serverId` as its read-only `paseo daemon status --json` reports it (a daemon that is not running or a status that cannot be read admits nothing), from a launcher that is not excluded. The launcher is `PASEO_AGENT_ID`, with the excluded-launcher check above. Remote, Linux, Windows or missing targets stay Opus and take no turn.
- An Opus turn records the plain Opus high default. A Neon turn records Neon high with a fresh `proof`, under its own reason, with the same runtime, receipt and launch checks as the replacement. With fresh `unavailable` evidence newer than any fresh proof, it records the Sol medium, Fast off backup under its own reason. With neither, it records Opus and the Neon turn stays next.
- What counts: a newly recorded eligible lane that took its turn's route. Nothing else counts: a resolve, dry run or replay of a recorded lane, a forced lane, an owner-named route, a decline (resolved, never recorded), another class, another launcher, a refused record, and a Neon turn that fell back to Opus. `route.mjs --class code --task T --lane L` passes no target, so it stays Opus and takes no turn.
- Recording: the launcher chain and the local daemon status are read first, without a lock. Only a fresh eligible lane that takes a turn then takes the alternation lock, re-admits against the locked turn state, writes the task record, and counts the turn once. Every other record never touches the lock: a replay, an owner-named route, another class, a forced lane, and a lane that falls back to Opus without a turn. When a competing lane of the same launcher took the turn first, the record is refused (`alternation turn changed`) and the lane may be resolved again; do not retry blindly. If the process dies between the two writes, the lane is recorded and its turn is not counted, so that launcher repeats that one turn; no route is wrong and no turn counts twice.
- Turn state: `~/.config/opc/code-alternation.json`, beside `routing.json`, which it never touches. It holds only a per-launcher count and time, for at most 256 launchers, the most recent kept. It must be a regular file owned by the user with mode 0600. When it is unreadable, unsafe or malformed, every lane stays Opus, takes no turn, and the file is left for the owner. A lock left by a writer that died blocks every lane on the host that would take a turn, from any launcher, until it is removed; other records go on. A refusal names the holder: when it is still running, retry once it finishes; when it is gone, run `node scripts/task-state.mjs unlock ~/.config/opc/code-alternation.json`, which removes the lock only when its recorded holder is gone or its pid now names another process.
- Recorded lanes, forced 314a lanes included, resume and rebuild on their recorded route. PMs, owner-named routes, every other class (`review-security` and its decision 332 escalation included), excluded launchers and the pace writer are unchanged.

OPN `code` workers take the same path. An OPN `code` worker joins the alternation only through OPC's managed code-lane path: `createTask` on its git checkout, then resolve and record with the full context, `create_workspace`, `buildManagedWorkerRequest` and `create_agent`, as in [Worker placement](imp-execution.md#worker-placement "runtime"). A worker started any other way, such as in the PM's own workspace with no task record, runs Opus high and takes no turn. Non-code OPN workers are unchanged.

Remote targets: this admission takes only the local daemon's own `serverId`. A forced 314a lane still takes the caller's `target` as local, as before; that limit remains for the forced path and its existing receipts. A caller-supplied remote proof or capability is never accepted, and a lane for any other host stays Opus and takes no turn. A PM on another host reads no switch (it is read only on a Mac), so its own launches stay Opus.

## Errors

Network and proxy errors, such as `Connection error` or a 502 `backend unavailable`, are retried on the same route by sending the same Worker a continue follow-up. They never change the model or effort. Rate limits, unavailable capabilities, and real launch failures still stop the lane; substitution requires a new explicit owner decision.
