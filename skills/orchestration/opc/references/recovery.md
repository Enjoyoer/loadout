# Recovery and cancellation

Inspect the failed component: Worker execution separately from controller/messaging health, page loading separately from authentication. A network or proxy error (`Connection error`, 502 `backend unavailable`) is retried on the same route with a continue follow-up to the same Worker; it never changes model or effort. Rate limits and real launch failures still stop the lane. Preserve existing state. A lost message or unknown/still-running launch never authorizes replacement; slow loading alone does not justify restart or another login. Never bypass a human challenge.

For managed Workers, call `cancel_agent({agentId})` on the recorded identity and confirm the owned run stopped through Paseo. Retain workspace and commits for integration or explicit abandonment under [cleanup](worktree-lifecycle.md "runtime"). Cancellation alone does not authorize archival.

An interrupted `delivery.mjs test` leaves `tests.status: 'running'` with its pid and that process's start time. SIGINT or SIGTERM stops the test command and records `blocked`; if the process was killed outright, `delivery.mjs reconcile <task.json>` (which then also reconciles a pending merge) or the next `test`, `verify`, `merge` or planner launch marks the record `failed` with reason `interrupted` once that pid is gone or names a process with another start time, and records in `cleanup` what it did about the test command's process group. It signals the group when the command's start time still matches, and on POSIX also when its pid is gone, since a process group id cannot be reused while the group has members (`nothing left to signal` when it is empty). A pid that now names another process is never signalled: `cleanup` reads `incomplete: PID reused`, and likewise `incomplete: start time unreadable`. Start times are exact text in one fixed format (`ps` lstart under `LC_ALL=C` and `TZ=UTC`, the UTC creation time on Windows), never parsed or compared within a window; a live pid whose start time cannot be read counts as still running. On Windows the kill is `taskkill /T /F` from the test command: it follows parent ids from a live root, so a descendant orphaned after its parent exited is not found and keeps running (`cleanup` says so when the root is gone); stop it by hand. A `task.json.lock` holds its writer's pid and start time. It is stale and replaced when that pid is gone or names a process with another start time, or when it is empty and over 10 s old; a live pid's lock whose start time matches or cannot be read is never removed. If the lock changes hands during a reclaim, the call fails with `task lock contention`; retry it.
