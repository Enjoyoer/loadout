# Recovery and cancellation

Inspect the failed component: Worker execution separately from controller/messaging health, page loading separately from authentication. A network or proxy error (`Connection error`, 502 `backend unavailable`) is retried on the same route with a continue follow-up to the same Worker; it never changes model or effort. Rate limits and real launch failures still stop the lane. Preserve existing state. A lost message or unknown/still-running launch never authorizes replacement; slow loading alone does not justify restart or another login. Never bypass a human challenge. Scripts enforce; task records and receipts are bookkeeping, not security boundaries.

For managed Workers, call `cancel_agent({agentId})` on the recorded identity and confirm the owned run stopped through Paseo. Retain workspace and commits for integration or explicit abandonment under [cleanup](worktree-lifecycle.md "runtime"). Cancellation alone does not authorize archival.

An interrupted `delivery.mjs test` leaves `tests.status: 'running'` with its pid and that process's start time. SIGINT or SIGTERM passes to the test command's process group, which gets 10 s to exit, and records `blocked` with `cleanup`: `exited after signal`, or after the 10 s what killing the group under the identity rule below did. A killed group gets 10 s more to close; `group signalled` means it did, and `cleanup incomplete: did not exit` that it did not. A kill the rule forbids records why. In those cases the controller stops waiting, the command may still be running, and the receipt keeps its `child_pid` and `child_start`. If the process was killed outright, `delivery.mjs reconcile <task.json>` (which then also reconciles a pending merge) or the next `test`, `verify`, `merge` or planner launch marks the record `failed` with reason `interrupted` once that pid is gone or names a process with another start time, and records in `cleanup` what it did about the test command's process group. It signals the group when the command's start time still matches, and on POSIX also when its pid is gone, since a process group id cannot be reused while the group has members (`nothing left to signal` when it is empty). A pid that now names another process, or whose start time cannot be read, is never signalled: `cleanup` reads `cleanup incomplete: PID reused` or `incomplete: start time unreadable`. Start times are exact text in one fixed format (`ps` lstart under `LC_ALL=C` and `TZ=UTC`, the UTC creation time on Windows), never parsed or compared within a window; a live pid whose start time cannot be read counts as still running. On Windows the kill is `taskkill /T /F` from the test command: it follows parent ids from a live root, so a descendant orphaned after its parent exited is not found and keeps running (`cleanup` says so when the root is gone); stop it by hand. A `task.json.lock` holds its writer's pid, start time, and a token unique to that update, and appears already written, as a hard link to a finished file. Nothing removes another writer's lock implicitly. A writer that finds a lock waits up to 2 s, then fails with `task lock busy`, naming the holder's pid and start time and whether it is running, gone, reused, or unknown (start time unreadable). When a writer crashed and left its lock, run `node scripts/task-state.mjs unlock <task.json>`. It removes the lock only when the recorded pid is gone or now names a process with another start time. It refuses a running or unknown holder and a lock with no pid, such as an empty one an earlier OPC version left; remove that by hand once no OPC process works on the task. A writer whose token is no longer in the lock fails with `task lock lost` before it replaces `task.json`. An update writes `task.json` through a synced temporary file renamed over it. On POSIX it also syncs the directory before it returns, so an update that returned survives an OS crash or power loss. Windows gets a flushed file and an atomic rename only: Node cannot sync a directory there.
