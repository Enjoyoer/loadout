# Usage limit auto resume

Startup endpoint resolution uses explicit `PASEO_HOST`, then `$PASEO_HOME/paseo.pid` runtime listen metadata. An explicit non-default `PASEO_HOME` without valid endpoint metadata refuses to connect instead of falling back to another daemon. Invalid explicit hosts also fail closed. The standard local endpoint is a fallback only for an unset home or `~/.paseo`.

This server plugin keeps the existing usage-limit resume path (five-hour default) and adds a separate retry path for completed turns whose final assistant message is a transient provider error. Both paths obey the host `armed` setting and the `noresume=true` label. The plugin does not send while unarmed.

## Transient retry

The final assistant text must start with `API Error:` and contain `rate limit`, `rate_limit`, `temporarily limiting requests`, `overloaded`, `429`, or `529`. The exact final text `Selected model is at capacity` also qualifies. A normal answer that discusses these terms does not qualify. Explicit usage-limit failures retain the five-hour path.

Every turn that ends as `failed` (not `completed`) is resumed, whatever the error, unless it is an explicit usage limit (five-hour path) or the agent is opted out. The resume is a pure `continue` sent to the same session, never a replay (a Pi prompt timeout is the exception, see below), and it may be sent while the agent is in `error` status.

No retry is ever given up for its attempt count or for failing the same way again (since 0.3.0). Every retry, for failed turns and for completed-turn errors alike, follows one schedule: the first goes out immediately, then after 2, 5 and 15 minutes, then every 30 minutes, for as long as it keeps failing. Each delay is measured from the failure it retries, even if the provider spent hours retrying inside the turn. A repeated 429 rate limit or 402 credit-balance error keeps retrying too; while pq shows the whole pool out it is held until the reset instead (Quota awareness). A record ends only when:

- a retry succeeds;
- a newer user message arrives (`superseded`, `newer-user-message`), or the user cancels the retry turn;
- the agent is opted out (`noresume=true` or an excluded provider);
- the agent is archived (`agent-archived`) or deleted (`agent-missing`, on the second sweep that finds no agent).

A plugin reload keeps every record as it is. A `closed` agent status is not an ended one either: Paseo marks every agent `closed` when the daemon shuts down, and a send loads it again. An explicit close or kill by a user or an agent ends the record like an archive (`superseded agent-closed`). Paseo sends the same `agent.closed` event for both. The plugin therefore stores the close for the agent, not for one of its records, together with the daemon run that saw it (the plugin's parent process). It does so whether or not the agent has a record yet, so a record a handler creates after the close (a failed turn's first record, or a resume's successor) is held by it too. Until the close is decided the plugin sends nothing for the agent and reads none of its timelines. If the same daemon run outlives the close by 60 seconds, its records end. A new daemon run clears the close (`agent-close-cleared`) and the retry goes on. Work that began with a user message newer than the close is not affected, because that message opened the agent again. Paseo stops plugins a few seconds into a shutdown, well inside that window. Two limits: a daemon restart within 60 seconds of an explicit close keeps the record, and a close the plugin's own PM fallback reload causes is ignored.

A record's work is the failed turn it came from, bound by identity to the user row of its `turn_ended` event (or, if the event has none, to the predecessor record's own last send). The work's origin is that row's daemon timestamp, and every successor carries it on, so no record takes a later agent snapshot's user message. After its awaits, the turn-end handler reads the agent's timeline back to the bound row. The failure is stale (`stale-failure`) only if the latest user row is a different message, later in the daemon's timeline and stamped no earlier, and not the bound row rebuilt with a new ID. A stale failure creates no record and ends the record it would have handed off from, since newer work took over. Only daemon evidence decides this, never the plugin's clock, so clock skew cannot drop a failure. When nothing can be bound (a missing ID, or a failed read), the failure is not stale, and the snapshot's `lastUserMessageAt` stands in as the origin. A closed agent's timeline is never read, because the read would load it again. That covers an agent the snapshot shows closed, and an agent whose close landed while the snapshot was being read, since that snapshot may predate the close. The failure is then not stale and gets no origin, so the close holds and ends its record. The same holds when the bound row is gone from the timeline, which means the agent was loaded again after a close. After a daemon restart Paseo also rebuilds the agent's timeline from the provider session, where every user row gets a new ID and no `clientMessageId`. A user row with the record's expected text is still taken as the expected one, whether that is the original human message (a first retry not sent yet, for example on a quota hold) or the record's own last send, as long as the agent's `lastUserMessageAt` is unchanged, since a newer message would move it. This holds on every path: the send checks, the re-verification of an `uncertain` retry, and the prompt-timeout check. So a waiting retry survives a plugin reload and a daemon restart. One limit: a retry already sent and still running when the daemon stops cannot be told from a new message on the rebuilt timeline, and ends `superseded`. An identity or session change ends the record too (`identity-changed`); a PM fallback swap is not one (see PM quota fallback). A pending permission or attention request holds a send until it clears; a permission request on a record that has not sent, including a send not started yet, leaves it waiting on its schedule. The plugin keeps no timer per record; one poll sweeps every record, so an ended record leaves nothing behind. Logs are one set per retry, never one per poll: `retry-sent`, `retry-scheduled` (with `attempts` and the next `notBefore`), and one `send-skipped ... reason=not-due notBefore=...` while it waits; an unarmed host's `would-resume` and a PM's `send-deferred` are logged once per attempt too. The capacity match on completed turns also accepts Codex's `[System Error]` prefix and trailing `Please try a different model.`

If the agent has not settled yet, the immediate retry waits for the next sweep (30 seconds). `transientBackoffSeconds` sets the schedule (default `[0, 120, 300, 900, 1800]`; its last step repeats). `maxAttempts` and `transientMaxAttempts` are still accepted in settings files, which set them, but are ignored since 0.3.0. The plugin resends the last timeline user text exactly. If that text is empty, it asks the agent to continue the last request. It verifies a fresh timeline and agent snapshot before every send, including idle state, permission state, latest user message, model, and session. For transient records it follows older timeline pages until it finds the newest user row, so a long turn cannot hide its prompt behind the 200-row tail page. Transient `uncertain` records are re-verified on every sweep, including `retry-turn-ambiguous` and `user-prompt-missing`: a live failed turn with no newer human message is re-armed on the backoff; a running turn is left alone. Missing or incomplete evidence remains recoverable and is checked again, never treated as terminal. The latest user must match the checked original row or the retry's stable message ID and exact prompt. Usage-limit records retain their existing reset timing and their terminal uncertainty behavior for ambiguous deliveries. A usage resume whose turn fails hands the work to a new record for that failed turn, logged as `resume-failed-rescheduled`: another usage limit waits for its reset again, and any other failure retries on the schedule above. The handoff is one store write made only while the old record still waits on that turn, so a duplicate end event for the turn changes nothing and can never reset or resend a successor that already ran. A successful retry removes its record or settles it as done during live re-verification.

### Pi prompt timeouts

A failed turn on the `pi` provider whose error starts with `Pi RPC request timed out phase=prompt` takes its own path; other providers with a similar diagnostic (OMP) keep the ordinary failed-turn path. Paseo's Pi provider gives up when Pi does not acknowledge a prompt within `rpcTimeoutMs` (60 s by default), but Pi acknowledges only after its prompt preflight, which first runs Pi's own threshold compaction. The prompt is still pending in Pi and normally runs by itself once compaction ends, a few seconds later. An immediate `continue` meets the same compaction and times out too.

- No immediate send. The record waits, re-checked every sweep, until the agent is `idle` or `error` with no active turn, no compaction is in progress, and nothing new has appeared for 60 seconds after the failure or the end of compaction.
- The compaction signal is the agent's own timeline: a `compaction` row with status `loading` and no later `completed` row since the original message means Pi is still compacting. Paseo's agent status cannot show it (the timed-out turn is already failed while Pi compacts), and cache-aware-autocompact's state covers only its own `/compact` sends, which reach Pi as a separate compact RPC that rejects a concurrent prompt at once rather than timing it out.
- The whole check runs again on the final timeline read right before the send, after the send is claimed. Compaction and timeline rows do not change the agent's `updatedAt`, so the agent re-read alone cannot catch them. A wait found there puts the record back as it was; a stop ends it.
- Only execution evidence counts as the agent resuming by itself: reasoning, a tool call or a real answer after the original message, a running turn, or an `agent.turn_started` / `agent.turn_ended` hook for another turn. The record then ends `superseded` (`agent-resumed-itself`) with no send. A newer user message ends it the same way (`newer-user-message`). Any other row (a notification, an error row, a todo) proves nothing: the record waits (`unproven-activity`) and expires at the bound below without sending.
- Then the original message is resent once, with the usual stable message ID and pre-send checks. The replay is text only: Paseo's timeline keeps only a user message's text, so images and other attachments on the original are not resent, and a message with no text (attachments only) gets no resend at all. If the resend fails, or anything leaves the record `uncertain`, it ends `exhausted` (`rpc-timeout-resend-failed`, `rpc-timeout-<reason>`) and is never sent again.
- Every turn the plugin starts is marked handled in the state file when it starts or ends, with the same guard a pruned record leaves, and a turn whose newest user row is one of the plugin's own sends is never detected as a new failure. A repeated or late end event for a failed resend therefore cannot create a second record or a second send.
- The wait is bounded at 30 minutes from the failure; then the record ends `exhausted` with `rpc-timeout-wait-expired`.
- Logs: `rpc-timeout-waiting` (once per reason: `compaction-in-progress`, `settling`, `unproven-activity`, `agent-status=...`, `timeline-unavailable`), `rpc-timeout-no-resend`, `rpc-timeout-gave-up`, `send-skipped` for a final-read wait or stop, and the usual `retry-sent`.

The fleet can raise Paseo's Pi `rpcTimeoutMs` (personal-skills `pi.options`, see `fleet/README.md`), which avoids most of these timeouts.

## Quota awareness

Before it schedules a usage-limit resume, and again before every send, the plugin reads Paceline's quota CLI (`pq --json`, schemaVersion 1), the same source OPC's route pace uses (see `skills/orchestration/opc/references/routing.md`, Pace and Settings). The argv is the `pq` key of `~/.config/opc/routing.json` when it is a nonempty string array, else `["~/.local/bin/pq", "--json"]`; a leading `~` is expanded and pq runs without a shell. The agent's pool follows its provider and model as in OPC: Claude models (Opus, Sonnet, Fable, Haiku) read the claude accounts, GPT models (Sol, Luna, Astra) the codex accounts. Web and local models have no pool.

Only the `five_hour` and `seven_day` windows count. An account is out while one of them shows 0% left (or pq marks it blocking) and its reset, plus the buffer, is still ahead; it frees when its last out window resets. An account has quota only on a fresh reading whose windows all show some left. Any other account keeps the pool from reading as out.

- Usage limit: the resume is due about `quotaResetBufferSeconds` (60) after the pool's earliest real reset, the first time an out account frees (5-hour or weekly), instead of the flat `baseDelaySeconds`. Never earlier than a reset the error itself names. While another account still has quota, the reset only brings the resume earlier, never later than the flat delay.
- Transient and other failed turns: while some account in the pool has quota, retries run as before. If every account is out, the send is held until the earliest reset plus the buffer. A hold consumes no attempt.
- Out for the week: the same hold runs until the weekly reset. Every hold is logged once as `quota-hold ... reason="quota-blocked pool=<pool> weekly accounts=<n> until=<iso>"` (or `window=five_hour`) and stored on the record as `quotaHold`. No PM is notified; pooling handles rerouting. Each due sweep re-reads the quota, so an early reset or a freed account releases the hold (`quota-released`) and the send goes out.
- Quota refusals: after a failed turn the provider refused for quota (a usage limit, a 429 rate limit, or the 402 "credit balance is too low" of an API-key route), an account pq cannot show with quota left, such as a stale or rolled-over reading, counts as out too: only a fresh reading with quota left is capacity. The retry is then held as above (the reason adds `unproven=<n>`), and a PM may swap (see PM quota fallback). The rule applies only to the pool that refused; a 429 while pq shows an account with quota left stays an ordinary transient retry. Quota evidence is read on the raw error text, in three forms. First, a structured error code: `429`, `402`, `rate_limit*`, or `insufficient_credit(s)`. Second, a phrase: a rate-limit word (`rate limit`, `rate_limit_error`, `rate limited`), `credit balance is too low`, `insufficient credit(s)`, or `Too Many Requests`. Each phrase must stand on its own, never inside a path, a URL or an ID: no word character, slash, backslash, `.`, `-` or drive-letter colon right before it, and no word character, slash, backslash, `-` or `.` plus a word character right after it. A sentence-ending `.` still counts. Third, a numeric status at the very start of the error, after an optional `[System Error]` or `API Error:`: 429 or 402 followed by a JSON body, its reason phrase (`Too Many Requests`, `Payment Required`), `status code`, `:` and the error text, or nothing (`429 {...}`, `402 Payment Required`, `API Error: 429`). A quoted JSON key `"status":429`, `"status_code":429` or `"code":429` also counts, as does `rejected (429)`. A status number anywhere else does not count: a 429 inside a request ID, a path or a URL, a leading count such as `429 files processed`, or an `HTTP 429` in the middle of an error with no phrase and no code. Such an error stays an ordinary transient retry. An error that also names an overloaded, context-length or cooldown error, with or without a suffix such as `_error` or `_exceeded`, is never a quota refusal. The refusal belongs to the pool of the model that refused (the model Pi names in the error, else the one the turn ran on). It never applies to another pool. Re-verification sees only the live error text, so it recognizes no new refusal, and a repeat of the same failure keeps the record's evidence as it was. A record that follows its PM to another profile drops the evidence, so a refusal from before a swap or a restore never holds or swaps the PM again without a new refusal on that pool.
- Unknown quota keeps today's behaviour exactly: pq missing, erroring, slower than `pqTimeoutSeconds` (5), unparseable, another schemaVersion, a stale snapshot, or a pool pq does not list.

One pq reading is shared for `quotaCacheSeconds` (60), so many failing agents start one pq process. `quotaAware: false` turns the feature off.

## PM quota fallback

Off by default (`pmFallback: false`). When on, a live Pi agent labelled `role=pm` on a Claude model moves to an exact catalog profile while its Claude pool is out, and returns to its original profile once Claude is usable again. Workers, watchers and any agent without `role=pm` never change model. Every such PM is eligible: since 0.3.0 no label opts it out. The `nofallback` label and the `pmFallbackOptOutLabel` setting are gone; the setting is still accepted in settings files but ignored, and a PM that still carries the label swaps and returns like any other. Every write goes through one gate that also carries out a pending owner cancel first, on every trigger.

- Swap: after a PM turn fails with a quota refusal (a usage-limit error, the same evidence a usage resume record is built from, or a 429 rate limit or 402 credit-balance error; a completed reply never swaps, whatever its text says), or a sweep finds its failed-turn record on a quota hold, pq must show no Claude account with quota left and must not show the fallback pool out. A stale or rolled-over Claude account counts as out here; a fresh account with quota left means no swap (`pm-fallback-held ... claude-pool-has-capacity`), so a plain 429 stays a transient retry. A stale pq snapshot or missing quota never swaps. The plugin first stores the exact original model, thinking option and `opc.service-tier` label, then sends one `agent.config.apply` with `pmFallbackModel` (`fleet/gpt-6.1-sol`) and `pmFallbackThinking` (`medium`) together, sets `opc.service-tier=fast` (`pmFallbackServiceTier`), and reads the agent back. The fallback model and thinking option must be listed verbatim in the Pi catalog; an unset original thinking option is stored as the model's catalog default. A stored swap intent that was not applied yet (after a crash or restart) is decided again before it is applied: the agent must still be an eligible PM on its original model and a fresh pq reading must still show Claude out, or the intent is dropped. Once the fallback model is in place the swap is finished whatever quota reads: a partial swap is repaired, the stored record confirmed and the PM's resume record moved to the new model, and only then is it a return. It is never dropped. The PM's resume record follows it to the new profile, so the existing resume engine continues the same session on Sol.
- Return: the obligation lives in `<PASEO_HOME>/plugin-state/usage-limit-auto-resume/pm-return.json`, apart from resume records. Superseding, settling or pruning a record, plugin reload, daemon restart and idle periods do not remove it. The return is due only while pq, read fresh at that moment, shows a Claude account with fresh five-hour and weekly readings that both have quota left. A weekly-out account whose five-hour window reset, a missing weekly reading, or stale or unknown quota does not count, and an earlier due reading never authorizes a restore by itself.
- Applying: settings are applied whenever a swap or due return is outstanding, on `agent.turn_ended` and on the poll sweep as a backstop. A PM in the middle of a turn is changed too: Paseo applies the settings to its next turn and never interrupts the current one (verified on a scratch 0.11.1 daemon with the real Pi CLI). A change counts as done only once the daemon's stored agent record (`<PASEO_HOME>/agents/`, what a reload or restart loads) holds it too, since Paseo acknowledges settings in memory and persists them in the background. A mismatch on read-back, a change that never reaches the stored record, or a rejected update keeps the obligation and is tried again at the next turn end or sweep; it never settles on its own. While a swap or due return is unverified, the resume engine sends nothing for that PM.
- Only an explicit owner cancel ends a return early. A manual model change, a lost `role=pm` label or turning `pmFallback` off does not. An archived PM is never changed or resumed; its obligation waits.
- Sol also out: no swap, ordinary quota hold. On Sol and Sol runs out: ordinary hold on Sol until Claude returns. No ping-pong.
- Logs: `pm-swap-start`, `pm-swap-apply`, `pm-swap-verified`, `pm-restore-due`, `pm-restore-apply`, `pm-restore-verified`, `pm-*-failed`, `pm-*-mismatch`, `pm-*-unpersisted`, `pm-swap-dropped`, `pm-swap-not-completed`, `pm-return-waiting`, `pm-fallback-held`, `pm-enrolled`, `pm-return-cancelled`. The resume engine no longer ends a quota loop (0.2.2's `retry-stopped` is gone): a PM refused with pool capacity keeps retrying on the schedule, and swaps once pq shows the pool out.

Limits. Paseo has no idle-only settings barrier, so a message that lands between the return becoming due and the settings write can run one more turn on Sol; the next turn runs on the original profile. Paseo labels cannot be deleted, so an originally absent `opc.service-tier` is restored as an empty value, which fleet routing treats as absent. The settings writes use the daemon client that `@getpaseo/client` wraps (`applyAgentConfig`, `updateAgent`), because the public agent handle has no setter for them.

### Enroll a PM that already fell back, or cancel a return

Both go through the host settings file, which the plugin re-reads every sweep. Back it up first and keep its other values. Copy the original model ID verbatim from `paseo provider models pi --thinking`; `serviceTier` is the PM's original `opc.service-tier` label, or `null` if it had none.

```bash
f="${PASEO_HOME:-$HOME/.paseo}/plugin-settings/usage-limit-auto-resume/auto-resume-config.json"
cp "$f" "$f.bak-$(date -u +%Y%m%dT%H%M%SZ)"
jq --arg id "<agent-id>" --arg model "<original-model-id>" --arg thinking "<original-thinking-id>" \
  '.values.pmFallbackEnroll += [{agentId: $id, model: $model, thinkingOptionId: $thinking, serviceTier: null}]' \
  "$f" > "$f.tmp" && mv "$f.tmp" "$f"
```

The entry is applied once (`pm-enrolled`, or `pm-enroll-rejected` with a reason): the agent must be a live Pi `role=pm` agent not already on that profile, and the original must be a Claude model in the catalog. The PM keeps its current profile until the return is due. To cancel one return, add its `obligationId` (from `pm-swap-start`, `pm-enrolled` or `pm-return.json`) to `pmFallbackCancel` the same way: `jq --arg id "<obligation-id>" '.values.pmFallbackCancel += [$id]'`.

Follow-up seam (not in this plugin): a worker never swaps. A read-only planning companion for a parked worker would use the same quota-release signal (`restoreDue` in `server/fallback.ts`) and the worker's parked resume record, without changing the worker's model.

## Pattern evidence

- Claude has emitted `API Error: Server is temporarily limiting requests (not your usage limit) · This request would exceed your account's rate limit. Please try again later.` as a synthetic assistant message with `apiErrorStatus: 429`.
- Claude has also emitted `API Error: Request rejected (429)` with `rate_limit_error`.
- Codex has recorded `Selected model is at capacity`.
- With every Claude account out, Pi has failed turns with `429 {"type":"error","error":{"type":"rate_limit_error","message":"This request would exceed your account's rate limit. ..."}}`, and an API-key route with `402 ... Your credit balance is too low to access the Anthropic API.` Both read as quota refusals only while pq shows no account with quota left (Quota awareness).
- Anthropic documents `529 overloaded_error` as temporary overload and `429 rate_limit_error` as a rate limit: <https://docs.anthropic.com/en/api/errors>. A 429 can also indicate a spend cap, so explicit usage-limit text takes priority and unknown messages are not retried.

Paseo's [`agent.turn_ended` event](https://paseo.sh/docs/plugins/reference.md#lifecycle-hooks) supplies a completed outcome and, on 0.11, the agent's timeline. Paseo 0.13 sends that timeline empty, so the handler then reads the tail itself with `refetch({direction: "before", limit: 200})`, walking back to the newest user row, before any other await; with a non-empty event timeline nothing changes. That read follows the closed-agent rule above: a canceled turn is never read, since a kill, delete, archive or daemon shutdown cancels the turn just before it unloads the agent. Each page is read only right after a fetch, which never loads an agent, shows the agent loaded (its snapshot carries `activeTurn`) and neither closed nor archived, and only while this process has seen no close or archive of it since the event, during that fetch included: a fetch answered before a close it was in flight with still shows the agent open. Such a turn is handled as if its event had no timeline; for a canceled turn that only means an older record is not superseded by it, and the send checks catch the newer user message instead. The SDK's timeline `refetch()` also supplies the fresh page used for the final send check.

## Settings and install

Host-scoped settings are stored by Paseo at `<PASEO_HOME>/plugin-settings/usage-limit-auto-resume/auto-resume-config.json` as `{"version":2,"values":{...}}`. A missing file means defaults, and the default is `armed: false`, so a fresh install observes and records but sends nothing. Arm a host only after reviewing `paseo plugin logs usage-limit-auto-resume`, by writing `{"version":2,"values":{"armed":true}}` to that file.

Resume records live in `<PASEO_HOME>/plugin-state/usage-limit-auto-resume/state.json`. A missing file means no records. If the file is unreadable, corrupt, from another state version, or holds a malformed record (a missing id, an unknown state, or an unparseable time such as `notBefore`), the plugin logs one `state-unreadable` error line and changes nothing until the file is fixed or moved aside. It never renames or replaces the file itself. On Linux and macOS a state write completes only after the state directory is flushed, so a record written before a send survives a host crash; on Windows the rename is not flushed, and a host crash soon after a write can bring back the previous state.

A send that fails with `Transport not connected` never reached the daemon, so the record stays parked and the next sweep retries on a fresh connection. That rollback starts from the stored record and undoes only what the send claim set (state, send time, deadline, and the new attempt). If a turn started on the agent after the claim, the message may have arrived after all, so the record becomes `uncertain` with its turn identity and deadline kept. Usage-limit records send nothing further; transient records take the live re-verification path and wait while that turn is running. The turn start is noted in memory the moment the event arrives, before the plugin writes it to the state file. A turn that arrives while the rollback itself is being written restores the claim's attempt, send time and deadline with the turn ID, again as `uncertain`, before the sweep moves on; a terminal state another event wrote meanwhile is kept. Any other send error marks the record `uncertain`, with transient delivery ambiguity taking the same live re-verification path. If the retry's user row has not appeared yet, its verification window is retained before another send is considered.

A send claims its record only while the record is still in the state the send checks passed on, unchanged since, and at the same attempt count. The claim stays unsent until the message is handed to the daemon. Until then a permission request, an archive, or any turn that starts or ends on the agent cancels it. The event is noted on the pending send the moment it arrives, its turn is never taken as the resume's, and nothing is sent. Right before sending, the plugin reads the agent again. It sends only if every send check still passes and the agent's latest user message time, running turn and last-change time match the snapshot the claim was taken on; otherwise it cancels the send. A cancelled claim leaves no attempt behind. A permission request puts the record back to waiting, since nothing was sent, and it sends on its schedule once the permission is answered (a permission request after a send makes the delivery ambiguous and ends `uncertain`); an archive or another turn ends `superseded`. A send receipt moves only that live claim on to verification. A terminal state stored while the send was in flight is kept.

The resume or retry is itself a user message, so the agent's latest user time moves past the record's. Verification accepts the newer time only when the newest user row in a complete timeline page carries the attempt's stable message ID and exact prompt, and then stores it. Any other newer message still supersedes the record. When that newer message's turn fails, its distinct turn ID gets a fresh record through normal detection, quota holding, and release, even if the old record was still parked or being evaluated. Identical error text does not deduplicate different turns. Usage-limit verification retains its fail-closed handling of incomplete pages; transient verification defers and rechecks incomplete evidence.

The state file keeps every record that can still send, is verifying a send, or is `uncertain`. Of the settled records (done, exhausted, opted out or superseded), it keeps the 200 most recently updated. Each settled record pruned beyond that leaves a guard: its agent, source turn and persistence session, of which the newest 2000 are kept. A repeated event for a turn with a record or a guard is a duplicate, even after the agent's configuration changed. Each sweep reads the file once and reads it again only for records that can still act. A failed-turn record keeps its 20 newest attempts in full; older ones are counted, so message IDs and backoff continue from the full count.

## Pi coverage

Paseo 0.10.3 and 0.11.1 Pi failures are not ordinary completed assistant finals. Pi emits an assistant message with `stopReason: "error"` and `errorMessage`; Paseo's `latestPiErrorMessage` formats the error with `(stopReason=error, model=<provider>/<model>)`, then `completeTurn` emits `turn_failed`. The daemon timeline displays a `[System Error]` row, and the plugin receives `outcome.kind: "failed"` with `outcome.error.message`. Detection therefore uses the failed outcome, not `turnText()` or the display prefix.

A credential-free Pi RPC fixture on a disposable Paseo 0.10.3 daemon emitted `You've hit your usage limit. Try again in 1 second.` and verified detection as **usage**, no immediate generic retry, a delayed same-session/model continuation, and a completed resume. This wording (including the typographic apostrophe variant) is now recognized alongside `usage_limit_exceeded`, `out of credits`, and existing explicit quota patterns. Generic 429/rate limits remain on the failed-turn path, not the five-hour usage path. Normal completed answers remain `not-resumable/unrecognized-final`. The plugin was then pinned to `>=0.10.3 <0.12.0` and built against the exact 0.11.1 `@getpaseo/*` packages; the same fixture was rerun with that build on disposable 0.10.3 and 0.11.1 daemons: unarmed it logged `would-resume`, and armed (60-second test delay) it sent one continuation that completed.

Usage records originating from a failed outcome now carry `usageFailedOutcome`, allowing a due continuation from `error` status and its error attention marker. This is separate from generic `failedOutcome`: usage failures retain `baseDelaySeconds` (five hours by default) and the reset buffer rather than the transient schedule. Completed usage records do not gain this error-status exception. Permissions, active turns, identity/model/thinking/session changes, opt-outs, and newer user messages still block sends.

Model tests cover Pi snapshots with high and medium reasoning, formatted quota errors, default five-hour timing, the retry schedule, same-session verification, and resume gates. The daemon action fixture used a 60-second test delay; actual provider quota resets and live retry timing were not measured. A Pi failure that does not emit a recognized usage-limit signal may follow the generic failed-turn path instead. Keep existing host settings unchanged. If automatic resume is unavailable, send one explicit `continue` to the same Pi agent and verify its session/model/thinking; use an explicitly selected native Codex or Claude route if a new fallback session is needed. This package does not select or substitute models.
