# Usage limit auto resume

Startup endpoint resolution uses explicit `PASEO_HOST`, then `$PASEO_HOME/paseo.pid` runtime listen metadata. An explicit non-default `PASEO_HOME` without valid endpoint metadata refuses to connect instead of falling back to another daemon. Invalid explicit hosts also fail closed. The standard local endpoint is a fallback only for an unset home or `~/.paseo`.

This server plugin keeps the existing usage-limit resume path (five-hour default) and adds a separate retry path for completed turns whose final assistant message is a transient provider error. Both paths obey the host `armed` setting and the `noresume=true` label. The plugin does not send while unarmed.

## Transient retry

The final assistant text must start with `API Error:` and contain `rate limit`, `rate_limit`, `temporarily limiting requests`, `overloaded`, `429`, or `529`. The exact final text `Selected model is at capacity` also qualifies. A normal answer that discusses these terms does not qualify. Explicit usage-limit failures retain the five-hour path.

Every turn that ends as `failed` (not `completed`) is resumed, whatever the error, unless it is an explicit usage limit (five-hour path) or the agent is opted out. The resume is a pure `continue` sent to the same session, never a replay, and it may be sent while the agent is in `error` status. Transient failed turns have no attempt cap: they retry immediately, then after 2, 5, and every 15 minutes until a turn succeeds, a newer user message arrives, or the agent is archived or closed. A failed resume turn re-arms the same record, with its next backoff measured from that failure, even if the provider spent hours retrying inside the turn. Identity/session changes, opt-outs, and permissions still block sends. Interrupted or cancelled turns are not resumed. The capacity match on completed turns also accepts Codex's `[System Error]` prefix and trailing `Please try a different model.`

The first retry is sent to the same agent immediately, then after 2, 5, and 15 minutes, at most three sends by default for completed-turn errors. If the agent has not settled yet, the immediate retry waits for the next sweep (30 seconds). `transientMaxAttempts` and `transientBackoffSeconds` configure these independently of `maxAttempts` and `baseDelaySeconds`. The plugin resends the last timeline user text exactly. If that text is empty, it asks the agent to continue the last request. It verifies a fresh timeline and agent snapshot before every send, including idle state, permission state, latest user message, model, and session. For transient records it follows older timeline pages until it finds the newest user row, so a long turn cannot hide its prompt behind the 200-row tail page. Transient `uncertain` records are re-verified on every sweep, including `retry-turn-ambiguous` and `user-prompt-missing`: a live failed turn with no newer human message is re-armed on the backoff; a running turn is left alone. Missing or incomplete evidence remains recoverable and is checked again, never treated as terminal. The latest user must match the checked original row or the retry's stable message ID and exact prompt. Usage-limit records retain their existing reset timing, attempt cap, and terminal uncertainty behavior. A successful retry removes its record or settles it as done during live re-verification.

## Quota awareness

Before it schedules a usage-limit resume, and again before every send, the plugin reads Paceline's quota CLI (`pq --json`, schemaVersion 1), the same source OPC's route pace uses (see `skills/orchestration/opc/references/routing.md`, Pace and Settings). The argv is the `pq` key of `~/.config/opc/routing.json` when it is a nonempty string array, else `["~/.local/bin/pq", "--json"]`; a leading `~` is expanded and pq runs without a shell. The agent's pool follows its provider and model as in OPC: Claude models (Opus, Sonnet, Fable, Haiku) read the claude accounts, GPT models (Sol, Luna, Astra) the codex accounts. Web and local models have no pool.

Only the `five_hour` and `seven_day` windows count. An account is out while one of them shows 0% left (or pq marks it blocking) and its reset, plus the buffer, is still ahead; it frees when its last out window resets. An account has quota only on a fresh reading whose windows all show some left. Any other account keeps the pool from reading as out.

- Usage limit: the resume is due about `quotaResetBufferSeconds` (60) after the pool's earliest real reset, the first time an out account frees (5-hour or weekly), instead of the flat `baseDelaySeconds`. Never earlier than a reset the error itself names. While another account still has quota, the reset only brings the resume earlier, never later than the flat delay.
- Transient and other failed turns: while some account in the pool has quota, retries run as before. If every account is out, the send is held until the earliest reset plus the buffer. A hold consumes no attempt.
- Out for the week: the same hold runs until the weekly reset. Every hold is logged once as `quota-hold ... reason="quota-blocked pool=<pool> weekly accounts=<n> until=<iso>"` (or `window=five_hour`) and stored on the record as `quotaHold`. No PM is notified; pooling handles rerouting. Each due sweep re-reads the quota, so an early reset or a freed account releases the hold (`quota-released`) and the send goes out.
- Unknown quota keeps today's behaviour exactly: pq missing, erroring, slower than `pqTimeoutSeconds` (5), unparseable, another schemaVersion, a stale snapshot, or a pool pq does not list.

One pq reading is shared for `quotaCacheSeconds` (60), so many failing agents start one pq process. `quotaAware: false` turns the feature off.

## PM quota fallback

Off by default (`pmFallback: false`). When on, a live Pi agent labelled `role=pm` on a Claude model moves to an exact catalog profile while its Claude pool is out, and returns to its original profile once Claude is usable again. Workers, watchers and any agent without `role=pm` never change model. A PM labelled `nofallback=true` (`pmFallbackOptOutLabel`) stays pinned: the plugin never changes its settings, not to swap, repair or return it; a pending return waits until the label is removed or the owner cancels it. Every write goes through one gate that also carries out a pending owner cancel first, on every trigger.

- Swap: after a PM turn fails with a usage-limit error, the same evidence a usage resume record is built from (a completed reply never swaps, whatever its text says), or a sweep finds its usage record on a quota hold), pq must positively show every Claude account out and must not show the fallback pool out. Unknown, stale or missing quota never swaps. The plugin first stores the exact original model, thinking option and `opc.service-tier` label, then sends one `agent.config.apply` with `pmFallbackModel` (`fleet/gpt-6.1-sol`) and `pmFallbackThinking` (`medium`) together, sets `opc.service-tier=fast` (`pmFallbackServiceTier`), and reads the agent back. The fallback model and thinking option must be listed verbatim in the Pi catalog; an unset original thinking option is stored as the model's catalog default. A stored swap intent that was not applied yet (after a crash or restart) is decided again before it is applied: the agent must still be an eligible PM on its original model and a fresh pq reading must still show Claude out, or the intent is dropped. Once the fallback model is in place the swap is finished whatever quota reads: a partial swap is repaired, the stored record confirmed and the PM's resume record moved to the new model, and only then is it a return. It is never dropped. The PM's resume record follows it to the new profile, so the existing resume engine continues the same session on Sol.
- Return: the obligation lives in `<PASEO_HOME>/plugin-state/usage-limit-auto-resume/pm-return.json`, apart from resume records. Superseding, settling or pruning a record, plugin reload, daemon restart and idle periods do not remove it. The return is due only while pq, read fresh at that moment, shows a Claude account with fresh five-hour and weekly readings that both have quota left. A weekly-out account whose five-hour window reset, a missing weekly reading, or stale or unknown quota does not count, and an earlier due reading never authorizes a restore by itself.
- Applying: settings are applied whenever a swap or due return is outstanding, on `agent.turn_ended` and on the poll sweep as a backstop. A PM in the middle of a turn is changed too: Paseo applies the settings to its next turn and never interrupts the current one (verified on a scratch 0.11.1 daemon with the real Pi CLI). A change counts as done only once the daemon's stored agent record (`<PASEO_HOME>/agents/`, what a reload or restart loads) holds it too, since Paseo acknowledges settings in memory and persists them in the background. A mismatch on read-back, a change that never reaches the stored record, or a rejected update keeps the obligation and is tried again at the next turn end or sweep; it never settles on its own. While a swap or due return is unverified, the resume engine sends nothing for that PM.
- Only an explicit owner cancel ends a return early. A manual model change, a lost `role=pm` label or turning `pmFallback` off does not. An archived PM is never changed or resumed; its obligation waits.
- Sol also out: no swap, ordinary quota hold. On Sol and Sol runs out: ordinary hold on Sol until Claude returns. No ping-pong.
- Logs: `pm-swap-start`, `pm-swap-apply`, `pm-swap-verified`, `pm-restore-due`, `pm-restore-apply`, `pm-restore-verified`, `pm-*-failed`, `pm-*-mismatch`, `pm-*-unpersisted`, `pm-swap-dropped`, `pm-swap-not-completed`, `pm-return-waiting`, `pm-fallback-held`, `pm-enrolled`, `pm-return-cancelled`.

Limits. Paseo has no idle-only settings barrier, so a message that lands between the return becoming due and the settings write can run one more turn on Sol; the next turn runs on the original profile. Paseo labels cannot be deleted, so an originally absent `opc.service-tier` is restored as an empty value, which fleet routing treats as absent. The settings writes use the daemon client that `@getpaseo/client` wraps (`applyAgentConfig`, `updateAgent`), because the public agent handle has no setter for them.

### Enroll a PM that already fell back, or cancel a return

Both go through the host settings file, which the plugin re-reads every sweep. Back it up first and keep its other values. Copy the original model ID verbatim from `paseo provider models pi --thinking`; `serviceTier` is the PM's original `opc.service-tier` label, or `null` if it had none.

```bash
f="${PASEO_HOME:-$HOME/.paseo}/plugin-settings/usage-limit-auto-resume/auto-resume-config.json"
cp "$f" "$f.bak-$(date -u +%Y%m%dT%H%M%SZ)"
jq --arg id "<agent-id>" --arg model "<original-model-id>" --arg thinking "<original-thinking-id>" \
  '.values.pmFallbackEnroll += [{agentId: $id, model: $model, thinkingOptionId: $thinking, serviceTier: null}]' \
  "$f" > "$f.tmp" && mv "$f.tmp" "$f"
```

The entry is applied once (`pm-enrolled`, or `pm-enroll-rejected` with a reason): the agent must be a live Pi `role=pm` agent not already on that profile, and the original must be a Claude model in the catalog. The PM keeps its current profile until the return is due. To cancel one return, add its `obligationId` (from `pm-swap-start`, `pm-enrolled` or `pm-return.json`) to `pmFallbackCancel` the same way: `jq --arg id "<obligation-id>" '.values.pmFallbackCancel += [$id]'`.

Follow-up seam (not in this plugin): a worker never swaps. A read-only planning companion for a parked worker would use the same quota-release signal (`restoreDue` in `server/fallback.ts`) and the worker's parked resume record, without changing the worker's model.

## Pattern evidence

- Claude has emitted `API Error: Server is temporarily limiting requests (not your usage limit) · This request would exceed your account's rate limit. Please try again later.` as a synthetic assistant message with `apiErrorStatus: 429`.
- Claude has also emitted `API Error: Request rejected (429)` with `rate_limit_error`.
- Codex has recorded `Selected model is at capacity`.
- Anthropic documents `529 overloaded_error` as temporary overload and `429 rate_limit_error` as a rate limit: <https://docs.anthropic.com/en/api/errors>. A 429 can also indicate a spend cap, so explicit usage-limit text takes priority and unknown messages are not retried.

Paseo's [`agent.turn_ended` event](https://paseo.sh/docs/plugins/reference.md#lifecycle-hooks) supplies a complete timeline snapshot and a completed outcome. The SDK's timeline `refetch()` supplies the fresh page used for the final send check.

## Settings and install

Host-scoped settings are stored by Paseo at `<PASEO_HOME>/plugin-settings/usage-limit-auto-resume/auto-resume-config.json` as `{"version":2,"values":{...}}`. A missing file means defaults, and the default is `armed: false`, so a fresh install observes and records but sends nothing. Arm a host only after reviewing `paseo plugin logs usage-limit-auto-resume`, by writing `{"version":2,"values":{"armed":true}}` to that file.

Resume records live in `<PASEO_HOME>/plugin-state/usage-limit-auto-resume/state.json`. A missing file means no records. If the file is unreadable, corrupt, from another state version, or holds a malformed record (a missing id, an unknown state, or an unparseable time such as `notBefore`), the plugin logs one `state-unreadable` error line and changes nothing until the file is fixed or moved aside. It never renames or replaces the file itself. On Linux and macOS a state write completes only after the state directory is flushed, so a record written before a send survives a host crash; on Windows the rename is not flushed, and a host crash soon after a write can bring back the previous state.

A send that fails with `Transport not connected` never reached the daemon, so the record stays parked and the next sweep retries on a fresh connection. That rollback starts from the stored record and undoes only what the send claim set (state, send time, deadline, and the new attempt). If a turn started on the agent after the claim, the message may have arrived after all, so the record becomes `uncertain` with its turn identity and deadline kept. Usage-limit records send nothing further; transient records take the live re-verification path and wait while that turn is running. The turn start is noted in memory the moment the event arrives, before the plugin writes it to the state file. A turn that arrives while the rollback itself is being written restores the claim's attempt, send time and deadline with the turn ID, again as `uncertain`, before the sweep moves on; a terminal state another event wrote meanwhile is kept. Any other send error marks the record `uncertain`, with transient delivery ambiguity taking the same live re-verification path. If the retry's user row has not appeared yet, its verification window is retained before another send is considered.

A send claims its record only while the record is still in the state the send checks passed on, unchanged since, and at the same attempt count. The claim stays unsent until the message is handed to the daemon. Until then a permission request, an archive, or any turn that starts or ends on the agent cancels it. The event is noted on the pending send the moment it arrives, its turn is never taken as the resume's, and nothing is sent. Right before sending, the plugin reads the agent again. It sends only if every send check still passes and the agent's latest user message time, running turn and last-change time match the snapshot the claim was taken on; otherwise it cancels the send. A cancelled claim leaves no attempt behind. A permission request ends `uncertain`; an archive or another turn ends `superseded`. A send receipt moves only that live claim on to verification. A terminal state stored while the send was in flight is kept.

The resume or retry is itself a user message, so the agent's latest user time moves past the record's. Verification accepts the newer time only when the newest user row in a complete timeline page carries the attempt's stable message ID and exact prompt, and then stores it. Any other newer message still supersedes the record. When that newer message's turn fails, its distinct turn ID gets a fresh record through normal detection, quota holding, and release, even if the old record was still parked or being evaluated. Identical error text does not deduplicate different turns. Usage-limit verification retains its fail-closed handling of incomplete pages; transient verification defers and rechecks incomplete evidence.

The state file keeps every record that can still send, is verifying a send, or is `uncertain`. Of the settled records (done, exhausted, opted out or superseded), it keeps the 200 most recently updated. Each settled record pruned beyond that leaves a guard: its agent, source turn and persistence session, of which the newest 2000 are kept. A repeated event for a turn with a record or a guard is a duplicate, even after the agent's configuration changed. Each sweep reads the file once and reads it again only for records that can still act. A failed-turn record keeps its 20 newest attempts in full; older ones are counted, so message IDs and backoff continue from the full count.

```bash
npm run check
paseo plugin install "$PWD"
```

## Pi coverage

Paseo 0.10.3 and 0.11.1 Pi failures are not ordinary completed assistant finals. Pi emits an assistant message with `stopReason: "error"` and `errorMessage`; Paseo's `latestPiErrorMessage` formats the error with `(stopReason=error, model=<provider>/<model>)`, then `completeTurn` emits `turn_failed`. The daemon timeline displays a `[System Error]` row, and the plugin receives `outcome.kind: "failed"` with `outcome.error.message`. Detection therefore uses the failed outcome, not `turnText()` or the display prefix.

A credential-free Pi RPC fixture on a disposable Paseo 0.10.3 daemon emitted `You've hit your usage limit. Try again in 1 second.` and verified detection as **usage**, no immediate generic retry, a delayed same-session/model continuation, and a completed resume. This wording (including the typographic apostrophe variant) is now recognized alongside `usage_limit_exceeded`, `out of credits`, and existing explicit quota patterns. Generic 429/rate limits remain on the failed-turn path, not the five-hour usage path. Normal completed answers remain `not-resumable/unrecognized-final`. The plugin is pinned to `>=0.10.3 <0.12.0` and built against the exact 0.11.1 `@getpaseo/*` packages; the same fixture was rerun with that build on disposable 0.10.3 and 0.11.1 daemons: unarmed it logged `would-resume`, and armed (60-second test delay) it sent one continuation that completed.

Usage records originating from a failed outcome now carry `usageFailedOutcome`, allowing a due continuation from `error` status and its error attention marker. This is separate from generic `failedOutcome`: usage failures retain `baseDelaySeconds` (five hours by default), reset buffer, and `maxAttempts`, rather than uncapped transient retries. Completed usage records do not gain this error-status exception. Permissions, active turns, identity/model/thinking/session changes, opt-outs, and newer user messages still block sends.

Model tests cover Pi snapshots with high and medium reasoning, formatted quota errors, default five-hour timing, attempt caps, same-session verification, and resume gates. The daemon action fixture used a 60-second test delay; actual provider quota resets and live retry timing were not measured. A Pi failure that does not emit a recognized usage-limit signal may follow the generic failed-turn path instead. Keep existing host settings unchanged. If automatic resume is unavailable, send one explicit `continue` to the same Pi agent and verify its session/model/thinking; use an explicitly selected native Codex or Claude route if a new fallback session is needed. This package does not select or substitute models.
