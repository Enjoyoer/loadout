# Changelog

All notable changes are listed here. Loadout follows [semantic versioning](https://semver.org).

## Unreleased

### Added

- `history-cwd-fallback` 0.1.0, a server-only Paseo plugin. An archived agent whose Paseo worktree was deleted, for example a worker worktree removed after its merge, can open its timeline again. Paseo reads that history by starting the provider in the stored directory, and the spawn failed with `spawn <node> ENOENT` before the provider (Pi's `mcp-env.cjs` launcher) could run. A plugin hook cannot change that directory. For a history open, the plugin puts a link to an empty read-only directory under `<PASEO_HOME>/plugin-state/history-cwd-fallback/` at the missing path, recorded in a ledger first, and removes it 6 s later, about twice the longest Pi start measured on 0.11.1 and 0.13.0 (3.0 s under heavy load). Paseo emits no event after the spawn. The provider keeps running in the empty directory. It links only a path strictly inside Paseo's worktrees root (`worktrees.root`, else `<PASEO_HOME>/worktrees`) whose parent already exists, with no link and no git work tree between the root and that parent. It never creates directories. Any other missing path fails as before. The agent's stored directory never changes, and a present directory is untouched. Any other open of a linked path, such as the turn open of a send or an unarchive, is refused with `Working directory does not exist`, as Paseo refuses once the link is gone. The history load that comes before a send can make the link, since the hook input cannot tell it from a timeline open. The send is then refused, so the agent stays archived and no turn runs. Links are removed when the plugin stops and, after a crash, when it starts. A link is removed only while it still points to the plugin's empty directory, and no link is made while that directory is not empty. An unreadable ledger is moved aside. A workspace restore in those 6 s still takes Paseo's unarchive path and turns the worktree workspace into a directory workspace; that window and the other known limits are in its README. Checked on scratch Paseo 0.11.1 and 0.13.0 daemons with Pi agents.
- personal-skills: Pi direct providers can send a token. `directProviders.<name>.auth` takes `{"credential": <source>}` as well as `"none"`: Pi's key becomes a `!command` that runs `credential.py` on that source for every request, so Pi sends `Authorization: Bearer <value>` and the value never lands in `models.json`, `runtime.json`, agent copies or logs. The source must be an exact reference with only its kind's fields and no `prefix`, so a literal value, a plain string or an unknown key is refused. A new `command` source kind runs one fixed argv without a shell and reads one stdout line, for a token kept in an OS secret store instead of a plain-text file; the program must be an absolute path, POSIX or Windows whichever host derives the payload, to an allowlisted helper (macOS `security find-generic-password`, Linux `systemd-creds decrypt` to stdout `-`, or Python running a helper script file). A missing or failed credential fails only that provider's requests; `"none"` behaves as before. The fleet README shows a one-time store step per OS, and `example/pi-provider-overlay.json` a Keychain-backed direct provider.
- Pi launcher: a per-agent skill exclusion. `settings.overlay.json` may now also hold `"skillsExclude": ["<skill name>", ...]`, so one agent (for example each PM) drops some skills from its skill index while the other agents keep them. Each entry must be unique and name a skill directory, holding a `SKILL.md`, directly under exactly one of the roots Pi 1.0.0 loads skills from: the shared `<pi root>/agent/skills`, the agent's own `<pi root>/agents/<agent id>/skills`, and `~/.agents/skills` (where Paseo installs its own skills, such as `paseo-advisor`; `$HOME` first, then the OS home, as Pi resolves it, so `%USERPROFILE%\.agents\skills` on Windows). A name found in no root, or in two (ambiguous), a path, glob, `..`, Pi pattern prefix or an empty list refuses the launch. Project `.pi/skills` and `.agents/skills` folders load only for a trusted project, and Pi in RPC mode under the fleet's `defaultProjectTrust: "never"` trusts none, so they are not roots. The launcher appends Pi's exact exclusion `-<that root>/<name>` (native path form) to the merged `skills` list, which on Pi 1.0.0 removes that skill from the system prompt's skill list and from `/skill:` commands; nothing else about `skills` is overlay-settable. A glob exclusion `!<name>` would also drop a same-named skill directory in another root, so it is not used. Deleting the key or the overlay restores the skills at the next launch or `paseo agent reload`. Checked on real Pi 1.0.0 through the launcher on macOS and Windows, with a skill from each root (for example `paseo-advisor`) and a 9-skill PM list. Shape: `fleet/README.md`.
- reassign-pm: step 5 also carries the old PM's `settings.overlay.json` and `models.overlay.json`, exactly like `APPEND_SYSTEM.md`: copied unchanged into the new PM's agent dir when the old PM ran on Pi on the same host, hash-checked, never overwriting a different existing one, and reported. A new PM had started without the old PM's per-agent overlays, such as its skill exclusions.
- `wizard` restored in `loadout-ops` (owner decision 2026-10-23): it generates an interactive bash script that walks a human through manual setup, credential, or migration steps. It returns unchanged from its last reviewed version, before it was retired in #138, including the #107 credential-safety fixes (one bound project root, env file, and GitHub repository; safe `.env` writes), with its `tests/test_wizard.py` suite.
- Pi launcher: per-agent overlays. An owner or PM may write `models.overlay.json` or `settings.overlay.json` into a Pi agent's `<pi root>/agents/<agent id>/`, for example to give two agents a different context window for a trial. Before, every launch overwrote that agent's `models.json` and `settings.json` from the shared copies, so a per-agent change was lost. Each launch still starts from the shared copies and then applies the overlay, so deleting an overlay restores the defaults at the next launch or `paseo agent reload`. Overlays are a strict allowlist: a models overlay may set only `contextWindow` and `maxTokens` on models the shared catalog already has, matched by provider and `id`, and a settings overlay may set only `compaction` (`enabled`, `reserveTokens`, `keepRecentTokens`, and `modelOverrides` for existing `<provider>/<model id>` keys). Anything else, including executable packages, proxies, routes, credentials and Codemode settings, a wrong JSON type, an empty object or list, a non-positive count, an unknown provider or model, invalid JSON or an unreadable file, refuses the launch before any agent file is written. The merged settings must still pass the Codemode check. Probes and launches without a caller never read overlays. The syncs create, overwrite and remove no overlay. Exact shape: `fleet/README.md`.
- `trial` skill: tests an idea (a video, an X bookmark, a skill or workflow change) against the last 14 days of real work before adopting it. It splits the idea into rules, finds help and harm cases with evidence, replays at most 3 cases in scratch copies, and reports Adopt, Adopt modified or Drop per rule to the owning PM, who decides.
- bw-login: `bw-paste update` and `rotate` can change items that have a per-item key when the Mac's rbw is a patched rbw 1.15.0 whose agent `Encrypt` accepts an item key, identified by a version marker. bw-paste writes only after the running agent proves it encrypts with the item key: a rotate checks this before any new password reaches a page, and every write checks again that each new value decrypts with the item key. Otherwise it refuses and writes nothing. With a stock rbw, behavior is unchanged.
- bw-login: section 6 lets agents save (`bw-paste add`, into the Bitwarden folder `Agents`) and update (username, URI, notes) the current site's login. The helper generates passwords and enforces the site scope against the server's current copy of the item. Password rotation is not available yet (`bw-paste rotate` refuses). A saved change whose local sync failed is reported separately (exit 8). Agents never save a password a website shows, never delete, run each vault command once, and report every change (item, site, fields, never values). Agents never run `bw-unlock` or `bw-lock`.
- `START-HERE.md` at the repo root again, rewritten as a one-screen guide for someone copying a few skills: the layers, how the owner works, the minimum to copy, and what to replace. The README links it at the top. Root Markdown is now README, START-HERE, CHANGELOG and THIRD_PARTY_NOTICES (owner decision 2026-10-20).

Fast clicks and keys share fresh inspection and serialized writes; effort validates the same-daemon model/options and confirms settings-only updates. Rebind Toggle focus mode before using F. Documented 0.11.1 host-shell sizing, Tab focus trapping and duplicate-agent pane limitations fail closed rather than using private APIs.

- personal-skills: Codex and Claude Code run by hand use the user's own login; only Paseo-launched agents route through the fleet proxy. `paseo-providers.json` takes `launch` settings, top level or per host, for `claude`, `codex` and `pi`: `tokenFiles` maps an env name to an owner-only host file that the `mcp-env.cjs` launcher reads into the child env at launch time (never stored in config or printed), and `args` are flags the launcher puts right after the executable, such as Codex `-c model_provider="<id>"` before `app-server`. Wrapped commands become `node mcp-env.cjs --provider <id> -- <command>`, and `mcp-env.json` becomes `{servers, providers}`. On Windows the launcher wraps the default `claude`/`codex` commands too, resolving them through `PATH` and `PATHEXT` as Paseo does and running an npm `.cmd` shim's Node script directly, without `cmd.exe`; it accepts only token files whose ACL, checked on the handle it reads, is owner-only, and `scripts/new_token_file.ps1` creates one. Client-config removes the listed routing keys on a providers host only after that host's current provider settings are written and reloaded, reporting `held` until then. `client-config.json` takes `codex.removeTop` and `claude.removeEnv`, at any layer, to delete keys an earlier sync managed (for example `model_provider`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`) with the usual backup; a key both managed and listed is refused. The example fleet drops global routing and adds `example/routed-launch-overlay.json`.

- `usage-limit-auto-resume` 0.3.0 (trial through 10/27): retries never give up. On 10/21, PMs failed with Anthropic's `429 rate_limit_error` ("This request would exceed your account's rate limit") while pq still showed 31% weekly quota, and 0.2.2's repeated-quota-error stop ended each record `exhausted` (`quota-error-repeated`) after two retries, leaving the PMs idle until a human prompted them. That stop, the attempt caps (`maxAttempts`, `transientMaxAttempts`) and the `retry-stopped` log are removed. Every retry now goes out immediately, then after 2, 5 and 15 minutes, then every 30 minutes for as long as it fails (`transientBackoffSeconds` default `[0, 120, 300, 900, 1800]`, last step repeating), and ends only on success, a newer user message, an opt-out, or the agent being archived or deleted (a deleted agent's record ends on the second sweep that finds no agent). `maxAttempts` and `transientMaxAttempts` are still accepted in settings files but ignored. A `closed` agent no longer ends its record: Paseo 0.11.1 stores every agent as `closed` when the daemon shuts down, so 0.2.2 superseded every pending retry after a daemon restart (`agent-closed-or-archived`); the send now loads the agent again, and the record's own last send is still recognized on the timeline Paseo rebuilds after a restart (new message IDs, no `clientMessageId`), so a waiting retry survives a daemon restart as well as a plugin reload. A usage resume whose turn fails hands off to a new record for that turn (`resume-failed-rescheduled`) instead of ending `uncertain`, and an attention request only holds a usage resume instead of ending it. The quota hold until a pq reset, PM fallback swaps and Pi prompt-timeout handling are unchanged; 0.2.x records already `exhausted` stay settled, and mid-retry records continue on the new schedule. `would-resume` and `send-deferred` are logged once per attempt instead of every poll, and `retry-scheduled` and the `not-due` `send-skipped` carry the next `notBefore`. The PM fallback opt-out is removed too: a PM that inherited `nofallback=true` through a PM reassignment had its swap skipped (`pm-fallback-skipped reason=opted-out`). Now every live Pi `role=pm` agent on a Claude model is eligible, whatever its labels, including for repairing a landed swap and for the return. `pmFallbackOptOutLabel` is still accepted in settings files but ignored. Review fixes: a failed resume turn's handoff to its successor (and a retry's handoff to a usage record) is one guarded store write, so a duplicate end event for the same turn can no longer overwrite a successor that already succeeded and send again. An explicit close or kill ends the record like an archive (`agent-closed`). A close sent by a daemon shutdown is told apart by the daemon run (the plugin's parent process): a new run clears it, and a run that outlives the close by 60 seconds ends the record. Nothing is sent until then. The close is stored per agent, so it also holds a record that a handler still in flight creates after it. Work that began with a user message newer than the close goes on. That user message is the failed turn's own row, bound by identity from its `turn_ended` event, carried on by every successor and never taken from a later snapshot. A failure is stale (`stale-failure`, no record) only when the timeline's latest user row is a different, later message. This is decided from daemon evidence alone, never the plugin's clock, so clock skew cannot drop a failure. The check never reads a closed agent's timeline, including one whose close landed while the handler was reading the agent, so it never loads a killed agent again. A rebuilt timeline row matches by text and an unchanged `lastUserMessageAt` on every path, so a first retry held by quota, or a waiting `uncertain` retry, is no longer superseded after a daemon restart. A permission request on a record that has not sent only holds it; it no longer leaves a usage record `uncertain` for good.
- bw-login: password rotation is available again, only when the owner asks for it in that task, and both rotate and browser sign-up are now two-phase: `bw-paste` fills and submits, keeps the generated password pending (encrypted, at most 10 minutes), and changes the vault only after the agent signs in with it in a fresh browser session (`--signin`, then `--commit`). A page that disappears, an error panel, a redirect or a session-expired page is never taken as acceptance. A rotate that is not confirmed leaves the vault unchanged; a sign-up that is not confirmed is saved with the note `unconfirmed: verify by sign-in` (exit 9) rather than lost, unless the site shows the sign-up form again (`add --discard`). Generated passwords fit the field's `minlength`, `maxlength` and `pattern`. Add without a browser is saved marked unconfirmed. `bw-paste update` takes `--uri-add` up to 10 times, all or nothing. A site on another domain (or a login's first URI) can be added only with `--cdp`/`--cdp-profile` and the tab on exactly that https origin, one per call; it is audited and printed as cross-domain, and agents report each one to the owner.

A generated password that page code saw before the helper submitted goes to recovery instead of being deleted. - bw-login: security review fixes for `bw-paste` (#188). A browser-level guard (CDP request interception and URL events, armed before the password goes in) stops any request carrying the password in its URL or to another site, across every frame and tab, and any URL that held the password is a leak (exit 6) on every exit path. Success needs the page to stay clean for a moment and a final field check. Rotate and add commit need the tab of an acknowledged sign-in and a page showing the login's username. A password the site may have is never deleted: ended, expired or unsaved ones wait in recovery (`bw-paste recover`), with a notification for the owner. Per-item locks, strict tunnel schemas, and a rate-limit result that keeps its meaning. A cross-domain `--uri-add` saves only that exact host, and is printed and notified as a widen; the owner chose no extra approval step.
- bw-login: `bw-paste` submits only by clicking the field's own submit control (or the sign-in widget's single button), never `form.submit()`. If the page does not handle that submit itself and the form would send by GET (a form without a method is GET) or to another site, it cancels the browser's submission and refuses (exit 5), so a credential never goes into a URL; sign-in widgets inside an outer GET form that handle the submit keep working. After every submit it checks the tab's URL and history for the value; a match is exit 6 `CREDENTIAL LEAKED`, with the tab closed, and the agent must ask the owner to rotate the credential (2026-10-20 incident: a sign-in widget inside an outer form sent the password in the URL).
- bw-login: a "Pick the path" table up top, and a hard stop: never submit unless every credential field's length is above 0 and grew by the paste (a prefilled field never counts; on the CDP path, a successful helper call for each credential field replaces the growth check); otherwise clear, stop and report. The clipboard path needs a Mac or Windows shell known to be in the browser's own desktop session (never Linux, whose copy goes to the Mac; `navigator.platform` only rules out an OS mismatch) and a `probe123` paste that reads back equal; otherwise use a Playwright browser with the CDP fill, or stop.
- bw-login: adds a CDP fill path for Playwright and other automation-owned Chromium browsers, which the OS clipboard does not reach. `bw-paste <id> username|password --cdp-profile <dir>` (or `--cdp http://127.0.0.1:<port>`) writes the value over the loopback DevTools protocol into the exact field it checked, never into whatever has focus. It needs exactly one matching tab and a page URL that matches a saved URI under that URI's Bitwarden match mode (Host compares port; Starts with and Exact compare port, path and `#` route; Regular expression and Never never authorize). Passwords require `--submit`: the helper submits the field's own form and succeeds only after verifying that no password field still holds a value. Exit 5 means the value is not in the page. Exit 6 (`UNSAFE STATE`) means it could not verify that, so it closed the tab, or asks the agent to close the session. On every path, nothing but a length-only check may snapshot, screenshot, eval, trace or record the page between the password fill and the submit, because Playwright, Paseo and Browser Use snapshots can contain field values. Afterwards a length-only check must show the password fields empty, or the tab is closed, before any snapshot. "Do not improvise" becomes "use only these paths; anything else, stop and report".

- OPC task locks are never reclaimed implicitly. A lock is published already holding its writer's pid, start time and a unique token (a hard link to a finished file); the writer checks its token before replacing `task.json` and releases only a lock that holds it. A writer that finds a lock fails after 2 s with `task lock busy`, naming the holder and the recovery command, and `task-state.mjs unlock <task.json>` removes a crashed writer's lock only when its pid is gone or reused. On Windows the rename is not flushed, so a host crash soon after a write can bring back the previous state.

Concurrent first state reads share one read, so a slow read cannot roll back a newer write.
- `cache-aware-autocompact` takes a running tool call's status from fresh history on each retry, so a tool that completed, failed, or was canceled after its turn ended no longer blocks compaction until the retries run out. A tool call with a status the plugin does not know counts as running, and a remembered turn must hold only running tool calls with a call id.

A turn that started during the send, even one the turn-start handler has not stored yet or one that arrives while the rollback is being written, turns the record `uncertain` with its turn ID, deadline and attempt kept, instead of re-arming a duplicate send.
- `usage-limit-auto-resume` claims a record for a send only while it is unchanged since the send checks, at the same attempt count. Until the message is handed to the daemon, a permission request, an archive, or any turn that starts or ends on the agent cancels the send, and that turn is never taken as the resume's. The agent is read again right before sending, and a newer user message, a turn change or a failing send check cancels it. A send receipt no longer turns a terminal state back into `verifying`. A resumed turn still running at the next poll is no longer superseded by the plugin's own message, and failed retries keep their backoff and attempt count. The state file never prunes a record that can still act or is `uncertain`. It keeps at most 200 settled records, plus a guard (agent, source turn, persistence session) for up to 2000 pruned ones, so a repeated turn event stays a duplicate. Sweeps re-read the file only for actionable records, and failed-turn records keep their 20 newest attempts.
- `orphan-project-sweeper` no longer treats a non-empty parent as proof of a mount. On Linux and macOS every mount point `/etc/fstab` declares over a project root must be mounted; on Windows no existing ancestor may be a junction, symlink, volume mount point or non-directory, and a parent or drive root that cannot be read, or is not a directory, is unverifiable rather than missing (`mount-absent` and `mount-unverifiable` skips). The root, parent and mount checks run again immediately before `removeProject`.

- OPC test recovery tells a reused pid from the recorded process by its exact start time, read in one fixed format, and stops the test command's process group, on POSIX even after its leader exited; a pid reused by another process is never signalled and the record says the cleanup is incomplete. Windows uses `taskkill /T /F`, which cannot reach a descendant orphaned after its parent exited. Task locks record their holder's start time; a live holder whose start time cannot be read keeps its lock.
- OPC relaunches a recorded Worker lane (repair, restart) after a class-table change. Given the task record, lane and lane class, the Worker request and brief take only the lane's recorded route and rebuild it while it keeps the owner's rules for that class, whatever its recorded source: code classes never run a GPT or web model, `ui` is exactly Opus xhigh with Fast off, and no route runs below its class minimum. A task default also keeps its class's model and Fast, at any effort up to the class ceiling that the Pi catalog still serves. An explicit provider must be the one the validated route maps to, and `route.mjs` refuses route flags that would select another route for a recorded lane.

- Fleet push writes the fleet copy and its `.loadout-sync.json` through uniquely named, exclusively created temp files and reads the record back, so a planted `<file>.loadout-tmp` link can no longer redirect a write; a leftover temp name is skipped only when it is a regular file.
- Fleet push, skills sync, and plugins sync check each write and removal again right before it: the directories from the home directory down (a linked `~/.claude` or `~/.config` is refused) and the file itself. A file edited after preflight is not written over, and a removal moves the file aside and verifies it first, so an edit made meanwhile is kept and the host fails.

- Skills and plugins sync refuse paths that are not portable (a backslash, colon, control character, trailing dot or space, or a Windows device name) or that name one file on a case-insensitive host, and check each plugin file against its own plugin directory; `generate_manifest.py` and the skills overlay refuse such paths before publication. A plugin file or skill renamed only in case is no longer removed or retired, which on a macOS or Windows host would remove the published one.
- Skills sync updates the overlay history as one transaction under an OS lock, written through a temp file and an atomic replace.
- Fleet push, skills sync, and plugins sync share one destination path check. Plugins sync now also refuses a file path that leaves the plugin root, and all three refuse a dangling symlink among a destination's parent directories.
- Plugins sync records each staged plugin's check result on the host and runs a failed or missing check again, instead of reporting success on a rerun; a plugin whose re-check passes is reloaded. Files no longer published are removed from the staged plugin directory while unedited.
- Provider sync records a reload owed after a write and retries it on the next run; a retry that fails is `FAILED`, not a warning.
- Skills sync retires a skill it installed (per the host's sync record) once it is no longer published, keeping and reporting a locally edited one, and records an overlay hash only after a host accepts it.

- The skills, plugins, and client-config programs write through uniquely named temp files and rename one only while it is still the file they wrote.
- `cache-aware-autocompact` no longer lets two state stores in one process clobber one temp file or an old store write after a reload. Every store for a file shares one write queue; a newer store fences off older ones, and teardown waits for the write in flight.
- `cache-aware-autocompact`, `pm-native-worker-guard`, and `usage-limit-auto-resume` write their JSON state through one shared atomic writer, `plugins/_shared/atomic-json.ts`: a uniquely named, exclusively created temp file, flushed and renamed over the state file, with a brief retry when Windows reports the file busy. A temp file that cannot be removed after a failed write is reported with that write's error. The on-disk format is unchanged.
- Fleet sync clears an inherited `PASEO_HOST`, `PASEO_HOME`, and agent variables in every host program and provider reload, so a provider reload, a plugin install, and their config reads all address the host's own daemon, never one the launching session or a host's shell profile named. A host's optional `paseo_home` in `hosts.json` sets that daemon's home instead of the default.

- Provider sync checks the host config and `required_env` before touching the Pi runtime, counts a Pi runtime change (or a runtime configuration that failed partway) as a write that owes a reload, and merges onto a config another writer changed during the merge instead of overwriting it.

Both client files are written through an fsynced temp file and renamed only while they still hold the revision the merge read; a concurrent change is merged in one retry, then the host fails.
- Provider and client-config backups get a unique name and are created new, so two updates in one second no longer overwrite the first backup.
- Pi deploy rollback checks every runtime file for edits, symlinks, and reparse points (junctions included) before changing anything, restores atomically, and checks the daemon config and backup again right before restoring the config; apply merges onto a daemon config changed during the install instead of overwriting it, and both stage the config through an unpredictable, exclusively created temp file and refuse a config that is not a regular file.
- The Pi picker patch replaces its state, bundle, entry, and backups atomically and remembers the previous patch generation, so an interrupted write can still be checked, reapplied, and rolled back.
- Provider sync fails a relay host's write with a readiness timeout, sending nothing, when its terminal shows no shell prompt.
- The fleet docs no longer promise a no-fleet single-host sync; a one-host fleet does that.
- Fleet sync's remote programs travel on stdin with their payload in one SHA256-checked envelope, so the ssh command line is a short fixed boot and Windows hosts stay far below the `cmd.exe` length limit; a corrupted envelope runs nothing.
